## Q1. Grace merges the full roster against a scores feed that's missing one player, validating cardinality and tagging each row's origin, then filters by score with `.isin()`. What does this print? (Roadmap #40, #15, #28)

```python
import pandas as pd

roster = pd.DataFrame({
    'name': ['Alice', 'Bob', 'Carol', 'Dave'],
    'team': ['Red', 'Blue', 'Red', 'Blue'],
})
scores = pd.DataFrame({
    'name': ['Alice', 'Bob', 'Carol'],
    'stats.score': [88, 45, 92],
})

merged = roster.merge(scores, on='name', how='left', validate='one_to_one', indicator=True)
print(merged['_merge'].tolist())
print(merged.loc[merged['name'] == 'Dave', 'stats.score'].isna().tolist())

high_scorers = merged[merged['name'].isin(scores.loc[scores['stats.score'] > 50, 'name'])]
print(high_scorers['name'].tolist())
```
A. `['both', 'both', 'both', 'right_only']` then `[True]` then `['Alice', 'Carol']` — gets everything else right but mislabels Dave's indicator as `'right_only'` rather than `'left_only'`; a row that came only from the *left* frame (`roster`) is tagged `'left_only'` — `'right_only'` would mean a row existed only in `scores`, which can't happen here since `how='left'` keeps every roster row no matter what
B. Raises `MergeError` — wrongly assumes `validate='one_to_one'` requires every key in `roster` to also exist in `scores`; `validate` only checks that the merge key isn't *duplicated* within either frame, it says nothing about keys matching across the two — whether an unmatched key is kept or dropped is entirely `how=`'s job
C. `['both', 'both', 'both', 'left_only']` then `[True]` then `['Alice', 'Bob', 'Carol']` — gets the merge and missing-value parts right but wrongly assumes `.isin()` pulls in every name that appears in `scores` at all, rather than only the names surviving the `stats.score > 50` filter applied first — Bob's `45` should exclude him
D. `['both', 'both', 'both', 'left_only']` then `[True]` then `['Alice', 'Carol']` — `how='left'` keeps every roster row including Dave, who has no match in `scores` and is correctly tagged `'left_only'` with a `NaN` score. `validate='one_to_one'` passes silently because `name` is unique in both frames — it was never checking whether Dave *has* a match. `scores.loc[scores['stats.score'] > 50, 'name']` is `['Alice', 'Carol']` (Bob's `45` fails the filter), so `.isin()` against that keeps only Alice and Carol

## Q2. Spot the bug — Grace wants each row tagged with its team's average score, so she tries writing it as a plain groupby aggregation assigned straight into a new column, then fixes it. What does this print? (Roadmap #40, #13, #30)

```python
import pandas as pd

df = pd.DataFrame({
    'team': ['Red', 'Red', 'Blue', 'Blue', 'Blue'],
    'score': [88, 92, 45, 50, 60],
})

df['team_avg'] = df.groupby('team')['score'].agg('mean')
print(df['team_avg'].tolist())

fixed = df.assign(team_avg=df.groupby('team')['score'].transform('mean').round(2))
print(fixed['team_avg'].tolist())
```
A. `[nan, nan, nan, nan, nan]` then `[90.0, 90.0, 51.67, 51.67, 51.67]` — `.agg('mean')` collapses each group down to one row per *team*, returning a 2-row Series indexed by `'Red'`/`'Blue'`, not one row per original row. Assigning that straight into `df['team_avg']` aligns by **index**, and `df`'s index is the integers `0`-`4`, which share nothing with `'Red'`/`'Blue'` — so every row lands `NaN`. `.transform('mean')`, by contrast, is built to return a result the same length and index as the original group, broadcasting each team's mean back onto every one of that team's rows: Red's two rows both get `90.0` (`(88+92)/2`), Blue's three rows all get `51.67` (`(45+50+60)/3`, rounded)
B. Raises `ValueError` then `[90.0, 90.0, 51.67, 51.67, 51.67]` — wrongly assumes assigning a shorter, differently-indexed Series into an existing column immediately raises, when pandas actually attempts the assignment via index alignment and only produces `NaN` for every row that doesn't line up, not an error
C. `[90.0, 90.0, 51.67, 51.67, 51.67]` then `[90.0, 90.0, 51.67, 51.67, 51.67]` — wrongly assumes `.agg('mean')`'s per-team result is silently broadcast back onto every row of that team, as if `.agg()` and `.transform()` always returned identically shaped output
D. `[nan, nan, nan, nan, nan]` then `[nan, nan, nan, nan, nan]` — correctly spots the first bug but wrongly assumes `.transform()` has the exact same index-alignment problem as `.agg()`, when `.transform()` exists specifically to avoid it by always matching the original frame's shape and index

## Q3. Building on Day 46-48's player/score scenarios, Grace's match log has inconsistent name casing across weeks, so she normalizes names before pivoting scores by exact match date. What does this print? (Roadmap #40, #17, #18, #19)

```python
import pandas as pd

log = pd.DataFrame({
    'player': ['Alice', 'alice', 'Bob', 'BOB', 'Carol'],
    'match_date': ['2026-10-01', '2026-10-08', '2026-10-01', '2026-10-08', '2026-10-01'],
    'points': [10, 14, 5, 7, 12],
})

log['player_norm'] = log['player'].str.lower()
log['match_date'] = pd.to_datetime(log['match_date'])

pivot = pd.pivot_table(
    log, index='player_norm', columns='match_date', values='points',
    aggfunc='sum', fill_value=0,
)
print(pivot.loc['alice'].tolist())
print(pivot.loc['bob'].tolist())
print(log['match_date'].dt.day_name().unique().tolist())
```
A. `[10, 14]` then `[5, 7]` then `['Thursday']` — `.str.lower()` normalizes `'Alice'`/`'alice'` and `'Bob'`/`'BOB'` down to the same `player_norm` key before pivoting, so each player's two weeks of points land in one pivoted row instead of being split across case-sensitive duplicates: `alice` gets `[10, 14]`, `bob` gets `[5, 7]`. Both `2026-10-01` and `2026-10-08` fall on a Thursday, which `.dt.day_name()` reports — and since every row shares one of those two dates, the unique set of weekday names is just `['Thursday']`
B. `KeyError` — wrongly assumes `pivot_table`'s `index` argument must reference the *original* `player` column, as if a derived column like `player_norm` created earlier in the same script couldn't be used as a pivot key
C. `[10, 0]` then `[0, 7]` then `['Thursday']` — wrongly assumes the case-mismatched rows (`'alice'`, `'BOB'`) get dropped or zero-filled as if they'd never been normalized, rather than `.str.lower()` actually having merged them under one shared key before the pivot ran
D. `[10, 14]` then `[5, 7]` then `['Thursday', 'Wednesday']` — gets the pivot right but wrongly assumes `'2026-10-01'` and `'2026-10-08'` (exactly 7 days apart) land on different weekdays, when any two dates a week apart always fall on the same weekday

## Q4. Grace tries to turn each team's raw scores into a percentage of that team's total in one division, hits a shape error, then fixes it. What does this print? (Roadmap #40, #3, #4, #33)

```python
import numpy as np

scores = np.array([
    [88, 92, 79],
    [45, 50, 60],
])

team_totals = scores.sum(axis=1)
print(team_totals.tolist())

try:
    normalized = scores / team_totals
    print(normalized.tolist())
except Exception as e:
    print(type(e).__name__)

fixed = scores / team_totals[:, np.newaxis]
print(np.round(fixed, 2).tolist())
```
A. `[259, 155]` then `ValueError` then `[[0.34, 0.36, 0.31], [0.29, 0.32, 0.39]]` — `scores.sum(axis=1)` collapses each row (team) across its columns, giving one total per team: `[259, 155]`. Dividing the `(2, 3)` array by that `(2,)` array tries to broadcast by aligning *trailing* dimensions — `3` against `2` — which don't match and don't satisfy broadcasting's "equal or 1" rule, so it raises `ValueError`. Reshaping `team_totals` to `(2, 1)` with `[:, np.newaxis]` gives broadcasting a dimension of size `1` to stretch across the 3 columns correctly, dividing each row by *its own* team's total
B. `[259, 155]` then `[[0.34, 0.36, 0.31], [0.29, 0.32, 0.39]]` then same again — wrongly assumes NumPy broadcasting is smart enough to match a `(2,)` array against a `(2, 3)` array row-by-row automatically, without reshaping, when broadcasting only aligns dimensions from the *trailing* end
C. `[345, 155]` then `ValueError` then `[[0.26, 0.27, 0.23], [0.29, 0.32, 0.39]]` — wrongly computes the first row's total as `345` (as if `axis=1` had summed down a column instead of across a row), when `axis=1` reduces along each row, giving Alice's team `88+92+79=259`, not `345`
D. `[259, 155]` then `TypeError` then `[[0.34, 0.36, 0.31], [0.29, 0.32, 0.39]]` — gets the shapes and final values right but names the wrong exception; a genuine shape mismatch in an elementwise NumPy operation raises `ValueError`, not `TypeError`

## Q5. Contrasting with Day 48's chained-assignment gotcha, Grace keeps each player's most recent match and bumps their points by one point, assigning straight into a plain variable rather than any chained expression. What does this print? (Roadmap #40, #31, #39)

```python
import pandas as pd

log = pd.DataFrame({
    'player': ['Alice', 'Bob', 'Alice', 'Carol', 'Bob'],
    'points': [10, 5, 14, 12, 7],
})

latest = log.drop_duplicates(subset='player', keep='last')
print(latest['points'].tolist())

latest['points'] = latest['points'] + 1
print(latest['points'].tolist())
print(log['points'].tolist())
```
A. `[10, 5, 12]` then `[11, 6, 13]` then `[10, 5, 14, 12, 7]` — wrongly uses `keep='last'`'s behavior as if it were `keep='first'`; `keep='last'` retains each player's *last* occurrence, not their first, so Alice's kept row should hold her second entry (`14`), not her first (`10`)
B. `[14, 12, 7]` then `[15, 13, 8]` then `[10, 5, 14, 12, 7]` — `drop_duplicates(subset='player', keep='last')` keeps each player's most recent row: Alice's second entry (`14`), Carol's only entry (`12`), Bob's second entry (`7`). `latest['points'] = latest['points'] + 1` is a plain, single-bracket assignment of a whole column directly onto the named variable `latest` itself — unlike Day 48's `df[mask][col] = val` pattern, there's no intermediate throwaway object here to raise `ChainedAssignmentError` over; it's an ordinary write that lands on `latest`, bumping its scores to `[15, 13, 8]`. `latest` was already its own independent object the moment `drop_duplicates()` created it, so none of this ever touches `log`, which stays `[10, 5, 14, 12, 7]` regardless
C. `[14, 12, 7]` then `ChainedAssignmentError` then `[14, 12, 7]` — wrongly assumes *any* indexing-then-assigning pattern involving a filtered/deduplicated DataFrame triggers `ChainedAssignmentError`, when that warning is specifically about chaining two indexing operations (like `df[mask][col] = val`) in one expression — a single `latest['points'] = ...` on an already-named variable isn't chained indexing at all
D. `[14, 12, 7]` then `[15, 13, 8]` then `[11, 6, 15, 13, 8]` — gets `latest` right but wrongly assumes the write also somehow propagates back into `log`'s matching rows, as if `latest` still shared memory with `log` after `drop_duplicates()` ran, rather than being a fully independent object
