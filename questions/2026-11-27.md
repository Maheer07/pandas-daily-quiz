## Q1. Grace builds a small `orders` table from two partial per-shift Series, then looks up the same value two different ways. What does this print? (Roadmap #47, #48)

```python
import pandas as pd

morning = pd.Series([12, 9, 15], index=['b', 'a', 'c'])
afternoon = pd.Series([3, 7], index=['c', 'a'])
orders = pd.DataFrame({'morning': morning, 'afternoon': afternoon})

print(orders.iloc[0]['morning'])
print(orders.loc['b', 'morning'])
```
A. `9.0` then `12` — A dict of Series aligns onto the **sorted union** of all labels (`a, b, c`), not `morning`'s original `b, a, c` order — so row position `0` is label `'a'`, not `'b'`. `orders.iloc[0]` first builds a one-row `Series` spanning *both* columns; since `afternoon` is already `float64` (it's missing a value for `'b'`), that row-wide `Series` upcasts entirely to `float64`, so `'morning'`'s own value prints as `9.0`. `orders.loc['b', 'morning']` instead pulls a single scalar straight out of the still-`int64` `'morning'` column, with no row-wide upcast involved, so it prints the plain int `12`.
B. `12.0` then `12` — wrongly assumes position `0` lines up with `'b'`, the first key `morning` was originally given, as if dict-of-Series construction preserved any one input's order; the row index is built from the sorted union of labels, so position `0` is alphabetically-first `'a'`, not `'b'`.
C. `9.0` then `12.0` — correctly finds which row/label each lookup lands on but wrongly assumes `.loc['b', 'morning']` also upcasts to `float64`; selecting directly from a single column that itself has no missing values returns that column's own `int64` scalar, with no other column's dtype bleeding in.
D. `9` then `12` — correctly finds both values but wrongly keeps `orders.iloc[0]['morning']` displaying as a plain int; selecting a whole row first returns a `Series` spanning every column, and because `afternoon` is `float64`, the entire returned row — including the value that came from `morning` — upcasts to `float64` and prints with a decimal point.

## Q2. Building on Q1's `orders` table, Grace flags busy shifts with `np.where` and checks how the missing afternoon shift gets aggregated. What does this print? (Roadmap #45, #46)

```python
import numpy as np

flag = np.where(orders['afternoon'] > 5, 'busy', 'slow')
print(flag.tolist())

print(orders['afternoon'].sum(), orders['afternoon'].mean())
print(orders['afternoon'].to_numpy().sum())
```
A. `['busy', 'slow', 'slow']` then `10.0 5.0` then `nan` — `orders['afternoon']` is `[7.0, NaN, 3.0]` in row order `a, b, c`. A comparison against `NaN` (`NaN > 5`) is always `False`, never an error, so the missing `'b'` shift gets `np.where`'s `False`-branch value, `'slow'`, same as `'c'`. `Series.sum()`/`.mean()` default to `skipna=True`: they total just the two real values (`7+3=10.0`) and divide by a count of `2` (`5.0`) — but once converted `.to_numpy()`, the bare array reverts to NumPy's `nan`-propagating default, so the identical data sums to `nan`.
B. `TypeError` then nothing printed — wrongly assumes comparing `NaN > 5` raises, as if a missing value couldn't be compared to a number; comparisons involving `NaN` are always valid and simply evaluate to `False`.
C. `['busy', 'slow', 'slow']` then `3.333333333333333 3.333333333333333` then `nan` — gets the flags right but wrongly divides the sum by the full row count (`3`) instead of the count of non-missing values (`2`), as if `skipna=True` only trimmed the numerator; pandas skips the missing entry for both the sum and the implicit count `.mean()` divides by.
D. `['busy', 'slow', 'slow']` then `10.0 5.0` then `10.0` — wrongly assumes `.to_numpy()` carries the Series's skip-`nan` convention into the resulting array; once the data is a plain `ndarray`, NumPy's own propagating default takes over and the same values sum to `nan`, not `10.0`.

## Q3. Still on `orders`, Grace enlarges it by one row through `.loc`, then builds a second, unrelated frame using a broadcast scalar. What does this print? (Roadmap #48, #47)

```python
orders.loc['d', 'morning'] = 20
print(orders.dtypes.tolist())
print(orders['morning'].tolist())

fresh = pd.DataFrame({'morning': [5, 6], 'tip': 2})
print(fresh.dtypes.tolist())
```
A. `[dtype('float64'), dtype('float64')]` then `[9.0, 12.0, 15.0, 20.0]` then `[dtype('int64'), dtype('int64')]` — Enlarging through `.loc` for a brand-new label reindexes *every* column to make room for the new row, and since an `int64` column can't represent that row's `NaN` placeholder, pandas upcasts the whole `'morning'` column to `float64` as part of the reindex itself — even though you then immediately filled every cell, including `'d'`'s, with a real number. That upcast comes from the reindexing step, not from anything actually missing in the final result. Building `fresh` from a dict is unrelated: broadcasting the bare scalar `2` down `'tip'` never introduces an intermediate `NaN` anywhere, so neither column there needs to upcast, and both stay `int64`.
B. `[dtype('int64'), dtype('float64')]` then `[9, 12, 15, 20]` then `[dtype('int64'), dtype('int64')]` — wrongly assumes only the *unmentioned* column (`afternoon`) upcasts on `.loc` enlargement, as if explicitly supplying a value for `'morning'` shields it from the same reindex; the new row is introduced as `NaN` across every column before your value gets written in, so `'morning'` upcasts right along with `afternoon`.
C. `[dtype('float64'), dtype('float64')]` then `[9.0, 12.0, 15.0, 20.0]` then `[dtype('float64'), dtype('int64')]` — correctly traces the `.loc` enlargement but wrongly assumes broadcasting a scalar in a dict also upcasts a neighboring list-based column; `fresh`'s `'morning'` list has no missing values, and broadcasting `2` down `'tip'` changes nothing about any other column's dtype.
D. `[dtype('float64'), dtype('float64')]` then `[9, 12, 15, 20]` then `[dtype('int64'), dtype('int64')]` — gets both dtype lines right but wrongly prints `'morning'`'s values without a decimal point, as if the column only looked `float64` without actually formatting like one; a genuinely `float64` column always prints every value with a `.0`, including whole numbers like `20.0`.

## Q4. Returning to Q1's original `orders` (before Q3's enlargement), Grace filters it with a boolean Series mask whose labels are shuffled, then tries the same trick with a mask covering only two of the three labels. What does this print? (Roadmap #46, #48)

```python
import pandas as pd

busy_mask = pd.Series([False, True, True], index=['b', 'c', 'a'])
print(orders.loc[busy_mask])

partial_mask = pd.Series([True, False], index=['a', 'c'])
try:
    print(orders.loc[partial_mask])
except Exception as e:
    print(type(e).__name__)
```
A.
```
   morning  afternoon
a        9        7.0
c       15        3.0
```
then `IndexingError` — A boolean **Series** indexer passed to `.loc` is matched by *label*, not position (same rule Day 57 Q5 established for plain Series selection): `busy_mask` covers exactly `orders`'s three labels, just reordered, so pandas aligns it correctly and returns the rows flagged `True` (`'c'` and `'a'`) in `orders`'s own row order. `partial_mask` covers only two of the three labels, so pandas refuses to guess what the missing `'b'` flag should be and raises `IndexingError`, rather than silently dropping or defaulting it.
B.
```
   morning  afternoon
b       12        NaN
c       15        3.0
```
then
```
   morning  afternoon
a        9        7.0
```
(no error) — wrongly matches each mask by *position* instead of by label, as if `busy_mask`'s flags lined up with `orders`'s rows in whatever order each happens to be stored — `False` with `'a'`, `True` with `'b'`, `True` with `'c'` — and then does the same for `partial_mask` against `orders`'s first two rows; a boolean Series indexer is aligned by its own labels, never by position, and a label-set mismatch raises instead of pairing up positionally.
C.
```
   morning  afternoon
a        9        7.0
c       15        3.0
```
then
```
   morning  afternoon
a        9        7.0
```
(no error) — gets the first selection right but wrongly assumes a partially-overlapping mask just uses whichever labels happen to match (here, only `'a'`) and silently ignores the rest; `.loc` with a boolean Series indexer requires the label sets to match *exactly*, and any mismatch — missing or extra labels — raises `IndexingError` rather than filtering down to the overlap.
D. `IndexingError` then `IndexingError` — wrongly assumes `busy_mask` also fails just for being out of `orders`'s original row order; alignment only cares that the *set* of labels matches exactly, and `busy_mask` has precisely `orders`'s three labels, merely shuffled, which `.loc` aligns without complaint.

## Q5. To close out the week, Grace adds a duplicate-labeled bonus Series to `orders['morning']`, tries folding that same Series into a new `DataFrame`, then flags the result with `np.where`. What does this print? (Roadmap #46, #47, #45, #48)

```python
import numpy as np

bonus = pd.Series([1, 1, 5], index=['a', 'a', 'c'])
boosted = orders['morning'] + bonus
print(boosted.tolist())

try:
    combo = pd.DataFrame({'morning': orders['morning'], 'bonus': bonus})
except ValueError as e:
    print(type(e).__name__)

flagged = np.where(boosted > 15, 'high', 'low')
print(boosted.iloc[-1], flagged[-1])
```
A. `[10.0, 10.0, nan, 20.0]` then `ValueError` then `20.0 high` — Series arithmetic tolerates `bonus`'s duplicate `'a'` label just fine: `orders['morning']`'s single `'a'` value (`9`) pairs against *both* of `bonus`'s `'a'` rows (`9+1=10.0` twice), the missing `'b'` label becomes `NaN`, and `'c'` becomes `15+5=20.0` — all sorted (`a, a, b, c`) because a duplicate label forces that fallback. Folding the same duplicate-labeled `bonus` straight into a `DataFrame` is the stricter operation: it must reindex onto one shared axis and refuses a duplicate-labeled input outright, raising `ValueError`. `boosted.iloc[-1]` is ordinary negative positional indexing — the last row in `boosted`'s own order, label `'c'`, value `20.0` — and since `20 > 15` is `True`, `np.where`'s last flag is `'high'`.
B. `[10.0, nan, 20.0]` then `ValueError` then `20.0 high` — wrongly assumes the duplicate `'a'` label gets collapsed into one entry during the addition, as if alignment deduplicated a repeated label first; alignment instead pairs the single `orders['morning']['a']` value against *each* of `bonus`'s two `'a'` rows separately, keeping both in the result.
C. `[10.0, 10.0, nan, 20.0]` then `ValueError` then `nan low` — correctly traces the addition and the `DataFrame` rejection but wrongly assumes `.iloc[-1]` lands on the `NaN` `'b'` row; `.iloc[-1]` always means the last position in `boosted` as it's actually ordered (`a, a, b, c`), which is `'c'` (`20.0`), not `'b'`.
D. `[10.0, 10.0, nan, 20.0]` then (no error, `combo` builds fine) then `20.0 high` — wrongly assumes folding a duplicate-labeled Series into a `DataFrame` is just as tolerant as plain Series arithmetic; `DataFrame` construction from a dict of Series needs one well-defined row index to align everything onto, and explicitly rejects a duplicate-labeled input with `ValueError`.

## Answer key

1. **A** — Dict-of-Series construction sorts the union of labels (`a, b, c`), so `.iloc[0]` is `'a'`, not `morning`'s original first key `'b'`. Selecting a whole row upcasts to `float64` because `afternoon` is `float64`; selecting a single still-`int64` column scalar via `.loc` does not. B wrongly assumes position `0` matches the original input order. C wrongly assumes `.loc`'s column scalar also upcasts. D wrongly keeps the upcast row's value displaying as a plain int.
2. **A** — `NaN > 5` is `False`, never an error, so the missing shift gets `np.where`'s `False` branch. `Series.sum()`/`.mean()` default to `skipna=True` (total and count both exclude the `NaN`); `.to_numpy()` strips that and reverts to NumPy's `nan`-propagating default. B wrongly assumes comparing `NaN` raises. C wrongly uses the full row count as `.mean()`'s denominator. D wrongly assumes `.to_numpy()` keeps the skip-`nan` behavior.
3. **A** — `.loc` enlargement reindexes every column for the new row, upcasting any `int64` column to `float64` as part of that reindex — even the column you explicitly set. Scalar broadcasting in dict construction introduces no `NaN`, so nothing upcasts. B wrongly assumes only the unmentioned column upcasts. C wrongly assumes scalar broadcasting also upcasts a neighboring column. D gets the dtypes right but wrongly drops the decimal formatting of a genuinely `float64` column.
4. **A** — A boolean Series indexer passed to `.loc` aligns by label, not position; a reordered-but-complete mask works, a mask missing a label raises `IndexingError`. B wrongly aligns by position. C wrongly assumes a partial-label mismatch silently uses the overlap instead of raising. D wrongly assumes mere reordering (without a label-set mismatch) also raises.
5. **A** — Series `+` tolerates a duplicate-labeled operand, pairing the single `'a'` value against each `bonus` row labeled `'a'`; building a `DataFrame` from a dict of Series rejects a duplicate-labeled input with `ValueError`; `.iloc[-1]` is the last row in `boosted`'s actual order (`'c'`, `20.0`), which is `> 15`. B wrongly collapses the duplicate label in the addition. C wrongly points `.iloc[-1]` at the `NaN` row. D wrongly assumes `DataFrame` construction tolerates the duplicate label too.
