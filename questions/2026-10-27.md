Topics: `groupby().transform()` vs `.agg()` vs `.apply()` — when each is required (Roadmap #30)

## Q1. Building on the recurring `df6`, Grace wants to add each person's team average as a new column, aligned row-by-row. What does this print? (Roadmap #30, #13)

```python
import pandas as pd

data6 = {'name': ['Alice', 'Bob', 'Carol', 'Dave', 'Eve', 'Frank'],
         'team': ['Red', 'Blue', 'Red', 'Blue', 'Red', 'Blue'],
         'region': ['North', 'South', 'North', 'North', 'South', 'South'],
         'score': [88, 45, 92, 60, 75, 50]}
df6 = pd.DataFrame(data6, index=[100, 101, 102, 103, 104, 105])

df6['team_mean'] = df6.groupby('team')['score'].transform('mean')
print(df6[['name', 'team', 'score', 'team_mean']])
```
A. All 6 original rows print in their original order, each with its own team's mean score sitting alongside it: Alice/Carol/Eve (Red) each show `85.0`, Bob/Dave/Frank (Blue) each show `51.666667` — `transform()` computes one aggregate per group but broadcasts that same value back onto every row belonging to the group, so the result stays exactly the same shape and order as `df6`.
B. Raises a `ValueError` about mismatched lengths — wrongly treats `transform()` as if it behaves like `agg()`, collapsing to one row per team (2 rows) that couldn't be assigned into a 6-row column.
C. The same 6 rows print, but the values are swapped: Red's rows show `51.666667` and Blue's rows show `85.0` — mixes up which team's mean belongs to which group.
D. Raises a `TypeError`, assuming `transform()` only accepts a function object (like `lambda x: x.mean()`) and rejects the string shorthand `'mean'` that `agg()` accepts.

## Q2. Contrast with Q1: Grace checks what index each result actually carries. What does this print? (Roadmap #30, #15)

```python
mt = df6.groupby('team')['score'].transform('mean')
ma = df6.groupby('team')['score'].agg('mean')
print(mt.index.tolist())
print(ma.index.tolist())
```
A. `[100, 101, 102, 103, 104, 105]` then `['Blue', 'Red']` — `transform()`'s output is one value per *original row*, so it keeps `df6`'s own index untouched; `agg()`'s output is one value per *group*, indexed by the distinct `team` labels, which `groupby()` sorts alphabetically by default (`'Blue'` before `'Red'`) regardless of which team appeared first in the data.
B. `['Blue', 'Red']` then `[100, 101, 102, 103, 104, 105]` — swaps the two: wrongly assumes `transform()` collapses to group labels like `agg()` does, and that `agg()` instead keeps every original row.
C. `[100, 101, 102, 103, 104, 105]` then `['Red', 'Blue']` — gets `transform()` right, but wrongly assumes `groupby()`'s default ordering follows first-appearance order in the data (`'Red'` appears in row 100, before `'Blue'`) rather than its actual default of sorting group keys alphabetically.
D. Raises an `AttributeError` on the second `print()`, wrongly assuming only `transform()`'s result is a `Series` with an `.index`, while `agg()` on a single column returns a plain NumPy array instead.

## Q3. Grace wants each team's min and max score together. What does this print? (Roadmap #30, #19)

```python
def minmax(g):
    return pd.Series({'min': g.min(), 'max': g.max()})

applied = df6.groupby('team')['score'].apply(minmax)
print(applied.loc[('Red', 'max')])

try:
    df6.groupby('team')['score'].agg(minmax)
except Exception as e:
    print(type(e).__name__)
```
A. `92` then `ValueError` — `apply()` lets the per-group function return a whole `Series`, so pandas stacks those into a result indexed by `(team, label)` pairs, and `applied.loc[('Red', 'max')]` correctly finds Red's max score of `92`; `agg()`, by contrast, requires each group's result to reduce to a single scalar, so handing it a function that returns a multi-value `Series` raises `ValueError`.
B. `92` then nothing is printed (no exception) — correctly gets the `apply()` result, but wrongly assumes `agg()` can also accept a function that returns a `Series`, treating it the same as `apply()`.
C. `60` then `ValueError` — correctly identifies that `agg()` raises, but misreads the `MultiIndex` lookup, grabbing Blue's max (`60`) instead of Red's (`92`).
D. Raises a `KeyError` on the first `print()`, wrongly assuming `apply()`'s stacked result is indexed only by `team`, with `'min'`/`'max'` becoming columns rather than a second index level.

## Q4. Building on Day 34's boolean-mask pattern, Grace flags each person as above or below their *own team's* average — not the dataset's overall average. What does this print? (Roadmap #30, #28)

```python
df6['rel_to_team'] = df6['score'] - df6.groupby('team')['score'].transform('mean')
below_avg = df6.loc[df6['rel_to_team'] < 0, 'name'].tolist()
print(below_avg)
```
A. `['Bob', 'Eve', 'Frank']` — `transform('mean')` broadcasts each team's own mean back onto every row of that team (Red: `85.0`, Blue: `51.666667`), aligned to `df6`'s original index, so the subtraction happens cleanly row-by-row; Bob (`45−51.67`), Eve (`75−85`), and Frank (`50−51.67`) all come out negative.
B. `[]` — swaps `transform` for `agg`, which returns only 2 rows indexed by team label (`'Blue'`/`'Red'`); subtracting that from `df6['score']` (indexed `100`–`105`) aligns by index, and since none of those labels overlap, every result is `NaN`, so no row satisfies `< 0`.
C. `['Alice', 'Carol', 'Dave']` — picks the *above*-average rows instead of the below-average ones, as if the comparison were flipped to `> 0`.
D. Raises a `ValueError`, wrongly assuming a `groupby().transform()` result can't be subtracted directly from the original column without first calling `.to_numpy()` to strip away index alignment — but that alignment is exactly why `transform()`'s output can be used directly, since it already shares `df6`'s index.

## Q5. Grace wants each person's score as a percentage of their *own team's* total. Which line is correct — one whose result lines up with `df6`'s existing rows so it could be assigned straight back as a new column? (Roadmap #30, #26)

A. `df6['score'] / df6.groupby('team')['score'].transform('sum') * 100` — `transform('sum')` broadcasts each team's total (Red: `255`, Blue: `155`) back onto every row of that team before the division runs elementwise, giving a flat, same-shape result aligned to `df6`'s own index (e.g. Alice ≈ `34.51`, Bob ≈ `29.03`).
B. `df6['score'] / df6.groupby('team')['score'].sum() * 100` — drops `transform`, so the denominator collapses to 2 rows indexed by team label instead of 6 rows indexed like `df6`; dividing misaligns on the index and produces `NaN` for every original row.
C. `df6.groupby('team')['score'].apply(lambda g: g / g.sum() * 100)` — reaches the exact same percentage values, but returns them indexed by `(team, original_index)` pairs rather than `df6`'s plain index, so the shape doesn't match `df6`'s rows and it can't be dropped straight back in as a column the way `transform()`'s result can.
D. `df6['score'] / df6['score'].sum() * 100` — divides by the grand total of *all* scores (`410`) instead of each row's own team total, giving every row's share of the whole dataset rather than of its team.

## Answer key

1. **A** — `transform()` computes one aggregate per group (Red: `85.0`, Blue: `51.666667`) but hands back a result broadcast to every row of that group, so the output keeps `df6`'s original 6-row shape and order exactly, letting it be assigned straight into a new column. B wrongly imports `agg()`'s collapsing behavior into `transform()`, which would indeed break on reassignment — but that's not what `transform()` does. C swaps the two teams' means. D invents a restriction that doesn't exist — `transform()` happily accepts the same string shorthands (`'mean'`, `'sum'`, etc.) that `agg()` does.
2. **A** — `transform()`'s result has exactly one entry per original row, so it inherits `df6`'s own index untouched (`[100, ..., 105]`). `agg()`'s result has one entry per distinct group, indexed by the team labels themselves; by default `groupby()` sorts those group keys (alphabetically for strings), so `'Blue'` sorts before `'Red'` even though a Red row appears first in `df6`. B swaps which operation keeps which index. C correctly identifies `transform()`'s index but wrongly assumes `agg()` preserves first-appearance order instead of applying its default sort. D is wrong — both results are plain `Series` objects with a normal `.index`.
3. **A** — `apply()` lets the per-group callable return an arbitrary object, including a multi-value `Series`; pandas concatenates those per-group `Series` into one result indexed by `(team, label)` tuples, so `applied.loc[('Red', 'max')]` is `92`. `agg()` is stricter: it expects the function to reduce each group to a single scalar, and handing it a function that returns a 2-value `Series` triggers pandas' own `ValueError` ("Must produce aggregated value"). B wrongly assumes `agg()` tolerates a non-scalar return the same way `apply()` does. C mixes up the `MultiIndex` lookup, grabbing Blue's max instead of Red's. D invents a structural difference (columns vs. index levels) that doesn't match how `apply()` actually stacks a dict-like `Series` result.
4. **A** — `transform('mean')` gives Red rows `85.0` and Blue rows `51.666667`, each aligned to `df6`'s own index, so `df6['score'] - ...` subtracts cleanly row-by-row; the negative results belong to Bob (`45 − 51.67`), Eve (`75 − 85`), and Frank (`50 − 51.67`). B shows exactly why `transform` (not `agg`) is required here: `agg()`'s 2-row, team-labeled result doesn't share any index values with `df6`'s row-labeled index, so the subtraction aligns on the union of both indexes and produces `NaN` everywhere relevant, leaving no row `< 0`. C just flips the sign of the comparison people might make by mistake. D is wrong — `transform()`'s defining feature is that its output *is* already aligned to the original index, so it subtracts directly with no extra conversion needed.
5. **A** — broadcasting each team's total back onto its own rows via `transform('sum')` before dividing keeps the result the same shape and index as `df6`, so Alice's score (`88`) over Red's total (`255`) gives `≈34.51%`, etc. B removes `transform`, so the denominator is a 2-row, team-indexed `Series`; dividing `df6['score']` (row-indexed) by that produces `NaN` across the board due to index misalignment, the same failure pattern as Q4's distractor. C is a trap: the *numbers* `apply()` produces here are identical to A's, but the result comes back with a `(team, original_index)` `MultiIndex` rather than `df6`'s own flat index, so it can't be assigned straight back as a column the way the question requires — it needs reshaping first. D silently swaps "percent of team total" for "percent of grand total," giving a different (and here, smaller) set of percentages for every row.
