Topics: Performance: vectorization vs `.apply()` vs `.iterrows()` (Roadmap #25)

## Q1. Spot the bug: building on the recurring `df6`, Grace tries to double everyone's score in place with a loop. What does this print? (Roadmap #25)

```python
import pandas as pd

data6 = {'name': ['Alice', 'Bob', 'Carol', 'Dave', 'Eve', 'Frank'],
         'team': ['Red', 'Blue', 'Red', 'Blue', 'Red', 'Blue'],
         'region': ['North', 'South', 'North', 'North', 'South', 'South'],
         'score': [88, 45, 92, 60, 75, 50]}
df6 = pd.DataFrame(data6, index=[100, 101, 102, 103, 104, 105])

for idx, row in df6.iterrows():
    row['score'] = row['score'] * 2

print(df6.loc[100, 'score'])
```
A. `176` — each `row` yielded by `.iterrows()` is a live view into `df6`'s own memory, so writing into it updates `df6` in place
B. `88` — `.iterrows()` builds a brand-new Series copy of each row on the fly, so assigning into `row` never touches `df6` at all; the loop silently does nothing useful
C. Raises a `SettingWithCopyWarning`, then leaves the value at `88`, because pandas detects the write is happening on a copy and blocks it
D. Raises a `ValueError: assignment destination is read-only`, the same error Day 29 Q4 hit when writing into a `.to_numpy(copy=False)` array

## Q2. Building on Q1's loop, Grace inspects what a row actually looks like mid-iteration. What does this print? (Roadmap #25)

```python
for idx, row in df6.iterrows():
    print(row.dtype, type(row['score']))
    break
```
A. `int64 <class 'numpy.int64'>` — `.iterrows()` keeps each column's own dtype intact within the row Series it builds
B. `object <class 'int'>` — to combine `score`'s number with `name`/`team`/`region`'s strings into one row-shaped Series, pandas has to upcast the whole row to a single common dtype; since no numeric dtype can also hold strings, it falls back to `object`, and the integer ends up stored as a plain Python `int` rather than a NumPy scalar
C. `object <class 'numpy.int64'>` — the row becomes `object`-dtype overall, but each individual value still keeps its exact original NumPy scalar type
D. Raises a `TypeError`, because `.iterrows()` refuses to build a row Series out of columns with incompatible dtypes

## Q3. Building on Q2's dtype trap, Grace isolates just the numeric columns, hoping that avoids it. She adds a bonus-percentage column and loops again. What does this print? (Roadmap #25)

```python
df6['bonus_pct'] = [0.1, 0.2, 0.15, 0.05, 0.25, 0.1]

for idx, row in df6[['score', 'bonus_pct']].iterrows():
    print(type(row['score']), row['score'])
    break
```
A. `<class 'numpy.int64'> 88` — `.iterrows()` preserves each column's own dtype even when the row mixes an `int64` column with a `float64` one
B. `<class 'numpy.float64'> 88.0` — building one row-shaped Series out of an `int64` column and a `float64` column still forces pandas to pick a single common dtype for the whole row, and the more general `float64` wins, so the integer score silently becomes a float
C. Raises a `TypeError`, because an `int64` column and a `float64` column can't be combined into one Series without an explicit `.astype()` call first
D. `<class 'int'> 88` — same `object`-dtype fallback as Q2, since any row mixing two different dtypes always collapses all the way to `object`

## Q4. Grace rewrites Q3's loop with `.itertuples()` instead, hoping to dodge the dtype surprise. What does this print? (Roadmap #25)

```python
for t in df6[['score', 'bonus_pct']].itertuples():
    print(type(t.score), t.score)
    break
```
A. `<class 'int'> 88` — `.itertuples()` builds each field straight from its own column's array rather than assembling a single row-shaped Series first, so `score` keeps its integer value instead of being upcast to match `bonus_pct`'s `float64`; this is exactly why `.itertuples()` is the documented fix for Q3's row-wide dtype trap
B. `<class 'numpy.float64'> 88.0` — same upcasting as `.iterrows()`, since `.itertuples()` builds its namedtuples the same row-at-a-time way under the hood
C. Raises an `AttributeError`, because `.itertuples()` only exposes fields by position (`t[0]`, `t[1]`, ...), not by name, unless `name=None` is passed
D. `<class 'numpy.int64'> 88` — `.itertuples()` preserves the exact NumPy scalar type of each column, so `score` keeps its original `numpy.int64` wrapper rather than becoming a plain Python `int`

## Q5. Grace wants a `bonus` column equal to `score * bonus_pct`. Which option gives the correct values *and* avoids the per-row Python-level cost that made Q1-Q4 risky? (Roadmap #25)

A. `df6['bonus'] = df6.apply(lambda row: row['score'] * row['bonus_pct'], axis=1)` — gives correct values, but `apply(axis=1)` still builds one row-shaped Series per call internally, so it carries the same per-row Python-level overhead that made `.iterrows()` a trap in Q1-Q3
B. `df6['bonus'] = df6['score'] * df6['bonus_pct']` — a single vectorized multiplication across the whole columns at once, handled by NumPy/pandas' compiled loop with no per-row Python-level work at all
C. `df6['bonus'] = [s * b for s, b in zip(df6['score'], df6['bonus_pct'])]` — gives the same correct numbers as B, but computes them with an explicit Python-level `for` loop (hidden inside the list comprehension) over each pair of values, instead of letting pandas multiply the whole columns at once
D. `df6['bonus'] = df6[['score', 'bonus_pct']].sum(axis=1)` — looks just as vectorized and fast as B, but `.sum(axis=1)` *adds* the two columns row-wise instead of multiplying them, so every resulting value is wrong

## Answer key

1. **B** — `.iterrows()` is documented to hand back a freshly constructed Series copy for each row, not a view into `df6`'s underlying memory, so mutating the local `row` variable inside the loop body has no effect on `df6` itself; after the loop, `df6.loc[100, 'score']` is still `88`. A wrongly assumes `.iterrows()` gives live, writable access back into the DataFrame — it never does. C invents a warning that doesn't fire here; `SettingWithCopyWarning` is about chained-indexing writes on a DataFrame slice, not about plain assignment into an already-copied Series. D confuses this with Day 29 Q4's `.to_numpy()` read-only buffer — a Series from `.iterrows()` is fully writable, it just isn't connected to `df6` at all, so no error is raised; the write simply goes nowhere.
2. **B** — `.iterrows()` builds each row by assembling all of that row's values (one from every column) into a single new Series, which means every value in the row has to share one common dtype. Since the row mixes `score`'s numbers with `name`/`team`/`region`'s strings, there's no numeric dtype general enough to hold both, so the row's dtype falls back to `object`; within that `object` array, `score`'s value comes back as a plain Python `int` rather than the `numpy.int64` the `score` column itself stores. A is wrong — dtype is explicitly *not* preserved per-column within an `.iterrows()` row; that's the trap this question targets. C is wrong — the individual value's type changes too (`int`, not `numpy.int64`), it isn't just the row's overall label that becomes `object`. D is wrong — `.iterrows()` happily builds rows out of mismatched column dtypes by upcasting to `object`; it doesn't raise.
3. **B** — even restricted to just the two numeric columns, `.iterrows()` still has to combine every value in the row into one Series with one dtype; combining an `int64` column with a `float64` column upcasts the whole row to `float64` (the more general of the two), so `score`'s `88` silently becomes `88.0` and `type(row['score']))` reports `numpy.float64`. A wrongly assumes per-column dtypes survive inside an `.iterrows()` row even when both dtypes are numeric — they don't; only the row's single shared dtype survives. C is wrong — `int64` and `float64` combine without any error; no `.astype()` call is needed or involved. D wrongly extends Q2's `object`-fallback rule to this case — that fallback only happens when no common *numeric* dtype exists (e.g. with strings in the mix); two purely numeric dtypes instead upcast to the more general numeric type, `float64`, not all the way to `object`.
4. **A** — `.itertuples()` doesn't build one shared Series for the whole row the way `.iterrows()` does; instead it pulls each field straight from its own column's underlying array when constructing the namedtuple, so `score` keeps its integer value (`88`) even though `bonus_pct` in the same row is a float. That per-column (not per-row) dtype handling is exactly why the pandas docs recommend `.itertuples()` over `.iterrows()` when you need to preserve each column's own type. B wrongly imports Q3's row-upcasting behavior into `.itertuples()` — that's precisely the dtype trap `.itertuples()` avoids. C is wrong — fields are accessed by attribute name (`t.score`) by default; positional-only access is what you'd get by passing `name=None`, not the reverse. D is wrong about the exact type — the value comes back as a plain Python `int`, not a `numpy.int64` wrapper, even though the dtype (unlike in `.iterrows()`) is at least the correct numeric kind rather than upcast to float or object.
5. **B** — multiplying `df6['score'] * df6['bonus_pct']` operates on both columns as whole NumPy arrays in one compiled pass, with no Python-level iteration over individual rows or elements at all, which is both correct and the fastest of the four options. A is wrong to pick despite giving correct numbers — `.apply(axis=1)` must still invoke its lambda once per row and assemble a row-shaped Series to do it, which carries essentially the same per-row Python overhead that made `.iterrows()` a trap in Q1-Q3. C also gives correct numbers but computes them with an ordinary Python `for` loop running underneath the list comprehension, element by element, rather than letting pandas/NumPy vectorize the whole multiplication at once. D is fast and vectorized but semantically wrong — `.sum(axis=1)` adds `score` and `bonus_pct` row-wise instead of multiplying them, so none of its resulting values match the intended bonus calculation.
