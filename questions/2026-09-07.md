## Q4. Which line produces the array below?

```
array([[0, 1, 2],
       [3, 4, 5]])
```
A. `np.arange(6).reshape(2, 3)`
B. `np.arange(6).reshape(3, 2)`
C. `np.arange(6).reshape(2, 3).T`
D. `np.arange(1, 7).reshape(2, 3)`

## Q5. What does the following print?

```python
import numpy as np
arr = np.array([1, 2, 3], dtype='float32')
new_arr = arr.astype('int32')
arr[0] = 99
print(new_arr[0])
```
A. 99
B. 99.0
C. 1
D. 1.0

## Answer key

1. **A** — `np.array` fills row by row, so two inner lists of length 3 give shape `(2, 3)` with `ndim=2`. B swaps rows/cols (a common `.shape` mix-up). C wrongly assumes the array gets flattened. D has the right shape but `ndim` is the *number* of axes (2 here), not something derived from the total element count or nesting depth beyond that.
2. **B** — NumPy applies type promotion: mixing `int` and `float` values upcasts the whole array to `float64` so no precision is lost. A ignores the `3.5` entry. C is wrong because `object` dtype only kicks in for genuinely incompatible types (e.g. strings mixed with numbers), not numeric mixes. D is wrong because there's no complex/imaginary value present.
3. **B** — Assigning into an `int`-dtype array casts the value via truncation (toward zero), not rounding, and does so silently (no error). So `1.9` becomes `1`. A ignores that the array's dtype forces a cast. C incorrectly assumes rounding behavior. D is wrong because NumPy performs the unsafe cast silently by default instead of raising.
4. **A** — `np.arange(6)` gives `[0,1,2,3,4,5]`, and `.reshape(2, 3)` fills row-major into 2 rows of 3, exactly matching the target. B has rows/cols swapped, producing `[[0,1],[2,3],[4,5]]`. C transposes A's correct result into shape `(3,2)` with values `[[0,3],[1,4],[2,5]]`. D starts counting from 1 instead of 0, giving `[[1,2,3],[4,5,6]]`.
5. **C** — `.astype()` returns a brand-new array by default (a copy, not a view), so mutating `arr` afterward has no effect on `new_arr`. `new_arr[0]` was cast from the original `1.0` (float32) down to `int32`, giving `1`. A and B both wrongly assume `astype` returns a view that reflects later mutations of `arr`. D has the right "unaffected" idea but the wrong dtype — `new_arr` is `int32`, so it prints as `1`, not `1.0`.
