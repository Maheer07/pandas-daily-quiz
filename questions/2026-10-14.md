## Q1. Building on the recurring `df6`, Grace converts `team` to a `category` dtype to shrink its memory footprint. What does this print? (Roadmap #23)

```python
import pandas as pd
data6 = {'name': ['Alice', 'Bob', 'Carol', 'Dave', 'Eve', 'Frank'],
         'team': ['Red', 'Blue', 'Red', 'Blue', 'Red', 'Blue'],
         'region': ['North', 'South', 'North', 'North', 'South', 'South'],
         'score': [88, 45, 92, 60, 75, 50]}
df6 = pd.DataFrame(data6, index=[100, 101, 102, 103, 104, 105])

df6['team'] = df6['team'].astype('category')
print(df6['team'].cat.categories.tolist())
```
A. `['Red', 'Blue']` — categories keep the order the values first appeared in the column
B. `['Blue', 'Red']` — when no explicit category order is given, `astype('category')` sorts the discovered unique values
C. Raises an `AttributeError`, because the `.cat` accessor only exists after explicitly constructing a `pd.Categorical`, not after a plain `.astype('category')` call
D. `[0, 1]` — `.cat.categories` returns the underlying integer codes, not the original labels

## Q2. Building on Q1's conversion, Grace adds a category that no row actually has. What does this print? (Roadmap #23)

```python
df6['team'] = pd.Categorical(df6['team'], categories=['Red', 'Blue', 'Green'])
print(df6.groupby('team')['score'].mean())
```
A. `Red` 85.0 and `Blue` 51.666... only — `Green` has no matching rows, and modern pandas defaults `groupby()` to `observed=True`, which only aggregates over categories that actually occur in the data
B. `Red` 85.0, `Blue` 51.666..., and `Green` is also listed, with `NaN` as its mean — `groupby` on a categorical column always aggregates every category defined on the dtype, whether or not any row actually has it
C. `Red` 85.0, `Blue` 51.666..., and `Green` 0.0 — pandas treats an empty group's sum as `0`, and since `.mean()` reuses the same aggregation machinery, it also defaults empty groups to `0`
D. Raises a `ValueError`, because `Green` has no rows backing it, and `groupby` refuses to aggregate a category with no observations

## Q3. Building on Day 27's bins-and-scores theme, Grace buckets each score into a tier and filters by it. What does this print? (Roadmap #23)

```python
df6['tier'] = pd.cut(df6['score'], bins=[0, 60, 80, 100], labels=['low', 'mid', 'high'])
print(df6[df6['tier'] > 'low']['name'].tolist())
```
A. `['Alice', 'Carol', 'Eve']` — `pd.cut()`'s labels form an **ordered** categorical by default, so `>` compares by each tier's rank (`low < mid < high`), correctly keeping everyone above the lowest tier
B. Raises a `TypeError`, because comparing a categorical `Series` to a plain string with `>` is undefined unless `ordered=True` is passed explicitly to `pd.cut()`
C. `[]` (empty list), because `'low'` isn't a valid value to compare against a categorical dtype column, so the comparison evaluates to all-`False`
D. `['Bob', 'Dave', 'Frank']` — `pd.cut()` assigns `labels` in the order given, so `'low'` is treated as the *highest* rank since it's `bins[0]`'s label, and `>` keeps everything below it

## Q4. Grace wants to measure the real memory cost of keeping `team` as plain strings (object dtype) versus converting it to `category`. Which call actually accounts for the memory used by the individual string contents, not just pointers to them? (Roadmap #23)

```python
df6['team_obj'] = df6['team'].astype(str)
```
A. `df6['team_obj'].memory_usage()` — by default `deep=True`, so this already walks each string to measure its actual content size
B. `df6['team_obj'].memory_usage(deep=True)` — `deep=False` (the default) only sums the pointer-sized slots that reference each string object, while `deep=True` walks every actual string and adds its true memory footprint
C. `df6['team_obj'].nbytes` — `.nbytes` on an object-dtype Series already reports the full recursive size of every string it holds
D. `df6['team_obj'].memory_usage(deep=False)` — passing `deep=False` explicitly forces pandas to recompute the *real* string sizes exactly once, caching the deep result afterward

## Q5. Spot the bug: building on Q1's categorical `team` column, Grace tries to correct Alice's team. What actually happens? (Roadmap #23)

```python
df6['team'] = df6['team'].astype('category')
df6.loc[100, 'team'] = 'Green'
print(df6.loc[100, 'team'])
```
A. `'Green'` — assignment works normally and simply adds `'Green'` as a new value in that cell
B. `NaN` — pandas silently converts any value not already in the category list to a missing value on assignment
C. Raises a `TypeError`: `Cannot setitem on a Categorical with a new category ('Green'), set the categories first` — a categorical column's allowed values are fixed to its existing `categories`; assigning something outside that set requires explicitly adding it first (e.g. via `.cat.add_categories()`), it isn't auto-added
D. Raises a `KeyError`, because `100` isn't a valid category even though it's a valid row label

## Answer key

1. **B** — `astype('category')` with no categories/order specified builds the categories from the column's unique values and sorts them when they're sortable (plain strings are), giving `['Blue', 'Red']` lexicographically rather than `['Red', 'Blue']` (first-appearance order). A describes `pd.Categorical`'s behavior when you pass `ordered=False` with explicit `categories=` matching appearance order, not what a bare `astype('category')` does. C is wrong — `.cat` is available on any categorical-dtype Series, `astype('category')` included; no separate `pd.Categorical()` construction step is required. D is wrong — `.cat.codes` returns the integer codes; `.cat.categories` returns the actual label values.
2. **A** — a categorical dtype carries its full set of allowed `categories` independently of which ones appear in the data, but `groupby()`'s `observed` parameter controls whether unused categories are included; in current pandas, `observed=True` is the default, so grouping only produces rows for categories that actually occur — `Red` (85.0) and `Blue` (51.666...) — and `Green`, with zero backing rows, never shows up at all. B describes the *older* pandas default (`observed=False`, now deprecated/changed), which used to include every category in the dtype and show `NaN` for empty ones — that's not how a bare `df.groupby('team')` behaves anymore. C invents a sum-defaults-to-zero rule that isn't how pandas handles empty groups even under the old `observed=False` behavior — those showed `NaN`, never `0`. D is wrong — `groupby` never refuses to run just because a category is unused; under the current default it's simply left out of the result entirely.
3. **A** — `pd.cut()` defaults to `ordered=True` for its resulting categorical, so the `labels` you supply get a real rank order matching the bin order (`low < mid < high`). That makes `df6['tier'] > 'low'` a legitimate ordered comparison that keeps every row ranked above `'low'`: Alice (88, high), Carol (92, high), and Eve (75, mid) — Bob/Dave/Frank all land in the `low` bin (score ≤ 60) and get excluded. B is wrong — ordering is already the default for `pd.cut()`'s output; you don't need to pass `ordered=True` yourself. C is wrong — ordered categorical comparisons against a string that matches one of the categories work fine; this isn't an invalid-value situation. D misreads which end is "high" — `pd.cut()` ranks labels in the same order as the bins they're attached to (ascending bin edges), so `'low'` is the *lowest* rank, not the highest.
4. **B** — `Series.memory_usage()` defaults to `deep=False`, which for an object-dtype column only adds up the fixed-size pointers/references pandas stores for each Python object, not the strings' own memory; `deep=True` actually walks each string and sums its real size, which is exactly why `category` dtype (storing each unique string once, plus small integer codes) tends to save memory over object dtype with many repeated values. A is wrong about the default — it's `deep=False`, not `deep=True`. C is wrong — `.nbytes` reports the raw buffer size (essentially itemsize × length) for the underlying array, which for object dtype is just the pointer array, not a recursive walk of the strings. D is wrong — `deep=False` is the shallow, pointer-only calculation; it doesn't recompute or cache anything deep.
5. **C** — a categorical column's valid values are fixed to its current `categories`; pandas does not auto-expand that set on assignment. Trying to write a value that isn't already a category (`'Green'` isn't, when `categories` is still `['Blue', 'Red']`) raises `TypeError: Cannot setitem on a Categorical with a new category ('Green'), set the categories first` — you'd need `df6['team'].cat.add_categories(['Green'])` before such an assignment could succeed. A wrongly assumes categorical assignment behaves like a plain object column, silently accepting anything. B invents a silent-NaN fallback that isn't how pandas handles this case — it raises instead of coercing to missing. D is wrong — `100` is a perfectly valid row label here (it's part of `df6`'s own index); the error has nothing to do with row-label validity, it's about the *value* being assigned.
