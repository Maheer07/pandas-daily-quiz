## Q1. Reusing Day 53's two-team score grid, Grace totals it three different ways instead of looping over rows and columns by hand. What does this print? (Roadmap #44, #4)

```python
import numpy as np

grid = np.array([[88, 92, 79], [45, 50, 60]])  # shape (2, 3): 2 teams, 3 rounds

print(grid.sum())
print(grid.sum(axis=0).tolist())
print(grid.sum(axis=1).tolist())
```
A. `414` then `[133, 142, 139]` then `[259, 155]` — `grid.sum()` with no axis flattens everything and adds all six values (`88+92+79+45+50+60=414`). `axis=0` **collapses** the first axis (rows), leaving one total per *column* — per round, across both teams: `88+45=133`, `92+50=142`, `79+60=139`. `axis=1` collapses the second axis (columns), leaving one total per *row* — per team, across all rounds: `88+92+79=259`, `45+50+60=155`.
B. `414` then `[259, 155]` then `[133, 142, 139]` — swaps the two axis results, as if `axis=0` meant "sum along each row" (per-team) and `axis=1` meant "sum along each column" (per-round); `axis=N` actually names the axis that gets *collapsed*, so `axis=0` collapses rows to give per-column totals and `axis=1` collapses columns to give per-row totals — the opposite of this answer's assumption.
C. `6` then `[133, 142, 139]` then `[259, 155]` — wrongly computes the no-axis `sum()` as if it counted the number of elements (like `.size`) instead of adding their values; `grid.sum()` with no axis always adds every element together.
D. `414` then `[133, 142, 139]` then `[259, 154]` — gets everything right except mistraces the last row total, computing `45+50+60` as `154` instead of `155`.

## Q2. Contrasting with Day 53 Q5's `int8` wraparound, Grace now reduces the same running totals with `.sum()` instead of adding a scalar directly. What does this print? (Roadmap #44, #4, #41, #43)

```python
import numpy as np

totals = np.array([120, 45, 92], dtype=np.int8)

elementwise_bump = totals + np.int8(100)
print(elementwise_bump.dtype, elementwise_bump.tolist())

reduction = totals.sum()
print(reduction.dtype, reduction)
```
A. `int8 [-36, -111, -64]` then `int64 257` — Elementwise addition keeps both operands at `int8` (same as Day 53 Q5), so `120+100`, `45+100`, and `92+100` all wrap via two's-complement overflow. A **reduction** like `.sum()` is a different operation entirely: NumPy promotes small integer dtypes to a wider default integer type (`int64` on this platform) specifically so the running total doesn't overflow mid-accumulation, so `120+45+92` comes through as the true value `257`, not wrapped and not kept at `int8`.
B. `int8 [-36, -111, -64]` then `int8 1` — wrongly assumes `.sum()` keeps the `int8` dtype and wraps the accumulation the same way elementwise arithmetic does (`257 mod 256 = 1`); reductions promote to a wider integer type precisely to avoid this, so the dtype changes and the true sum survives.
C. `int64 [220, 145, 192]` then `int64 257` — wrongly assumes elementwise addition between two `int8` operands also auto-promotes to `int64` to dodge overflow, contradicting Day 53 Q5's lesson that same-width operand addition stays at that width and wraps.
D. `int8 [-36, -111, -64]` then `int64 1` — correctly promotes the reduction's dtype but still computes the sum as if accumulation happened in `int8` first and only got cast to `int64` afterward (`257 mod 256 = 1`); promotion happens *before* accumulation, so the true sum `257` is computed directly in `int64` and never wraps.

## Q3. Building on Q1's grid, Grace finds the best single round instead of just totalling scores. What does this print? (Roadmap #44, #4, #42)

```python
import numpy as np

grid = np.array([[88, 92, 79], [45, 50, 60]])

print(grid.argmax())
print(grid.argmax(axis=0).tolist())
print(grid.argmax(axis=1).tolist())
```
A. `1` then `[0, 0, 0]` then `[1, 2]` — `grid.argmax()` with no axis flattens the array in row-major order (`88, 92, 79, 45, 50, 60`) and returns the position of the overall maximum, `92`, which sits at flat index `1`. `axis=0` collapses rows, returning each column's own winning row-index: every column's larger value is in row `0` (`88>45`, `92>50`, `79>60`), giving `[0, 0, 0]`. `axis=1` collapses columns, returning each row's winning column-index: row 0's max `92` is at column `1`, row 1's max `60` is at column `2`, giving `[1, 2]`.
B. `92` then `[0, 0, 0]` then `[1, 2]` — confuses `argmax` (the *position* of the maximum) with `max` (the maximum *value* itself); `argmax` never returns the value found, only its index.
C. `1` then `[1, 2]` then `[0, 0, 0]` — swaps the two axis results exactly like Q1's trap: `axis=0` collapses rows (per-column index), and `axis=1` collapses columns (per-row index) — not the other way around.
D. `(0, 1)` then `[0, 0, 0]` then `[1, 2]` — wrongly assumes a no-axis `.argmax()` directly returns a 2-D `(row, col)` coordinate tuple, the way `np.unravel_index(grid.argmax(), grid.shape)` would; `.argmax()` alone always returns a single flat integer index into the flattened array, never a coordinate tuple on its own.

## Q4. Tying together Q1's aggregations and Day 53's broadcasting rules, Grace tries to mean-center each team's scores two different ways. What does this print? (Roadmap #44, #4, #43)

```python
import numpy as np

grid = np.array([[88, 92, 79], [45, 50, 60]])

row_means = grid.mean(axis=1)
print(row_means.tolist())

centered_kd = grid - grid.mean(axis=1, keepdims=True)
print(centered_kd.tolist())

try:
    centered = grid - row_means
except Exception as e:
    print(type(e).__name__)
```
A. `[86.33333333333333, 51.666666666666664]` then `[[1.6666666666666714, 5.666666666666671, -7.333333333333329], [-6.666666666666664, -1.6666666666666643, 8.333333333333336]]` then `ValueError` — `grid.mean(axis=1)` collapses columns to one average per row, shape `(2,)`. Adding `keepdims=True` instead keeps that collapsed axis as size `1`, giving shape `(2, 1)` — exactly the size-`1` axis that Day 53 Q3 showed stretches to match `grid`'s 3 columns, so each row's own mean is subtracted from every value in that row. Without `keepdims`, `row_means` is shape `(2,)`; its trailing axis (length 2) is compared against `grid`'s trailing axis (length 3) — same mismatch as Day 53 Q1's second case — and since neither is `1`, it raises.
B. `[86.33333333333333, 51.666666666666664]` then `[[1.6666666666666714, 5.666666666666671, -7.333333333333329], [-6.666666666666664, -1.6666666666666643, 8.333333333333336]]` then `[[1.67, 5.67, -7.33], [-6.67, -1.67, 8.33]]` (no error) — wrongly assumes a shape-`(2,)` array broadcasts against `grid`'s rows anyway; broadcasting only ever compares trailing axes, so `(2,)` vs `grid`'s trailing axis of `3` is a genuine mismatch that raises, not a shape NumPy infers "must mean per-row."
C. `[86.33333333333333, 51.666666666666664]` then `[[-20.333, -24.333, -11.333], [10.0, 5.0, -5.0]]` (wrong column-centering values) then `ValueError` — wrongly centers by the *column* means instead of the row means used in `grid.mean(axis=1, keepdims=True)`, as if `axis=1` meant "average down each column" rather than "average across each row."
D. `[86.33333333333333, 51.666666666666664]` then `[[1.67, 5.67, -7.33], [-6.67, -1.67, 8.33]]` then `ValueError` but claims `grid.mean(axis=1, keepdims=True)` has shape `(2, 3)` — wrongly assumes `keepdims=True` restores the collapsed axis to its *original* size (3) rather than keeping it at size `1` (which is the whole point of the flag — a size-`1` placeholder axis that broadcasting can stretch).

## Q5. To round out the aggregations theme, Grace discovers one round's score never got recorded and is stored as `np.nan`. What does this print? (Roadmap #44, #4)

```python
import numpy as np

round_scores = np.array([88.0, 92.0, np.nan, 50.0, 60.0])

print(round_scores.sum())
print(round_scores.mean())
print(np.nansum(round_scores))
print(np.nanmean(round_scores))
```
A. `nan` then `nan` then `290.0` then `72.5` — Ordinary `.sum()` and `.mean()` propagate any `nan` they touch: combining a number with `nan` always produces `nan`, so both results come out as `nan` regardless of the other four real values. `np.nansum()` and `np.nanmean()` are specifically designed to skip `nan` entries instead of propagating them: they sum/average only the four real scores (`88+92+50+60=290`), giving `290.0` and `290/4=72.5`.
B. `0.0` then `0.0` then `290.0` then `72.5` — wrongly assumes plain `.sum()`/`.mean()` silently treat a `nan` as `0` and still return a real number; they don't quietly substitute a value for `nan` at all, they propagate it, so the result itself becomes `nan`.
C. `nan` then `nan` then `290.0` then `58.0` — gets the plain aggregations and `nansum` right but miscalculates `nanmean` by dividing the real-value sum by the *original* element count (`290/5=58.0`) instead of the count of non-`nan` elements actually averaged (`290/4=72.5`).
D. `nan` then `nan` then `nan` then `nan` — wrongly assumes the `nan`-aware functions `np.nansum`/`np.nanmean` still propagate `nan` just like the plain versions; their entire purpose is to exclude `nan` entries from the computation rather than letting one bad value poison the whole result.
