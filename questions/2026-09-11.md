## Q4. What does the following print?


## Q5. What does the following print?

```python
import numpy as np
data = np.array([[10, 20, 30, 40],
                  [50, 60, 70, 80]], dtype=np.float32)
last_two_cols = data[:, -2:]
print(last_two_cols.mean(axis=0))
```
A. [35. 75.]
B. [50. 55. 60.]
C. [50. 60.]
D. Raises an IndexError because -2: is invalid syntax

## Answer key

1. **A** — Python-style true division (`/`) always upcasts the result to `float64`, even when both operands are integers, giving `[0.5, 1., 1.5]`. B wrongly assumes `/` behaves like floor division (`//`) and truncates. C keeps the correct `float64` dtype but wrongly assumes the *values* got truncated too — dtype promotion and value truncation are separate concepts (this is the reverse mistake of Day 1/2's "assigning into an int array truncates" rule: here nothing is being assigned into an int array, so no truncation happens). D wrongly assumes mixing an int array with a Python int needs an explicit cast.
2. **C** — `arr2d[:, 1:]` slices all rows but only columns from index 1 onward, giving `[[2, 3], [5, 6]]`; `.sum(axis=1)` then sums across each row: `[2+3, 5+6] = [5, 11]`. A is the `axis=0` result on the same slice (column sums `2+5=7, 3+6=9`), the classic axis mix-up. B wrongly reads the slice `1:` as "last column only" (as if it were `-1:`), taking just `[3, 6]`. D forgets the `axis=` parameter entirely and returns the grand total (`2+3+5+6=16`).
3. **D** — `arr[idx]` gathers `[1, 3, 5]`; multiplying by `1.5` promotes that temporary array to `[1.5, 4.5, 7.5]` (float), but assigning it back into `arr`, which is `int32`, silently truncates toward zero (same rule as Day 1 Q3 and Day 2 Q3/Q4) — not the whole-array upcast some might expect. So positions 0, 2, 4 become `1, 4, 7`, leaving the untouched positions 1, 3 as `2, 4`, giving `[1, 2, 4, 4, 7]`. A assumes NumPy rounds to the nearest integer on cast instead of truncating. B wrongly assumes the assignment upcasts `arr` itself to `float64`, but an existing array's dtype never changes from an in-place assignment. C wrongly assumes an incompatible-type error is raised — the unsafe cast happens silently.
4. **B** — `row_max = arr2d.max(axis=1)` gives shape `(2,)`: `[6, 9]`. Dividing the `(2, 3)` array by a `(2,)` array aligns shapes from the trailing dimension: `3` vs `2` — neither matches nor is `1`, so broadcasting fails with a `ValueError` (the same rule from Day 3 Q3, but here without the `keepdims=True` that Day 4 Q3 used to fix it). A is the value you'd get from mistakenly using `axis=0` (column max `[2, 5, 9]`) instead of `axis=1`, which happens to broadcast (shape `(3,)` against `(2,3)`) but divides by the wrong axis's max. C is what the correct row-wise division would produce *if* `row_max` had been computed with `keepdims=True` (shape `(2,1)`) — the fix that's missing here. D wrongly assumes broadcasting silently no-ops when shapes don't align, instead of raising an error.
5. **C** — `data[:, -2:]` takes all rows and the last two columns (`30, 40` and `70, 80`), giving `[[30, 40], [70, 80]]`; `.mean(axis=0)` then averages *down* each column: `[(30+70)/2, (40+80)/2] = [50., 60.]`. A is the `axis=1` result (row-wise means: `35., 75.`), the recurring axis mix-up. B has the right idea for "average per column" but wrongly includes a third value, as if the slice had kept 3 columns instead of 2. D is wrong — negative-stop-omitted slices like `-2:` are valid NumPy/Python syntax and select the last two columns without error.
