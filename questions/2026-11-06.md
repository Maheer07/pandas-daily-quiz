## Q1. Building on Day 41's row-centering-via-broadcast pattern and Day 42's `np.linalg` work, Grace rescales the recurring `grid` so each row becomes a unit vector, using `np.linalg.norm(..., axis=1, keepdims=True)` instead of a manual `.reshape(-1, 1)`. What does this print? (Roadmap #33, #34)

```python
import numpy as np

grid = np.array([[88, 45, 92], [60, 75, 50]])
row_norms = np.linalg.norm(grid, axis=1, keepdims=True)
print(row_norms.shape)
normalized = grid / row_norms
print(np.round(normalized, 3).tolist())
print(np.round(np.linalg.norm(normalized, axis=1), 3).tolist())
```
A. `(2, 1)` then `[[0.652, 0.333, 0.681], [0.554, 0.693, 0.462]]` then `[1.0, 1.0]` — `np.linalg.norm(grid, axis=1, keepdims=True)` computes each row's Euclidean length and keeps the reduced axis as size 1, giving shape `(2, 1)` — already broadcast-ready against `grid`'s `(2, 3)` with no `.reshape()` needed. Dividing broadcasts each row's own norm down that row, so every normalized row now has unit length, which the final check confirms by recomputing each row's norm and getting `1.0` back for both
B. `(1, 3)` then `[[0.826, 0.514, 0.879], [0.563, 0.857, 0.478]]` then `[1.311, 1.132]` — confuses `axis=1` (collapse each row) with `axis=0` (collapse each column): computes each *column's* norm instead, giving shape `(1, 3)`, and the division normalizes columns rather than rows, so the rows themselves don't end up unit-length, which is exactly what the final (still per-row) check catches
C. `(2,)` then raises `ValueError` — wrongly treats `keepdims=True` as having no effect, as if `axis=1` already returned a flat `(2,)` shape, which wouldn't broadcast against `grid`'s trailing axis of 3 without an explicit reshape
D. `(2, 1)` then `[[88.0, 45.0, 92.0], [60.0, 75.0, 50.0]]` then `[135.03, 108.282]` — correctly gets the shape from `keepdims=True` but wrongly assumes dividing by `row_norms` leaves `grid` unchanged, and that the final check re-reports the original row norms instead of recomputing the (now unit) norms of the normalized array

## Q2. Building on Day 43's `pd.NamedAgg`-style syntax and Day 44's `.resample()` work, Grace discovers that `.resample()`'s `.agg()` accepts the exact same named-aggregation keywords as `.groupby()`'s does. What does this print? (Roadmap #35, #36)

```python
import pandas as pd

ts = pd.DataFrame({
    'score': [10, 20, 30, 40, 50, 60],
    'bonus': [1, 2, 3, 4, 5, 6],
}, index=pd.date_range('2026-01-01', periods=6, freq='D'))

summary = ts.resample('2D').agg(
    total_score=('score', 'sum'),
    avg_bonus=('bonus', 'mean'),
)
print(summary.columns.tolist())
print(summary['total_score'].tolist())
print(summary['avg_bonus'].tolist())
```
A. `['total_score', 'avg_bonus']` then `[30, 70, 110]` then `[1.5, 3.5, 5.5]` — `.resample('2D')` bins the 6 days into three 2-day windows (Jan1-2, Jan3-4, Jan5-6); `.agg()` on a resampled object takes the same `name=(column, func)` named-aggregation syntax as `.groupby().agg()`, so `total_score` sums each bin's `score` and `avg_bonus` averages each bin's `bonus`
B. Raises `TypeError` — wrongly assumes named-aggregation syntax is exclusive to `.groupby().agg()`, and that `.resample().agg()` only accepts a plain function name or list of functions, not `name=(column, func)` keyword pairs
C. `['total_score', 'avg_bonus']` then `[15.0, 35.0, 55.0]` then `[3, 7, 11]` — swaps which function each named column actually uses, computing `total_score` as each bin's *mean* score and `avg_bonus` as each bin's *summed* bonus, rather than matching each name to the aggfunc actually given
D. `['total_score', 'avg_bonus']` then `[30, 70, 110, 0]` then `[1.5, 3.5, 5.5, 0.0]` — wrongly assumes `.resample('2D')` always leaves a trailing partial bin the way Day 44's 10-day/3-day example did, missing that 6 days split evenly into three 2-day bins with no leftover, and inventing a 4th empty bin that doesn't exist

## Q3. Spot the bug — building on Day 43's named-aggregation style and Day 44's `groupby().rolling()` pattern, Grace tries to combine the two directly, giving a rolling sum a custom output name the same way she named `.agg()` outputs for a plain groupby. What does this print? (Roadmap #35, #36)

```python
df_g = pd.DataFrame({
    'team': ['Red', 'Red', 'Red', 'Blue', 'Blue', 'Blue'],
    'score': [10, 20, 30, 5, 15, 25],
})
try:
    rolled = df_g.groupby('team')['score'].rolling(2).agg(total=('score', 'sum'))
    print(rolled.tolist())
except Exception as e:
    print(type(e).__name__)
```
A. `SpecificationError` — named-aggregation tuples (`name=(column, func)`) are only accepted by `.groupby().agg()` and `.resample().agg()`, which reduce a full DataFrame's columns down to one row per group/bin. `groupby('team')['score']` has already narrowed things to a single Series before `.rolling()` is even called, and a rolling window's `.agg()` doesn't support that column-referencing tuple form at all — pandas rejects it with `pandas.errors.SpecificationError: nested renamer is not supported`
B. `[nan, 20.0, 40.0, nan, 30.0, 50.0]` — wrongly assumes rolling's `.agg()` accepts the same named-tuple syntax as groupby/resample's `.agg()`, producing the correct per-team rolling 2-sums (Blue sorted before Red, since `groupby` defaults to alphabetical group order) under the custom name `total` — when the call actually never gets that far and raises instead
C. `TypeError` — wrongly attributes the failure to an unrecognized-keyword-argument error, as if `.rolling()` or `.agg()` simply rejected the keyword `total` outright, rather than pandas' more specific `SpecificationError` for this exact nested/renamer-style aggregation spec
D. `AttributeError` — wrongly assumes `SeriesGroupBy.rolling()` doesn't support `.agg()` at all, when `.agg()` on a rolling object works fine for ordinary function names or lists — it's specifically the column-referencing named-tuple form that's rejected here

## Q4. Contrasting with Q1's broadcasting, Grace checks whether two same-shaped matrices can always combine with both `*` and `@`. What does this print? (Roadmap #33, #34)

```python
a = np.array([[1, 2, 3], [4, 5, 6]])
b = np.array([[10, 20, 30], [40, 50, 60]])
print((a * b).tolist())
try:
    print((a @ b).tolist())
except ValueError as e:
    print(type(e).__name__)
```
A. `[[10, 40, 90], [160, 250, 360]]` then `ValueError` — `*` is pure elementwise multiplication, which only needs the two shapes to be broadcast-compatible; since both are the identical `(2, 3)` shape, it just multiplies entry-by-entry. `@` is matrix multiplication instead, which requires the *inner* dimensions to match (left's columns vs right's rows) — here that's `3` vs `2`, which don't match, so it raises `ValueError` even though the two arrays are otherwise the exact same shape
B. `ValueError` then `[[10, 40, 90], [160, 250, 360]]` — swaps which operator is the strict one, wrongly assuming elementwise `*` is the one that enforces matrix-multiplication's inner-dimension rule and that `@` is the one that just broadcasts freely on identical shapes
C. `[[10, 40, 90], [160, 250, 360]]` then `[[10, 40, 90], [160, 250, 360]]` — wrongly assumes `@` succeeds and matches `*` whenever the two operands' overall shapes are identical, missing that matmul compatibility is about the *inner* dimensions lining up, not the two shapes being equal
D. `[[10, 40, 90], [160, 250, 360]]` then `[[140, 320], [320, 770]]` — correctly gets the elementwise line but wrongly assumes NumPy automatically transposes the right-hand operand to make dimensions line up whenever a plain `@` would otherwise fail, rather than just raising `ValueError`

## Q5. Building on Day 41's `.reshape(-1, 1)` fix for a broadcasting failure, Grace now feeds a `.resample()` result into that same pattern, splitting each day's score into a share of its own 3-day block total. What does this print? (Roadmap #33, #36)

```python
s = pd.Series(
    [10, 20, 30, 40, 50, 60],
    index=pd.date_range('2026-01-01', periods=6, freq='D'),
)
block_totals = s.resample('3D').sum().to_numpy()
blocks = s.to_numpy().reshape(2, 3)
print(block_totals.tolist())
try:
    print(np.round(blocks / block_totals, 3).tolist())
except ValueError as e:
    print(type(e).__name__)
print(np.round(blocks / block_totals.reshape(-1, 1), 3).tolist())
```
A. `[60, 150]` then `ValueError` then `[[0.167, 0.333, 0.5], [0.267, 0.333, 0.4]]` — `s.resample('3D').sum()` bins the 6 daily values into two 3-day totals, `60` and `150`; reshaping the raw values into a `(2, 3)` grid lines each block up as its own row. Dividing straight by the `(2,)` totals fails because broadcasting compares shapes from the trailing axis inward (`3` vs `2`, neither is `1`) — the exact same failure shape as Day 41's unreshaped row-means. Reshaping the totals to `(2, 1)` puts the needed `1` in the trailing position, letting each row divide cleanly by its own block's total
B. `[60, 150]` then `[[0.167, 0.333, 0.5], [0.267, 0.333, 0.4]]` then the same result again — wrongly assumes broadcasting checks the *leading* axis first (so a 2-element array "obviously" matches the grid's 2 rows), missing that NumPy always compares from the last axis inward, which is exactly why the plain division fails before any reshape is applied
C. `[20, 50]` then `ValueError` then `[[0.5, 1.0, 1.5], [0.8, 1.0, 1.2]]` — confuses `.resample('3D').sum()` with `.mean()`, averaging each block instead of totaling it (`20`, `50`), which throws off every downstream value even though the broadcasting logic itself is applied correctly
D. `[60, 150]` then `ValueError` then `ValueError` — correctly predicts the first failure but wrongly assumes `.reshape(-1, 1)` turns `block_totals` into shape `(1, 2)` rather than `(2, 1)`, so expects the "fixed" division to fail the exact same way

## Answer key

1. **A** — `np.linalg.norm(grid, axis=1, keepdims=True)` computes each row's Euclidean length while keeping the reduced axis as size 1, giving shape `(2, 1)` — already broadcast-ready against `grid`'s `(2, 3)`. Dividing scales each row to unit length, confirmed by the final re-check printing `[1.0, 1.0]`. B swaps `axis=1` for `axis=0`, normalizing columns instead of rows. C wrongly treats `keepdims=True` as a no-op. D gets the shape right but wrongly assumes the division (and the final check) don't actually change/recompute anything.
2. **A** — `.resample('2D')` bins the 6 days into three 2-day windows; `.resample().agg()` accepts the same named-aggregation syntax as `.groupby().agg()`, so `total_score` sums (`30, 70, 110`) and `avg_bonus` averages (`1.5, 3.5, 5.5`) each bin correctly. B wrongly assumes this syntax is groupby-exclusive. C swaps which function each name actually computes. D wrongly invents a 4th leftover bin when 6 divides evenly by 2.
3. **A** — named-aggregation tuples are a groupby/resample feature for reducing full DataFrame columns to one row per group; a rolling window on an already-narrowed Series doesn't support that column-referencing form and raises `pandas.errors.SpecificationError: nested renamer is not supported`. B wrongly assumes the call succeeds and just computes the ordinary rolling sums. C and D misattribute the failure to the wrong exception type/cause.
4. **A** — elementwise `*` only needs broadcast-compatible shapes, which two identical `(2, 3)` arrays trivially are. Matrix multiplication `@` instead requires the *inner* dimensions to match (`3` vs `2` here), which fail regardless of the arrays' overall shape being equal, so it raises `ValueError`. B swaps which operator enforces which rule. C wrongly assumes equal overall shapes guarantee `@` succeeds. D wrongly invents an auto-transpose fallback NumPy doesn't perform.
5. **A** — `.resample('3D').sum()` gives block totals `[60, 150]`; dividing the reshaped `(2, 3)` grid directly by the `(2,)` totals fails on the same trailing-axis mismatch as Day 41's unreshaped case, while reshaping to `(2, 1)` fixes it, giving each day's share of its block's total. B wrongly assumes broadcasting checks the leading axis first. C confuses `.sum()` with `.mean()` on the resample step. D correctly predicts the first failure but wrongly assumes `.reshape(-1, 1)` yields shape `(1, 2)` instead of `(2, 1)`.
