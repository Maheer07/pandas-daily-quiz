## Q1. Grace chains a filter, a two-function aggregation, and a sort into one statement, building on the recurring `df6`. What does this print? (Roadmap #26)

```python
import pandas as pd

data6 = {'name': ['Alice', 'Bob', 'Carol', 'Dave', 'Eve', 'Frank'],
         'team': ['Red', 'Blue', 'Red', 'Blue', 'Red', 'Blue'],
         'region': ['North', 'South', 'North', 'North', 'South', 'South'],
         'score': [88, 45, 92, 60, 75, 50]}
df6 = pd.DataFrame(data6, index=[100, 101, 102, 103, 104, 105])

chain1 = (df6[df6['score'] > 50]
          .groupby('team')['score']
          .agg(['mean', 'count'])
          .sort_values('mean', ascending=False))
print(chain1)
```
A. Filters out only Bob (45) and keeps Frank (50), since `> 50` is read as `>= 50`, giving Red mean 85.0/count 3 and Blue mean 55.0/count 2, with Red's row first.
B. Filters out both Bob (45) and Frank (50), since neither score is strictly greater than 50, leaving Red with Alice/Carol/Eve (mean 85.0, count 3) and Blue with only Dave (mean 60.0, count 1); sorted descending by mean, Red's row comes first.
C. The two aggregate columns print as `count` then `mean`, in alphabetical order, regardless of the order written inside `agg(['mean', 'count'])`.
D. Raises a `ValueError`, because `sort_values()` can't take a single column name once the object being sorted is the multi-column result of `.agg()` with a list of functions — a list of column names is required instead.

## Q2. Building on Q1's filter, Grace groups by two keys instead of one, then sorts the result. What does this print? (Roadmap #26, #14)

```python
chain2 = (df6[df6['score'] >= 60]
          .groupby(['team', 'region'])['score']
          .sum()
          .sort_values(ascending=False))
print(chain2)
```
A. Raises a `TypeError`, because `sort_values()` can't be called on a `Series` whose index is a `MultiIndex` without first specifying which level to sort by.
B. Prints in the groupby's own default (sorted-by-index) order instead — `Blue`/`North` (60) first, then `Red`/`North` (180), then `Red`/`South` (75) — because `sort_values()` here sorts the index labels, not the summed values.
C. Prints sorted by the summed values themselves, highest first: `Red`/`North` (180), then `Red`/`South` (75), then `Blue`/`North` (60) — `sort_values()` on a `Series` always sorts by its values, and a `MultiIndex` doesn't change that.
D. Prints the same three rows as C but in ascending order — lowest total first — because `.sort_values()` defaults to ascending and the explicit `ascending=False` here is silently ignored on a `MultiIndex`-indexed `Series`.

## Q3. Spot the bug: Grace tries to grab the `team` column out of a chain she just built. What actually happens? (Roadmap #26, #13)

```python
chain3 = (df6.groupby('team')['score']
          .mean()
          .sort_values(ascending=False))
print(chain3['team'])
```
A. Raises `KeyError: 'team'` — after `.groupby('team')['score'].mean()`, the result is a `Series` whose index *is* the team labels (`'Red'`/`'Blue'`); `'team'` is only that index's *name*, not one of its actual labels, so there's no row to find under the key `'team'`.
B. Returns `array(['Red', 'Blue'], dtype=object)` — bracket indexing a `Series` by its index's name returns every label in that index level.
C. Returns `NaN` — bracket indexing with a key that isn't present in a `Series`' index returns `NaN` rather than raising, the same way `.get()` would with no default.
D. Returns a one-column `DataFrame` containing the two team labels — because the chain implicitly calls `.reset_index()` before being printed, turning `'team'` back into an accessible column.

## Q4. Building on Q1-Q2's filtering, Grace swaps in an `.isin()` filter on `region` before grouping. What does this print? (Roadmap #26, #9)

```python
chain4 = (df6[df6['region'].isin(['North'])]
          .groupby('team')['score']
          .agg('mean')
          .sort_values())
print(chain4)
```
A. `Red  90.0` then `Blue  60.0` (descending) — leaving `sort_values()`'s `ascending` argument unset defaults to `False`.
B. `Red  85.0` then `Blue  51.666...` (ascending) — treats the filter as never happening, averaging all three rows of each team (including the South-region rows) instead of only the North rows.
C. Raises a `ValueError`, because `.isin()` requires its argument to be exactly as long as the column it's filtering, and `['North']` is only length 1 while `df6['region']` has 6 rows.
D. `Blue  60.0` then `Red  90.0` — the `isin(['North'])` filter keeps only Alice, Carol, and Dave; grouping those by team and averaging gives Blue (just Dave) 60.0 and Red (Alice+Carol) 90.0; `sort_values()` with no arguments defaults to ascending, so Blue's smaller mean comes first.

## Q5. Grace wants, for each team, the total of only the rows scoring 60 or higher, sorted highest-total-first — using a single vectorized chain (no row-wise Python-level calls). Which line is correct? (Roadmap #26, #25)

A. `df6[df6['score'] >= 60].groupby('team')['score'].sum().sort_values(ascending=False)` — filters individual rows to keep only scores ≥ 60 first (Alice 88, Carol 92, Dave 60, Eve 75), then groups the four surviving rows by team and sums, then sorts the two team totals descending — entirely with vectorized pandas calls, giving Red 255 then Blue 60.
B. `df6.groupby('team')['score'].sum()[df6['score'] >= 60].sort_values(ascending=False)` — raises an indexing error: the boolean mask `df6['score'] >= 60` is built against `df6`'s original 6-row index, but it's then used to filter the already-grouped 2-row `Series` (indexed by team labels `'Blue'`/`'Red'`), and a boolean mask can't be aligned against a `Series` of a completely different length and index.
C. `df6.groupby('team')['score'].apply(lambda g: g[g >= 60].sum()).sort_values(ascending=False)` — reaches the same correct totals (Red 255, Blue 60) but does it by invoking a Python-level lambda separately for each group rather than filtering the whole frame with one vectorized boolean mask up front, so it isn't the single-vectorized-chain version the question asks for.
D. `df6.groupby('team')['score'].sum().loc[lambda s: s >= 60].sort_values(ascending=False)` — filters on each team's *overall total* instead of on individual rows before summing, so both teams survive (Red's total 255 and Blue's full, unfiltered total of 45+60+50=155), giving `Red 255` then `Blue 155` — not the intended `Red 255`/`Blue 60`.

## Answer key

1. **B** — `df6['score'] > 50` is a strict inequality, so Bob (45) and Frank (50) are both excluded (50 is not greater than 50) while Alice (88), Carol (92), Dave (60), and Eve (75) survive. Grouping the survivors by team gives Red (Alice, Carol, Eve) a mean of 85.0 over count 3, and Blue (Dave only) a mean of 60.0 over count 1; sorting descending by `'mean'` puts Red's row first. A wrongly treats `> 50` as `>= 50`, which would keep Frank and change Blue's stats. C invents an alphabetizing behavior `.agg()` doesn't have — it preserves the exact order of function names you pass it. D is wrong — `sort_values('mean', ...)` works perfectly well on a multi-column result as long as `'mean'` names one real column, no list required.
2. **C** — `sort_values()` on a `Series` sorts by the `Series`' own values, never by its index, whether that index is a simple `RangeIndex` or, as here, a 2-level `MultiIndex`. After the `>= 60` filter and the two-key sum (`(Red, North)=180`, `(Red, South)=75`, `(Blue, North)=60`), sorting descending by value puts `180` first, `75` second, `60` last. A and D both invent restrictions/quirks that `sort_values()` doesn't have on a `MultiIndex`-indexed `Series` — it works exactly as documented, honoring `ascending=False`. B describes `sort_index()`'s behavior (sorted by index labels), not `sort_values()`'s.
3. **A** — `.groupby('team')['score'].mean()` collapses the data down to one row per team, with the team labels themselves (`'Red'`, `'Blue'`) becoming the `Series`' index; `.sort_values()` only reorders those rows, it doesn't add a row or column back. `'team'` is just that index's *name* — metadata describing what the index represents — not a label actually present in it, so `chain3['team']` can't find a match and raises `KeyError: 'team'`. B confuses this with `.index.tolist()` or similar — bracket-indexing by a name that isn't a label doesn't dump the whole index back out. C is wrong — a `Series` raises `KeyError` for a missing label in plain bracket indexing; it doesn't quietly return `NaN` (that's `.get()`'s behavior with a default). D is wrong — nothing in this chain calls `.reset_index()`; the team labels stay in the index throughout.
4. **D** — `.isin(['North'])` keeps only the three rows where `region` is `'North'`: Alice (Red, 88), Carol (Red, 92), and Dave (Blue, 60). Grouping those by team and averaging gives Red `(88+92)/2 = 90.0` and Blue `60.0`; `.sort_values()` called with no arguments defaults to ascending order, so Blue's smaller mean (60.0) prints first, then Red's (90.0). A wrongly assumes `sort_values()` defaults to descending — it's ascending unless `ascending=False` is passed explicitly. B ignores the filter entirely, averaging all three rows per team (including the South-region ones) instead of just the North rows. C is wrong about `.isin()` — it tests membership against any list of values, regardless of how that list's length compares to the column's length; there's no length-matching requirement.
5. **A** — filtering `df6` down to just the rows scoring ≥ 60 *before* grouping and summing is the single vectorized way to get each team's total made up only of qualifying rows: Red keeps Alice (88), Carol (92), and Eve (75) for a total of 255, and Blue keeps only Dave (60); sorting descending then prints `Red 255` followed by `Blue 60`. B is wrong — the boolean mask is built against `df6`'s original 6-row index but applied to the already-grouped 2-row `Series` (indexed by team names), and pandas can't align a boolean mask against a `Series` of mismatched length/index, so it raises rather than filtering anything. C reaches the same correct numbers but does so by running a Python-level lambda once per group via `.apply()`, exactly the per-group/row-wise overhead the question's "single vectorized chain" requirement rules out. D filters on each team's *overall* total rather than on individual rows first, so Blue's full unfiltered total (45+60+50=155, which is itself ≥ 60) survives instead of being trimmed down to just Dave's qualifying 60, giving the wrong final total for Blue.
