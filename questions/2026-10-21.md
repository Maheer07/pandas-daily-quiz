## Q1. Grace pivots the recurring `df6`, now with a `bonus_pct` column, using two value columns at once. What does this print? (Roadmap #27)

```python
import pandas as pd

data6 = {'name': ['Alice', 'Bob', 'Carol', 'Dave', 'Eve', 'Frank'],
         'team': ['Red', 'Blue', 'Red', 'Blue', 'Red', 'Blue'],
         'region': ['North', 'South', 'North', 'North', 'South', 'South'],
         'score': [88, 45, 92, 60, 75, 50]}
df6 = pd.DataFrame(data6, index=[100, 101, 102, 103, 104, 105])
df6['bonus_pct'] = [0.1, 0.2, 0.15, 0.05, 0.25, 0.1]

pt1 = pd.pivot_table(df6, values=['score', 'bonus_pct'], index='team',
                      columns='region', aggfunc='mean')
print(pt1.columns.tolist())
print(pt1.loc['Blue', ('score', 'South')])
```
A. `[('score', 'North'), ('score', 'South'), ('bonus_pct', 'North'), ('bonus_pct', 'South')]` then `47.5` — the outer column level follows the exact order the names were written inside `values=['score', 'bonus_pct']`
B. `[('bonus_pct', 'North'), ('bonus_pct', 'South'), ('score', 'North'), ('score', 'South')]` then `47.5` — with multiple value columns, `pivot_table` sorts the outer column level alphabetically by value-column name, regardless of the order they were listed in `values=`; `region`'s two categories fill the inner level the same as a single-value pivot would
C. Raises a `ValueError`, because `aggfunc='mean'` is a single string and can't be applied across two differently-typed value columns (`score` is `int64`, `bonus_pct` is `float64`) at once
D. `[('bonus_pct', 'North'), ('bonus_pct', 'South'), ('score', 'North'), ('score', 'South')]` then `60.0` — same alphabetical column ordering as B, but `df6.loc['Blue', ('score', 'South')]` actually grabs Blue's `North` value instead of `South`, because the inner level's labels are implicitly reversed whenever the outer level is sorted alphabetically

## Q2. Contrast with Q1: Grace now passes a *list of functions* to `aggfunc` instead of a list of value columns. What does this print? (Roadmap #27)

```python
pt2 = pd.pivot_table(df6, values='score', index='team', aggfunc=['mean', 'max'])
print(pt2.columns.tolist())
```
A. `[('mean', 'score'), ('max', 'score')]` — unlike Q1's `values=` list (which gets sorted alphabetically), a list passed to `aggfunc` keeps the exact order it was written in as the outer column level, with the single value column (`score`) repeated as the inner level
B. `[('max', 'score'), ('mean', 'score')]` — `aggfunc` lists are sorted alphabetically by function name, the same rule Q1 applied to the `values=` list
C. `[('score', 'mean'), ('score', 'max')]` — the value column always becomes the outer level and the function names become the inner level, regardless of which one was passed as a list
D. Raises a `TypeError`, because `aggfunc` only accepts a single string or callable — passing a list of function names like `['mean', 'max']` isn't supported

## Q3. Grace now gives each value column its *own* aggregation function via a dict. What does this print? (Roadmap #27)

```python
pt3 = pd.pivot_table(df6, values=['score', 'bonus_pct'], index='team',
                      aggfunc={'score': 'sum', 'bonus_pct': 'mean'})
print(pt3.loc['Red'].tolist())
print(pt3.columns.tolist())
```
A. `[0.166666..., 255]` then `['bonus_pct', 'score']` — each key in the `aggfunc` dict applies its own function only to that column (`bonus_pct` averaged, `score` summed), and the resulting columns are still sorted alphabetically by value-column name just like Q1's list, regardless of the dict's own key order (`'score'` was written first)
B. `[255, 0.166666...]` then `['score', 'bonus_pct']` — the columns come out in the exact order the dict's keys were written (`'score'` first, then `'bonus_pct'`), since Python dicts preserve insertion order
C. `[85.0, 0.166666...]` then `['bonus_pct', 'score']` — a dict passed to `aggfunc` is silently ignored in favor of `pivot_table`'s own default (`mean`) for every value column, so `score` comes back averaged (85.0) rather than summed
D. Raises a `ValueError`, because every key used in an `aggfunc` dict must also appear in `index` or `columns`, not in `values`

## Q4. Spot the bug: Grace swaps `pivot_table` for plain `pivot`, assuming it will behave the same on `df6`. What actually happens? (Roadmap #27, #15, #20)

```python
result4 = df6.pivot(index='team', columns='region', values='score')
```
A. Raises a `ValueError` (duplicate entries), because `('Red', 'North')` matches two rows — Alice and Carol — and plain `.pivot()` only reshapes labels without aggregating; it requires every `index`/`columns` combination to be unique, unlike `pivot_table()`, which resolves duplicates through `aggfunc`
B. Returns the exact same `DataFrame` as `pd.pivot_table(df6, values='score', index='team', columns='region')` from earlier days, since `.pivot()` defaults to averaging duplicate combinations just like `pivot_table()` does
C. Returns a `DataFrame` where `('Red', 'North')` silently holds only Carol's `92`, since `.pivot()` keeps the last-seen row for any duplicate combination and drops the earlier one
D. Raises a `KeyError`, because `.pivot()` requires `columns='region'` to already be part of a `MultiIndex` before it can be pulled out as a pivot axis

## Q5. Building on Day 32's filter-then-aggregate chains, Grace filters `df6` down to scores ≥ 60 before pivoting, and wants the resulting gap filled in rather than left blank. What does this print? (Roadmap #27, #26, #11)

```python
sub = df6[df6['score'] >= 60]
pt5 = pd.pivot_table(sub, values='score', index='team', columns='region',
                      aggfunc='mean', fill_value=0)
print(pt5.loc['Blue'].tolist())
```
A. `[60.0, 0.0]` — the filter leaves Blue with only Dave (`score=60`, region `North`), so Blue has no surviving `South` row at all; that missing `(Blue, South)` combination would normally show up as `NaN`, and `fill_value=0` replaces exactly that missing cell with `0`, leaving Dave's real `North` mean untouched
B. `[60.0, nan]` — `fill_value` has no effect here because it only takes effect when `dropna=False` is also passed explicitly
C. Raises a `ValueError`, because `fill_value` can only be combined with `margins=True`
D. `[0.0, 0.0]` — `fill_value=0` overwrites every cell in the result, including ones with real computed values, not just the missing ones

## Answer key

1. **B** — With multiple columns passed to `values=`, `pivot_table` sorts that outer column level alphabetically by value-column name (`bonus_pct` before `score`) regardless of the order they were written in `values=['score', 'bonus_pct']`; the inner `region` level still just holds `North`/`South` as usual, and Blue's `('score', 'South')` cell is Bob+Frank's mean, `(45+50)/2 = 47.5`. A wrongly assumes the `values=` list order is preserved as column order — Q2 contrasts this by showing `aggfunc` lists *do* preserve order, which is precisely the opposite rule. C invents a type restriction `aggfunc='mean'` doesn't have — a single string aggfunc applies independently to each value column regardless of their individual dtypes. D correctly identifies the alphabetical sort but then invents a nonsensical "reversed inner level" rule that doesn't exist — label-based `.loc` lookups always find the exact key asked for.
2. **A** — A list passed to `aggfunc` becomes the outer column level in the *exact order it was written* (`'mean'` then `'max'`), with the single value column `score` repeated as the inner level for each — the opposite ordering rule from Q1, where it was the `values=` list (not `aggfunc`) that got alphabetized. B wrongly imports Q1's alphabetical-sort rule onto `aggfunc` lists, which is backwards — that sorting only applies to the `values=` list when there are multiple value columns. C swaps which level is outer vs inner — function names are the outer level here since only one value column is involved; the value-column-outer arrangement is what Q1 showed for multiple *value* columns, not multiple functions. D is wrong — `aggfunc` fully supports a list of function names/callables, exactly as shown.
3. **A** — Each key in the `aggfunc` dict controls the aggregation applied to *that* value column only, so `bonus_pct` is averaged (`(0.1+0.2+0.25)/3 ≈ 0.1667` for Red) while `score` is summed (`88+92+75 = 255` for Red); the resulting columns are still sorted alphabetically (`bonus_pct`, `score`), the same rule as Q1's `values=` list, regardless of the dict writing `'score'` first. B wrongly assumes dict key *insertion* order drives column order — that's true for the dict itself, but `pivot_table`'s output columns still get sorted alphabetically same as any multi-value pivot. C invents a "dict is ignored" behavior — a per-column `aggfunc` dict is fully honored, not silently replaced by a single default function for every column. D invents a restriction that doesn't exist — `aggfunc` dict keys are expected to be value-column names, not `index`/`columns` names.
4. **A** — `('Red', 'North')` matches two source rows (Alice's 88 and Carol's 92); plain `.pivot()` is a pure reshape with no aggregation step, so it requires every `index`/`columns` pairing to map to exactly one row and raises `ValueError` the moment it finds a duplicate — this is exactly why `pivot_table()` exists, since it resolves such duplicates via `aggfunc`. B wrongly assumes `.pivot()` has an implicit aggregation step like `pivot_table()`'s default `'mean'` — it has none at all. C invents a silent last-value-wins behavior that `.pivot()` doesn't have; it raises rather than quietly dropping data. D invents an unrelated `MultiIndex` prerequisite — `.pivot()` works fine on plain columns; its only real constraint is uniqueness of the index/columns combination.
5. **A** — Filtering to `score >= 60` leaves Blue with only Dave (`North`, `60`), so the `(Blue, South)` cell has no underlying data and would normally be `NaN`; `fill_value=0` specifically replaces missing combinations like that with `0` while leaving every real computed value (Dave's `North` mean of `60.0`) untouched, giving `[60.0, 0.0]`. B invents a dependency on `dropna` that `fill_value` doesn't have — `fill_value` works on its own to replace missing combinations with the given value. C invents a restriction that doesn't exist — `fill_value` works independently of `margins`. D is wrong — `fill_value` only touches cells that would otherwise be `NaN` due to a missing index/columns combination; it never overwrites a real aggregated value.
