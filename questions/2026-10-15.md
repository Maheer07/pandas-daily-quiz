## Q1. Building on the recurring `df6` (the same table from the last several days), Grace pulls two columns out together as a raw array. What does this print? (Roadmap #24)

```python
import pandas as pd
import numpy as np

data6 = {'name': ['Alice', 'Bob', 'Carol', 'Dave', 'Eve', 'Frank'],
         'team': ['Red', 'Blue', 'Red', 'Blue', 'Red', 'Blue'],
         'region': ['North', 'South', 'North', 'North', 'South', 'South'],
         'score': [88, 45, 92, 60, 75, 50]}
df6 = pd.DataFrame(data6, index=[100, 101, 102, 103, 104, 105])

arr = df6[['name', 'score']].to_numpy()
print(arr.dtype)
```
A. a structured/record dtype that preserves each column's own original dtype as a separate field
B. Raises a `TypeError`, because `.to_numpy()` refuses to combine a string column and a numeric column into one array
C. `object` — with columns of different dtypes, `.to_numpy()` has to pick one common dtype for the whole 2-D array, and the most general type that can hold both strings and numbers is Python `object`
D. `int64` — `.to_numpy()` keeps the numeric columns' dtype and silently drops any non-numeric column from the result

## Q2. Building on Day 28's categorical `team` column, Grace extracts it to a NumPy array. What does this print? (Roadmap #23, #24)

```python
df6['team'] = df6['team'].astype('category')
arr2 = df6['team'].to_numpy()
print(arr2.tolist())
```
A. `[0, 1, 0, 1, 0, 1]` — `.to_numpy()` on a categorical Series returns the internal integer codes actually stored in memory, not the labels they point to
B. `['Red', 'Blue']` — `.to_numpy()` deduplicates to the unique categories, the same list `.cat.categories` would give
C. Raises a `TypeError`, because `.to_numpy()` isn't defined for categorical dtype — you'd need `.cat.codes.to_numpy()` instead
D. `['Red', 'Blue', 'Red', 'Blue', 'Red', 'Blue']` — `.to_numpy()` reconstructs the actual label for every row from the codes and categories, so the categorical dtype disappears and you get back plain string values in the original row order

## Q3. Building on Q1's `df6`, Grace applies a NumPy ufunc directly to a one-column DataFrame instead of converting it first. What does this print? (Roadmap #24)

```python
result = np.sqrt(df6[['score']])
print(type(result), round(result.loc[100, 'score'], 2))
```
A. `<class 'numpy.ndarray'> 9.38` — passing a DataFrame into a NumPy ufunc always converts it to a plain array first, so the index and column labels are discarded
B. `<class 'pandas.DataFrame'> 9.38` — pandas implements NumPy's ufunc protocol, so `np.sqrt` applies element-wise and hands back a DataFrame with the same shape, index, and columns intact
C. Raises a `TypeError`, because `np.sqrt` only accepts NumPy arrays — `df6[['score']].to_numpy()` would be required first
D. `<class 'pandas.DataFrame'> 88.0` — `np.sqrt` on a DataFrame is a no-op pass-through, because pandas objects don't support ufunc dispatch, so the original values come back unchanged

## Q4. Spot the bug: Frank extracts `df6['score']` to a NumPy array and tries to "fix" one value directly on the array. What actually happens? (Roadmap #24)

```python
arr4 = df6['score'].to_numpy()
arr4[0] = 999
```
A. `df6['score'].iloc[0]` becomes `999` — the default `copy=False` hands back the same memory `df6` already uses, so the array is fully writable and the edit passes straight through to the DataFrame
B. Raises `ValueError: assignment destination is read-only` — the default `copy=False` doesn't force a copy, so `arr4` can share memory with `df6`'s own block, but pandas marks that shared array **non-writable** so an in-place edit can't silently corrupt the DataFrame behind its back; `.to_numpy(copy=True)` would hand back a writable, independent copy instead
C. `df6['score'].iloc[0]` stays `88` because `.to_numpy()` with `copy=False` quietly makes an independent copy anyway, so `arr4` was never actually connected to `df6`'s memory
D. Raises a `KeyError`, because `.to_numpy()` detaches the array from its original index entirely, so position `0` isn't a valid assignment target

## Q5. Building on the index-alignment habits from Day 26's MultiIndex lesson, Grace adds two Series built from the *same* data but sorted differently. What does this print? (Roadmap #24)

```python
s_a = df6['score']
s_b = df6['score'].sort_values(ascending=False)
result = np.add(s_a, s_b)
print(type(result), result.tolist())
```
A. `<class 'numpy.ndarray'> [176, 90, 184, 120, 150, 100]` — passing two Series through a raw NumPy function like `np.add` always converts the result to a plain array, discarding both Series' pandas-specific type and index
B. `<class 'pandas.Series'> [180, 133, 167, 120, 125, 95]` — NumPy ufuncs keep the pandas type, but like raw array addition, they combine the two Series position by position, ignoring index labels altogether
C. Raises a `ValueError: cannot reindex on an axis with duplicate labels`, because aligning two Series that contain the same set of labels in different orders requires a one-to-one match pandas can't resolve automatically
D. `<class 'pandas.Series'> [176, 90, 184, 120, 150, 100]` — `np.add` dispatches through pandas' ufunc protocol, which aligns `s_a` and `s_b` by index label (not position) before adding; since `s_b` holds the exact same (index, value) pairs as `s_a`, just reordered, every label's value ends up added to itself, and the result stays a Series

## Answer key

1. **C** — a NumPy array needs one single dtype for every element, so when `.to_numpy()` combines pandas columns of different dtypes (here, `name`'s strings and `score`'s integers), it has to upcast everything to a common type; the only type general enough to hold both strings and numbers is Python `object`, so `arr.dtype` prints `object`. A is wrong — `.to_numpy()` on a DataFrame returns a plain 2-D array, not a structured/record array with per-column fields (that's a different NumPy feature entirely). B is wrong — `.to_numpy()` happily mixes dtypes by falling back to `object`; it doesn't refuse. D is wrong — no columns get silently dropped; `object`-dtype conversion is how *all* of the selected columns' data survives in one array.
2. **D** — `.to_numpy()` on a categorical Series materializes the real label for every row by looking up each row's code against `.cat.categories`, handing back ordinary string values in the Series' original row order — the categorical dtype is gone once you leave pandas. A confuses this with `.cat.codes.to_numpy()`, which *does* return the raw integer codes — but plain `.to_numpy()` resolves them back to labels. B is wrong — that's deduplication, which is what `.cat.categories` gives you, not what extracting the full column's values does. C is wrong — `.to_numpy()` is defined on every Series regardless of dtype, categorical included.
3. **B** — pandas DataFrames implement NumPy's `__array_ufunc__` protocol, so calling a ufunc like `np.sqrt` on a DataFrame dispatches back into pandas: it applies element-wise and returns a new DataFrame with the same index and columns, rather than falling back to plain array math. `sqrt(88) ≈ 9.38`, matching Alice's row. A is wrong — ufunc dispatch is exactly what *avoids* that conversion; the pandas type and labels are preserved. C is wrong — `np.sqrt` works directly on DataFrames and Series precisely because of that protocol; no manual `.to_numpy()` step is required. D is wrong — `np.sqrt` genuinely computes the square root; it isn't a pass-through, so the value changes from `88.0` to roughly `9.38`.
4. **B** — `.to_numpy()`'s default `copy=False` means pandas is *allowed* to hand back an array backed by the same memory `df6` already owns rather than making a redundant copy — but to prevent exactly the kind of silent corruption this question demonstrates, pandas marks that shared, no-copy array as non-writable. Trying `arr4[0] = 999` then raises `ValueError: assignment destination is read-only`; getting a writable array back requires asking for one explicitly with `.to_numpy(copy=True)`. A wrongly assumes the shared array is writable — it's deliberately locked precisely because it's shared. C is wrong about the mechanism — `copy=False` doesn't mean "always copies"; it means "copy only if necessary," and here no copy was needed, so the data stayed shared (just read-only). D invents an index-related failure that isn't what happens; the actual error is about write permission on the array, not an invalid position.
5. **D** — like regular pandas arithmetic operators, `np.add` dispatches to pandas' ufunc protocol when given two Series, which aligns them by index label before combining values — not by their physical row order. Since `s_b` is just `s_a`'s own values resorted (every index label still maps to the exact same score it always had), aligning by label and adding means each label's value gets added to itself: `88+88=176`, `45+45=90`, `92+92=184`, `60+60=120`, `75+75=150`, `50+50=100`, and the result keeps its Series type. A gets the right numbers but the wrong type claim — ufunc dispatch on two Series keeps the pandas type; it doesn't degrade to a bare array. B gets the right type but wrong numbers — that's what you'd get by ignoring index labels and just zipping the two Series' physical storage order together position-by-position, which is not how pandas (or NumPy's dispatch into pandas) actually behaves here. C invents a duplicate-label failure that doesn't apply — both `s_a` and `s_b` have six distinct labels (`100`-`105`), just in different orders; alignment on a shared, non-duplicated label set is exactly what pandas is designed to do without error.
