## Q1. Grace revisits Day 1's dtype-promotion lesson, but this time mixes three types in one array instead of two. What does this print? (Roadmap #41, #1)

```python
import numpy as np

scores = np.array([10, True, '20'])
print(scores.dtype)
print(scores.tolist())
```
A. `<U21` then `['10', 'True', '20']` — NumPy's type-promotion hierarchy treats `str` as incompatible with numeric/bool types for any dtype *other* than a unified string dtype, so the whole array is promoted to a fixed-width unicode dtype (`<U21`). Every element is converted to its own `str()` representation: the int `10` becomes `'10'`, the bool `True` becomes `'True'` (not `'1'`), and the string `'20'` is already a string.
B. `object` then `[10, True, '20']` — wrongly assumes NumPy falls back to `dtype=object` (preserving each element's original Python type) whenever it sees genuinely incompatible types, the way it would for something like a list of custom class instances; for built-in int/bool/str mixes, NumPy instead unifies everything into one common string dtype rather than boxing them individually.
C. `<U21` then `['10', '1', '20']` — gets the dtype right but wrongly assumes a bool stringifies the same way it numerically coerces (as `1`/`0`) rather than using Python's actual `str(True)` / `str(False)`, which are `'True'`/`'False'`.
D. `int64` then `[10, 1, 20]` — wrongly assumes the presence of a numeric-looking string like `'20'` gets silently parsed back into a number, as if NumPy tried numeric coercion first; NumPy never parses string contents during array creation, so a literal string anywhere in the input forces the whole array to a string dtype instead.

## Q2. Spot the bug — Grace pastes in a second team's scores but one of the inner lists is short a player. What does this print? (Roadmap #41, #1)

```python
import numpy as np

try:
    scores = np.array([[88, 92, 79], [45, 50]])
    print(scores.shape)
except Exception as e:
    print(type(e).__name__)
```
A. `ValueError` — since NumPy 1.24, constructing an array from nested sequences of inconsistent lengths no longer silently falls back to a 1-D `object` array; it now raises `ValueError` ("inhomogeneous shape") as soon as it detects the row lengths don't match, because a rectangular `(2, 3)` or `(2, 2)` array can't be built from a 3-element row and a 2-element row.
B. `(2,)` — wrongly assumes the old pre-1.24 NumPy behavior still applies today, where a ragged nested list quietly became a 1-D array of two `list` objects (`dtype=object`) instead of raising; that fallback was removed specifically because it was error-prone.
C. `TypeError` — names the wrong exception; a ragged-shape problem in array construction is reported as `ValueError`, not `TypeError`.
D. `(2, 3)` — wrongly assumes NumPy pads the shorter inner list with a filler value (like `0` or `nan`) to force a rectangular shape; NumPy never pads automatically during `np.array()` — it either finds a consistent rectangular shape or raises.

## Q3. Grace checks whether `np.array()` and `np.asarray()` on an already-existing array behave the same way. What does this print? (Roadmap #41, #1)

```python
import numpy as np

raw = np.array([88, 92, 79], dtype=np.int64)
copied = np.array(raw)
shared = np.asarray(raw)

copied[0] = 0
print(raw.tolist(), copied.tolist())

shared[0] = -1
print(raw.tolist(), shared.tolist())
```
A. `[88, 92, 79] [0, 92, 79]` then `[-1, 92, 79] [-1, 92, 79]` — `np.array()` copies its input by default even when the input is already an ndarray of the same dtype, so `copied` is an independent object and mutating it leaves `raw` untouched. `np.asarray()`, by contrast, returns the *same* underlying array object when the requested dtype already matches (no copy needed), so `shared` and `raw` are the same object and mutating `shared` mutates `raw` too.
B. `[0, 92, 79] [0, 92, 79]` then `[-1, 92, 79] [-1, 92, 79]` — wrongly assumes `np.array()` on an existing array skips copying the way `np.asarray()` does, as if the two constructors were interchangeable when the input is already an ndarray; `np.array()`'s default `copy=True` behavior still applies regardless of the input's type.
C. `[88, 92, 79] [0, 92, 79]` then `[88, 92, 79] [-1, 92, 79]` — wrongly assumes `np.asarray()` always copies too, missing that its entire purpose is to avoid an unnecessary copy whenever the input already satisfies the requested dtype/shape.
D. `[88, 92, 79] [0, 92, 79]` then `[-1, 92, 79] [92, 79]` — gets the sharing behavior right but miscounts `shared`'s length after the assignment, as if assigning to `shared[0]` somehow removed an element rather than just overwriting it in place.

## Q4. Building on Q1's dtype theme, Grace writes each team's running total into a narrow `int8` array, first by direct scalar assignment, then by array arithmetic. What does this print? (Roadmap #41, #1)

```python
import numpy as np

totals = np.array([120, 45, 92], dtype=np.int8)

try:
    totals[1] = 200
except OverflowError as e:
    print("OverflowError")

bumped = totals + np.int8(100)
print(bumped.tolist())
```
A. `OverflowError` then `[-36, -111, -64]` — assigning the raw Python integer `200` directly into an `int8` slot fails fast: `int8`'s range is `-128` to `127`, and modern NumPy raises `OverflowError` for an out-of-range Python integer scalar rather than silently wrapping it, so the assignment to `totals[1]` never happens and `totals` stays `[120, 45, 92]`. The later arithmetic `totals + np.int8(100)` is a different code path — elementwise NumPy-dtype arithmetic still wraps silently on overflow using two's-complement semantics: `120+100=220 → 220-256=-36`, `45+100=145 → 145-256=-111`, `92+100=192 → 192-256=-64`.
B. `[120, 26, 92]` then `[-36, -111, -64]` — wrongly assumes the scalar assignment succeeds by silently wrapping `200` into `int8` range (as older NumPy might have for some operations), rather than raising; modern NumPy explicitly checks a raw out-of-range Python int literal against the target dtype's bounds and refuses the unsafe assignment.
C. `OverflowError` then `OverflowError` — wrongly assumes the later `totals + np.int8(100)` arithmetic raises the same way the scalar assignment did; elementwise arithmetic between NumPy-typed values is governed by wraparound (modular) semantics, not the stricter bounds-checking applied to assigning a raw Python integer into an array slot — it never raises here.
D. `OverflowError` then `[184, 145, 192]` — correctly predicts the first exception but forgets `int8` is signed, treating the sums as if they wrapped into an unsigned `0`-`255` range instead of a signed `-128`-`127` one.

## Q5. To close out the dtype theme, Grace contrasts reinterpreting raw bytes with actually casting values. What does this print? (Roadmap #41, #1)

```python
import numpy as np

floats = np.array([1.0, 2.5, -3.75], dtype=np.float32)

reinterpreted = floats.view(np.int32)
cast = floats.astype(np.int32)

print(reinterpreted.tolist())
print(cast.tolist())
```
A. `[1065353216, 1075838976, -1066401792]` then `[1, 2, -3]` — `.view(np.int32)` doesn't touch a single bit of the underlying memory; it just relabels how those same 4-byte chunks are *interpreted*, so each `float32`'s raw IEEE-754 bit pattern gets read back as a (very different-looking) `int32` value. `.astype(np.int32)`, by contrast, actually converts each value numerically, truncating toward zero: `1.0 → 1`, `2.5 → 2`, `-3.75 → -3`.
B. `[1, 2, -3]` then `[1, 2, -3]` — wrongly assumes `.view()` behaves like `.astype()` and converts the numeric *value* of each float into the nearest representable integer, when `.view()` performs no value conversion at all — only a reinterpretation of the raw bytes.
C. `[1065353216, 1075838976, -1066401792]` then `[1065353216, 1075838976, -1066401792]` — wrongly assumes `.astype()` also just reinterprets bytes like `.view()` does, rather than actually converting each value to its integer equivalent.
D. `[1065353216, 1075838976, -1066401792]` then `[1, 3, -4]` — gets `.view()`'s bit-reinterpretation right but wrongly assumes `.astype()` to `int32` rounds to the nearest integer rather than truncating toward zero, which would turn `2.5` into `3` and `-3.75` into `-4` instead of `2` and `-3`.

1. **A** — Mixing an int, a bool, and a string forces the whole array to a unified string dtype (`<U21`); each element becomes its own `str()`: `10 → '10'`, `True → 'True'` (not `'1'`), `'20'` unchanged. B wrongly assumes incompatible types fall back to `dtype=object`. C wrongly assumes bools stringify numerically rather than via Python's actual `str(True)`. D wrongly assumes the numeric-looking string gets parsed back into a number.
2. **A** — Since NumPy 1.24, a ragged nested list (rows of different lengths) raises `ValueError` ("inhomogeneous shape") instead of silently becoming a 1-D `object` array. B revives that removed old-NumPy fallback behavior. C names the wrong exception type. D wrongly assumes automatic padding, which `np.array()` never does.
3. **A** — `np.array()` always copies by default, even from an existing same-dtype ndarray, so `copied` is independent and `raw` stays `[88, 92, 79]` after `copied[0] = 0`. `np.asarray()` returns the *same* object when no copy is needed, so `shared` IS `raw`, and mutating `shared` changes `raw` too. B wrongly assumes `np.array()` skips copying like `np.asarray()`. C wrongly assumes `np.asarray()` always copies, defeating its purpose. D gets the sharing right but miscounts the list length after an in-place scalar overwrite.
4. **A** — Assigning the out-of-range Python int `200` directly into an `int8` array slot raises `OverflowError` under modern NumPy's stricter bounds-checking, leaving `totals` unchanged; this is unrelated to elementwise array arithmetic (`totals + np.int8(100)`), which still wraps silently via two's-complement modular arithmetic, giving `[-36, -111, -64]`. B wrongly assumes the scalar assignment wraps instead of raising. C wrongly assumes the arithmetic raises the same way the assignment did. D gets the exception right but computes the wraparound as if `int8` were unsigned.
5. **A** — `.view(np.int32)` reinterprets the same underlying bytes as a different dtype with no value conversion, surfacing each `float32`'s raw bit pattern as an `int32`. `.astype(np.int32)` genuinely converts each value, truncating toward zero (`1.0→1`, `2.5→2`, `-3.75→-3`).
