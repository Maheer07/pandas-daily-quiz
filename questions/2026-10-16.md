## Q1. Building on the recurring `df6`, Grace pivots a two-key groupby result and pulls it out as a raw array. What does this print? (Roadmap #21, #24)

```python
import pandas as pd
import numpy as np

data6 = {'name': ['Alice', 'Bob', 'Carol', 'Dave', 'Eve', 'Frank'],
         'team': ['Red', 'Blue', 'Red', 'Blue', 'Red', 'Blue'],
         'region': ['North', 'South', 'North', 'North', 'South', 'South'],
         'score': [88, 45, 92, 60, 75, 50]}
df6 = pd.DataFrame(data6, index=[100, 101, 102, 103, 104, 105])

s = df6.groupby(['team', 'region'])['score'].mean()
arr = s.unstack('region').to_numpy()
print(arr.tolist())
print(arr.dtype)
```
A. `[[60.0, 47.5], [90.0, 75.0]]` then `float64` — `.unstack('region')` pivots the inner `region` level into columns, turning the 2-level `MultiIndex` Series into a 2×2 `DataFrame` (rows sorted `Blue`, `Red`; columns `North`, `South`) of means, and `.to_numpy()` simply drops the row/column labels, keeping the already-numeric `float64` values
B. `[[90.0, 75.0], [60.0, 47.5]]` then `float64` — the rows come out in the order `team` first *appeared* in `df6` (`Red` before `Blue`), since `.unstack()` preserves original appearance order rather than sorting
C. Raises a `ValueError`, because the unstacked `DataFrame`'s columns still carry a `columns.name` of `'region'`, and `.to_numpy()` refuses to strip a named axis without an explicit `.rename_axis(columns=None)` first
D. `[[60.0, 47.5], [90.0, 75.0]]` then `object` — `.to_numpy()` always falls back to `object` dtype whenever the source `DataFrame`'s axes (rows or columns) carry names, to avoid silently losing that label metadata

## Q2. Building on Day 28's categorical `team` column and Day 27's rolling lesson, Grace computes a 2-game rolling average per team. What does this print? (Roadmap #22, #23)

```python
df6['team'] = df6['team'].astype('category')
result = df6.groupby('team')['score'].rolling(2).mean()
print(result.tolist())
```
A. `[nan, 52.5, 55.0, nan, 90.0, 83.5]` — `groupby('team')` splits the data into its two groups (`Blue`'s rows 101/103/105, then `Red`'s rows 100/102/104, in category order since `team`'s categories sort as `['Blue', 'Red']`) and rolls independently within each, so the result is ordered *by group*, not by `df6`'s original row order
B. `[nan, nan, 90.0, 52.5, 83.5, 55.0]` — the result keeps `df6`'s original row order (100 through 105), with each team's rolling window just computed in place alongside the other team's rows
C. Raises a `TypeError`, because `.rolling()` can't be chained after a `groupby()` on a categorical column — only plain `object`-dtype grouping keys support windowed aggregations
D. `[nan, 66.5, 68.5, 76.0, 67.5, 62.5]` — grouping by `team` first doesn't actually change anything here, since `.rolling(2)` rolls over the full 6-row sequence regardless of which column was grouped on

## Q3. Spot the bug: building on Day 29's ufunc lesson, Grace applies the same kind of NumPy ufunc call to a two-column slice that now includes the categorical `team` column. What actually happens? (Roadmap #23, #24)

```python
df6['team'] = df6['team'].astype('category')
result = np.sqrt(df6[['score', 'team']])
```
A. Raises `TypeError: Object with dtype category cannot perform the numpy op sqrt` — pandas' ufunc protocol still needs every column to support the underlying numeric operation; unlike Day 29's all-numeric `df6[['score']]`, a categorical column has no square root defined, so the whole call fails even though `score` alone would work fine
B. Returns a `DataFrame` with `score` square-rooted and `team` left completely unchanged, because pandas silently skips any column a ufunc can't apply to
C. Returns a `DataFrame` where `team` is also "square-rooted" by applying `np.sqrt` to its underlying integer category codes, then re-mapping the result back to the nearest valid category label
D. Returns a plain `numpy.ndarray` of `object` dtype, because including a non-numeric column forces `np.sqrt` to fall back to element-by-element Python-level evaluation instead of dispatching through pandas' ufunc protocol

## Q4. Spot the bug: Grace assumes putting `team`/`region` into the index will make `.rolling()` restart per team, the way `.groupby('team').rolling()` did in Q2. What does this actually print? (Roadmap #21, #22)

```python
df6_idx = df6.set_index(['team', 'region'])
result4 = df6_idx['score'].rolling(2).mean()
print(result4.tolist())
```
A. `[nan, 66.5, 68.5, 76.0, 67.5, 62.5]` — `.rolling()` has no idea two of the index levels happen to be `team`/`region`; it just slides a window over the Series' physical row order top to bottom, exactly as it would on any plain `RangeIndex`. There's no implicit per-team restart — that behavior only exists when you explicitly call `.groupby('team')` first, as in Q2
B. `[nan, 52.5, 55.0, nan, 90.0, 83.5]` — same grouped result as Q2, because `set_index(['team', 'region'])` makes `.rolling()` automatically restart its window whenever the outer `team` level changes
C. Raises a `TypeError`, because `.rolling()` cannot be computed on a `Series` whose index is a `MultiIndex`
D. `[66.5, 68.5, 76.0, 67.5, 62.5, nan]` — the same ungrouped values as A, but with the `NaN` at the *end* instead of the start, because `.rolling()` defaults to a forward-looking window that needs a future value rather than a past one

## Q5. Building on Q2's categorical-grouped rolling, what are the resulting `MultiIndex`'s level names, in order? (Roadmap #21, #22, #23)

```python
df6['team'] = df6['team'].astype('category')
grouped = df6.groupby(['team', 'region'])['score']
rolled = grouped.rolling(2).mean()
print(rolled.index.names)
```
A. `['team', 'region', None]` — the two groupby keys keep their original column names as the outer two levels (needed since `.rolling()` must return one row per original record, not one row per group), and the third, innermost level is just `df6`'s own row index — which was never given a name, so it shows up as `None`
B. `['team', 'region']` — `.rolling()` after a two-key `groupby()` only ever returns a 2-level index, identical to what `.mean()` alone would give, since it's still "grouped by" those same two keys
C. `['team', 'region', 'score']` — the third level takes its name from the Series being aggregated (`'score'`), the same way a value column gets named after a Series in `.reset_index()`
D. Raises a `TypeError`, because `.rolling()` only supports a single-key `groupby()`; grouping by two keys (`['team', 'region']`) before calling `.rolling()` isn't allowed

## Answer key

1. **A** — `.unstack('region')` pivots the inner `region` level of `s`'s 2-level `MultiIndex` into columns, producing a 2×2 `DataFrame` whose rows are the outer `team` level (sorted `Blue` before `Red`, matching `team`'s sorted unique values) and whose columns are `North`/`South`. `.to_numpy()` then just discards those row/column labels, leaving a plain 2-D array of the already-numeric means, so the dtype stays `float64`. B wrongly assumes unstack preserves first-appearance row order — grouping (and the resulting unstack) sorts by the outer level's values, not by when they first showed up in `df6`. C invents a label-cleanup requirement that `.to_numpy()` doesn't have — it always strips labels regardless of whether an axis has a name. D wrongly claims named axes force an `object` dtype — `.to_numpy()`'s dtype is decided purely by the data's own dtype(s), never by axis metadata.
2. **A** — `groupby('team')` partitions the Series into its groups first (here, by `team`'s sorted categories, `Blue` then `Red`) and computes the rolling mean independently *within* each group, so the combined result is ordered group-by-group — `Blue`'s three rows (101, 103, 105) come first, then `Red`'s (100, 102, 104) — not interleaved back into `df6`'s original 100–105 row order. B wrongly assumes the grouped result gets reordered to match the original frame — it doesn't; `groupby()` output is ordered by group. C is wrong — `.rolling()` works the same after grouping on a categorical column as on any other dtype; categorical grouping keys are fully supported. D is wrong — grouping absolutely changes the computation; D's values are what you'd get from rolling over the *whole* ungrouped sequence (see Q4), not per-team.
3. **A** — pandas dispatches a NumPy ufunc call on a `DataFrame` through its `__array_ufunc__` protocol, but that still requires every column to support the operation; `np.sqrt` has no defined meaning for a `category`-dtype column, so the call raises `TypeError: Object with dtype category cannot perform the numpy op sqrt` for the whole call — even though `score` alone is perfectly fine (as Day 29 Q3 showed). B invents a silent-skip behavior that pandas' ufunc dispatch doesn't have — it fails loudly rather than partially applying. C invents an auto-remapping-through-codes behavior that doesn't exist for ufuncs on categorical data. D is wrong — the call doesn't fall back to element-by-element `object`-array evaluation; it raises before producing any result at all.
4. **A** — `.rolling()` is purely positional: it slides its window over a Series' rows in physical order, with no awareness of what the index levels are named or what values they hold. Setting `team`/`region` as the index via `set_index()` changes only how rows are *labeled*, not their physical order or any grouping behavior — so the output is identical to calling `.rolling(2).mean()` on plain `df6['score']` with its original `RangeIndex`-like integer index. B wrongly imports Q2's explicit `.groupby('team')` behavior into this code, which never calls `.groupby()` at all — a `MultiIndex` alone never triggers automatic per-level grouping. C is wrong — `.rolling()` works fine on a `MultiIndex`-indexed Series; it simply ignores the index's structure. D is wrong about the direction — `.rolling()`'s default window looks *backward* (the current row plus prior rows), which is exactly why the first row, lacking any prior value, is `NaN`; there's no forward-looking default.
5. **A** — grouping by two keys and then calling `.rolling()` can't collapse down to one row per group the way `.mean()` does, because a rolling window needs to preserve every individual row's position within its group; pandas does this by keeping `team` and `region` (the two groupby keys, each retaining its original column name) as the outer two `MultiIndex` levels, and adding `df6`'s own row index back as a third, innermost level — which prints as `None` because that row index itself was never given a name. B is wrong — a 2-level index couldn't disambiguate multiple rows per group, which `.rolling()` requires; it's specifically a 3-level result. C wrongly imports the `reset_index()` behavior (where a value column is named after the Series) into level-*naming* here — that third level is `df6`'s row index, not a value column, and has nothing to do with the Series' own name (`'score'`). D is wrong — `.rolling()` works fine after a multi-key `groupby()`; there's no restriction to single-key grouping.
