## Q1. Spot the bug: building on the recurring `df6`, Grace tries to negate a team comparison in one line. What actually happens? (Roadmap #28, #9)

```python
import pandas as pd

data6 = {'name': ['Alice', 'Bob', 'Carol', 'Dave', 'Eve', 'Frank'],
         'team': ['Red', 'Blue', 'Red', 'Blue', 'Red', 'Blue'],
         'region': ['North', 'South', 'North', 'North', 'South', 'South'],
         'score': [88, 45, 92, 60, 75, 50]}
df6 = pd.DataFrame(data6, index=[100, 101, 102, 103, 104, 105])

mask1 = ~df6['team'] == 'Red'
print(df6[mask1])
```
A. Raises a `TypeError`, because unary `~` binds tighter than `==`, so this is parsed as `(~df6['team']) == 'Red'`; `~` is bitwise invert, and inverting a column of plain Python strings has no defined meaning, so the error fires before `== 'Red'` ever runs
B. Returns the three Blue-team rows (Bob, Dave, Frank) — treats `~` as if it distributes over the whole comparison, negating `team == 'Red'` as a single unit
C. Returns the three Red-team rows (Alice, Carol, Eve) — treats the double negative of `~` and `==` as cancelling out, leaving the original `team == 'Red'` condition
D. Returns an empty `DataFrame` — assumes `mask1` evaluates to `False` for every row

## Q2. Building on Q1's precedence bug, Grace fixes it by adding parentheses. What does this print? (Roadmap #28, #9)

```python
mask2 = ~(df6['team'] == 'Red')
print(df6.loc[mask2, 'name'].tolist())
```
A. `['Bob', 'Dave', 'Frank']` — the parentheses force `team == 'Red'` to fully evaluate into a plain boolean Series first, and only then does `~` invert it elementwise, keeping exactly the Blue-team rows
B. `['Alice', 'Carol', 'Eve']` — assumes `~` has no real effect here, so the result is the same as `team == 'Red'` on its own
C. Raises the same `TypeError` as Q1 — assumes wrapping the comparison in parentheses doesn't change evaluation order, when forcing the comparison to run before `~` is applied is exactly what the parentheses accomplish
D. `['Bob', 'Dave', 'Frank']`, but also raises a `FutureWarning` about chained indexing — invents a warning that doesn't actually fire for this plain `.loc` boolean-mask lookup

## Q3. Grace filters `df6` using `.query()` with an external variable. What does this print? (Roadmap #28)

```python
threshold = 60
result3 = df6.query('score >= @threshold and team == "Red"')
print(result3['name'].tolist())
```
A. `['Alice', 'Carol', 'Eve']` — the `@` prefix lets the query string reach outside itself and read the local Python variable `threshold` (60), and `and` combines both conditions as a logical AND, matching exactly the three Red-team rows whose score is at least 60
B. Raises a `NameError: name 'threshold' is not defined` — mistakenly treats `@` as syntax for escaping reserved keywords or special characters in a column name (the way backticks are used), rather than its real purpose of referencing an outside variable
C. `['Alice', 'Carol', 'Dave', 'Eve']` — mistakenly treats the `and` inside the query string as combining the two conditions with OR semantics, taking the union of "score >= 60" and "team == 'Red'" instead of their intersection
D. Raises a `SyntaxError`, because mixing single quotes (around the whole query string) with double quotes (around the `"Red"` literal inside it) isn't allowed — nested quote types of different kinds inside a `.query()` string are perfectly valid Python and pandas syntax

## Q4. Building on Q3, Grace uses `.query()`'s `in` keyword as a membership test. What does this print? (Roadmap #28)

```python
subset4 = df6.query('region in ["North", "South"] and team != "Blue"')
print(len(subset4))
```
A. `3` — `region in [...]` matches every row, since `region` is always `"North"` or `"South"`; `team != "Blue"` then narrows that down to the three Red-team rows (Alice, Carol, Eve)
B. `6` — wrongly assumes `.query()` only evaluates the first clause of an `and`-joined expression and silently ignores everything after it
C. Raises a `SyntaxError`, because `.query()` doesn't support the `in` keyword for membership tests — only calling `.isin()` directly on a Series supports that; in reality `.query()`'s `in`/`not in` are documented equivalents of `.isin()`
D. `0` — treats `!=` inside a `.query()` string as unsupported syntax that silently makes the whole combined mask evaluate to `False` for every row

## Q5. Building on Day 32/33's groupby chains, Grace wants each non-Blue team's mean score using boolean indexing (not `.query()` this time). Which line is correct? (Roadmap #28, #13, #26)

A. `df6[~df6['team'].isin(['Blue'])].groupby('team')['score'].mean()` — correct: `~` negates the Blue-membership mask, keeping only the Red rows, whose mean is `(88+92+75)/3 = 85.0`
B. `df6[df6['team'].isin(['Blue'])].groupby('team')['score'].mean()` — drops the `~`, so it keeps Blue instead of excluding it, giving Blue's mean `(45+60+50)/3 ≈ 51.67` instead of Red's
C. `df6[~df6['team'] != 'Blue'].groupby('team')['score'].mean()` — the same operator-precedence bug as Q1: `~` binds to `df6['team']` before `!=` runs, so this raises a `TypeError` rather than computing anything
D. `df6[df6['team'].isin('Blue')].groupby('team')['score'].mean()` — passes the bare string `'Blue'` instead of a list; `.isin()` explicitly rejects non-list-like arguments (even though a string is technically iterable) and raises `TypeError: only list-like objects are allowed to be passed to isin()`, rather than silently iterating over its characters

## Answer key

1. **A** — Unary `~` binds more tightly than `==`, so `~df6['team'] == 'Red'` parses as `(~df6['team']) == 'Red'`. Pandas tries to compute `~df6['team']` first — a bitwise invert applied elementwise to a column of plain strings — which has no defined meaning and raises `TypeError` before the `== 'Red'` comparison ever happens. B wrongly assumes `~` somehow distributes over the entire comparison as if it were written `~(df6['team'] == 'Red')`; that's not how Python parses the expression. C invents a "double negative cancels out" rule that has no basis — there's no second negation present to cancel anything. D wrongly assumes the expression silently evaluates to all-`False` rather than raising; it never gets that far.
2. **A** — Wrapping the comparison in parentheses, `~(df6['team'] == 'Red')`, forces `team == 'Red'` to fully evaluate into a clean boolean Series first (`True` for Alice/Carol/Eve, `False` for Bob/Dave/Frank); `~` then flips every value, leaving `True` for exactly the Blue-team rows, so `.loc` returns `['Bob', 'Dave', 'Frank']`. B wrongly assumes `~` did nothing, reproducing `team == 'Red'`'s own result instead of its negation. C is wrong — the whole point of adding parentheses is to change which operation runs first, and it does: the comparison now happens before `~` is applied, avoiding Q1's bug entirely. D invents a `FutureWarning` that has no basis here; this is plain `.loc` boolean-mask indexing with no chained-assignment ambiguity to warn about.
3. **A** — The `@` prefix is exactly how `.query()` reaches outside the query string to read a local Python variable, so `@threshold` resolves to `60`; combined with `and`, the expression keeps rows where `score >= 60` **and** `team == "Red"` — Alice (88), Carol (92), and Eve (75), since Dave's 60 belongs to `team == "Blue"`. B misunderstands what `@` is for — it's the mechanism for referencing external variables, not a keyword-escaping syntax, so no `NameError` occurs. C wrongly treats the query's `and` as a union (OR) of the two conditions rather than their intersection (AND), which would incorrectly also admit Dave. D is a myth — Python freely allows a single-quoted string to contain double-quoted text (and vice versa) as a literal, and pandas' query parser accepts it the same way.
4. **A** — `region in ["North", "South"]` is `True` for every row since `region` only ever holds those two values; ANDing that with `team != "Blue"` narrows the result down to the three Red-team rows (Alice, Carol, Eve), so `len(subset4)` is `3`. B invents a short-circuit-and-ignore behavior that `.query()`'s `and` doesn't have — both clauses are always evaluated and combined. C is a myth — `.query()` explicitly documents `in`/`not in` as membership tests equivalent to calling `.isin()`, no `SyntaxError` results. D wrongly assumes `!=` isn't valid inside a query string; it's one of the most basic supported comparison operators there.
5. **A** — `~df6['team'].isin(['Blue'])` inverts the Blue-membership mask, keeping only the three Red rows (Alice 88, Carol 92, Eve 75), whose mean is `255/3 = 85.0`. B omits the `~`, so it keeps Blue's rows instead of excluding them, giving Blue's mean (`≈51.67`) rather than Red's. C repeats Q1's exact precedence bug — `~df6['team']` is evaluated (and raises `TypeError`) before `!= 'Blue'` ever gets a chance to run. D passes `.isin()` the bare string `'Blue'` rather than a one-item list; even though a string is technically iterable, pandas explicitly guards against this common mistake and raises `TypeError: only list-like objects are allowed to be passed to isin()` rather than quietly matching individual characters.
