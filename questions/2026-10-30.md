## Q1. Building on Day 38's dedup pattern and Day 36's merge validation, Grace appends two rows of the recurring `df6` back onto itself, cleans up with a plain `drop_duplicates()`, then validates a merge. What does this print? (Roadmap #31, #29)

```python
import pandas as pd

data6 = {'name': ['Alice', 'Bob', 'Carol', 'Dave', 'Eve', 'Frank'],
         'team': ['Red', 'Blue', 'Red', 'Blue', 'Red', 'Blue'],
         'region': ['North', 'South', 'North', 'North', 'South', 'South'],
         'score': [88, 45, 92, 60, 75, 50]}
df6 = pd.DataFrame(data6, index=[100, 101, 102, 103, 104, 105])

team_info = pd.DataFrame({'team': ['Red', 'Green'], 'manager': ['Pat', 'Sam']})

dupes = pd.concat([df6, df6.loc[[101, 103]]], ignore_index=True)
clean = dupes.drop_duplicates()
print(len(clean))

try:
    clean.merge(team_info, on='team', validate='one_to_many')
except Exception as e:
    print(type(e).__name__)
```
A. `8` then `MergeError` — wrongly assumes `drop_duplicates()` needs an explicit `subset=` or `keep=` argument to do anything at all, so `dupes` stays at its full 8 rows; the merge still correctly fails validation since `team` was never unique regardless of row count
B. `6` then `KeyError` — gets the row count right but wrongly assumes merge-cardinality violations surface as a column-lookup failure rather than through pandas' own dedicated validation exception (the same mix-up Day 36 Q3 ruled out)
C. `6` then `MergeError` — `drop_duplicates()`'s default (comparing every column, no `subset`) only removes rows that are *exact* full-row repeats; the two rows appended from Bob (101) and Dave (103) exactly match earlier rows and get dropped, shrinking `dupes` from 8 back to the original 6 — but `clean['team']` still repeats each value three times (`Red`×3, `Blue`×3), since none of the *original* six rows were duplicates of each other. `validate='one_to_many'` requires the *left* key to be unique, which it never was, so pandas raises `MergeError` regardless of the dedup step
D. `6` then nothing is printed (no exception) — wrongly assumes `'one_to_many'` checks the *right*-hand frame's uniqueness the way `'many_to_one'` does, and since `team_info['team']` has no duplicates, concludes the check passes

## Q2. Grace precomputes each person's team average with `transform()`, then runs an outer merge with `indicator=True` to see what happens to that already-computed column for a team that doesn't exist in `df6` at all. What does this print? (Roadmap #30, #29)

```python
df6['team_mean'] = df6.groupby('team')['score'].transform('mean')
merged = df6.merge(team_info, on='team', how='outer', indicator=True)
print(merged.loc[merged['team'] == 'Green', ['name', 'team_mean', 'manager']].to_dict('records'))
print(merged['team_mean'].isna().sum())
```
A. `[{'name': nan, 'team_mean': 85.0, 'manager': 'Sam'}]` then `0` — wrongly assumes the new `'Green'` row's `team_mean` falls back to reusing the most-recently-seen group's value rather than coming back `NaN`, when there's no `df6` row behind `'Green'` at all for any original column to inherit from
B. `[{'name': nan, 'team_mean': nan, 'manager': 'Sam'}]` then `1` — `how='outer'` adds a brand-new row for `'Green'` since it exists in `team_info` but not `df6`; that row has no corresponding left-hand data at all, so every `df6`-origin column — including the already-computed `team_mean` — comes back `NaN`, while `manager` (from `team_info`) is `'Sam'`. All 6 original rows keep the real `team_mean` they already had before the merge (matched *and* `'left_only'` alike), so exactly 1 row ends up `NaN`
C. `[{'name': nan, 'team_mean': nan, 'manager': 'Sam'}]` then `4` — gets the `'Green'` row right but wrongly assumes the three unmatched `'left_only'` Blue rows also lose their already-computed `team_mean`, when `'left_only'` only means "no match on the right" — the row's own original columns are untouched
D. `[]` then `0` — wrongly assumes an outer merge can't introduce a wholly new row into a frame that already has a precomputed/derived column, so `'Green'` never appears in `merged` at all

## Q3. Contrasting with Day 39's point about `astype('category')`, Grace stores the team as a *new* categorical column (leaving the original `team` column untouched) and flags who's above their own team's average. What does this print? (Roadmap #32, #30)

```python
df6['team_cat'] = df6['team'].astype('category')
df6['above_team_avg'] = df6.groupby('team_cat')['score'].transform(lambda s: s > s.mean())
print(df6['above_team_avg'].tolist())
print(df6['above_team_avg'].dtype)
```
A. `[False, True, False, False, True, True]` — swaps which team's rows end up `True` vs `False`
B. Raises a `ValueError` about mismatched lengths — wrongly treats the lambda as collapsing to one boolean per *group*, the way `agg()` would, rather than broadcasting back to all 6 rows the way `transform()` guarantees
C. `[True, False, True, True, False, False]` then `category` — wrongly assumes a column derived from grouping on a categorical key must itself inherit `category` dtype, when `transform()`'s own output dtype is just whatever its callable returns
D. `[True, False, True, True, False, False]` then `bool` — grouping by the new `team_cat` column gives identical groups to grouping by `team` itself (both categories, `Red`/`Blue`, are present), so `transform()` still broadcasts each row's own group verdict back correctly: Red's mean is `85.0` (Alice/Carol above, Eve below), Blue's is `51.67` (only Dave above); the result column's dtype is simply whatever the lambda returns (`bool`), entirely independent of `team_cat`'s own `category` dtype

## Q4. Building on Day 39's truncated team-percentage column, Grace checks whether that precision loss ever makes two unrelated rows look identical. What does this print? (Roadmap #32, #31)

```python
pct = df6['score'] / df6.groupby('team')['score'].transform('sum') * 100
df6['pct_int'] = pct.astype(int)
print(df6['pct_int'].tolist())
print(df6.duplicated(subset=['pct_int']).tolist())
```
A. `[34, 29, 36, 38, 29, 32]` then `[False, False, False, False, True, False]` — `astype(int)` truncates each team-relative percentage from Day 39's exact values, discarding the decimals; Bob's truncated `29` (Blue, from `29.03`) and Eve's truncated `29` (Red, from `29.41`) become identical once only the integer part is kept, and since `subset=['pct_int']` compares *only* that column — ignoring `team` entirely — `duplicated()`'s default `keep='first'` leaves Bob's earlier occurrence (index 1) `False` and flags Eve's later one (index 4) as the duplicate
B. `[34, 29, 36, 38, 29, 32]` then `[False, False, False, False, False, False]` — wrongly assumes `duplicated()` still implicitly considers `team` even though `subset` restricts comparison strictly to `pct_int`, concluding Bob and Eve don't count as duplicates since they're on different teams
C. `[35, 29, 36, 39, 29, 32]` then `[False, False, False, False, True, False]` — gets the duplicate flags right but wrongly assumes `astype(int)` rounds to the nearest whole number rather than truncating toward zero, the same rounding-vs-truncation mix-up Day 39 Q3 flagged
D. `[34, 29, 36, 38, 29, 32]` then `[False, True, False, False, False, False]` — gets the values right but flips which occurrence counts as the duplicate; the default `keep='first'` always leaves the *earliest* occurrence (Bob, index 1) `False` and flags the later repeat (Eve, index 4) instead

## Q5. Spot the bug: Grace dedupes `df6` by the `(team, region)` composite key, tags `region` as categorical for storage, computes each row's deviation from its own team's mean, then tries to validate a merge. What does this print? (Roadmap #31, #32, #30, #29)

```python
clean2 = df6.drop_duplicates(subset=['team', 'region'], keep='first')
clean2['region'] = clean2['region'].astype('category')
clean2['dev'] = clean2.groupby('team')['score'].transform(lambda s: s - s.mean())

try:
    result = clean2.merge(team_info, on='team', validate='one_to_one')
    print(len(result))
except Exception as e:
    print(type(e).__name__)

print(clean2['dev'].tolist())
```
A. `2` then `[6.5, -7.5, 7.5, -6.5]` — wrongly assumes deduping by the `(team, region)` composite key also guarantees the plain `team` column becomes unique, so `validate='one_to_one'` passes without error; under that mistaken assumption the inner-join default would keep only the two `Red` rows that match `team_info` (Alice, Eve), giving `len(result) == 2`
B. `MergeError` then `[6.5, -7.5, 7.5, -6.5]` — dropping duplicates on the `(team, region)` pair only removes rows that repeat that *exact combination* (Carol and Frank here), leaving `clean2` with `team` still duplicated — `Red` for both Alice and Eve, `Blue` for both Bob and Dave; `validate='one_to_one'` demands uniqueness on both merge keys, so it raises `MergeError` regardless of that earlier dedup step. None of this touches `dev`, already computed beforehand from each row's deviation within `clean2`'s own two groups: Red's mean is `81.5` (Alice `88→6.5`, Eve `75→-6.5`), Blue's is `52.5` (Bob `45→-7.5`, Dave `60→7.5`), printed in `clean2`'s row order `[Alice, Bob, Dave, Eve]`
C. `MergeError` then `[-6.5, 7.5, -7.5, 6.5]` — gets the exception right but swaps the sign of every deviation, as if Red's mean were `52.5` and Blue's were `81.5` instead of the other way around
D. `TypeError` then `[6.5, -7.5, 7.5, -6.5]` — correctly computes `dev` but wrongly assumes merge-cardinality violations surface as a generic `TypeError` rather than pandas' dedicated `MergeError`

## Answer key

1. **C** — `drop_duplicates()` with no `subset` compares every column across the full 8-row frame; the two rows appended from Bob (101) and Dave (103) exactly match earlier rows and get removed, shrinking `dupes` back to 6. But that only removed *exact repeats* — the original six rows were never duplicates of each other, so `clean['team']` still has `Red` and `Blue` each three times. `validate='one_to_many'` requires the *left* key to be unique, which was never true, so pandas raises `MergeError` regardless of the earlier cleanup. A wrongly assumes `drop_duplicates()` without arguments does nothing. B misreports the exception type — pandas uses its own `MergeError`, not `KeyError`. D mixes up `'one_to_many'` with `'many_to_one'`; it's the *left* side's uniqueness that's checked here, not the right's.
2. **B** — `how='outer'` unions both sides, so the unmatched `'Green'` key from `team_info` is added as a brand-new row with every `df6`-origin column — including the pre-computed `team_mean` — set to `NaN`, since there's no left-hand data behind it; `manager` comes through as `'Sam'`. The six original rows (three matched `'both'`, three `'left_only'`) all keep their real, already-computed `team_mean`, so only 1 row total is `NaN`. A invents a fallback to a leftover group value instead of `NaN`. C wrongly extends the `NaN`-ing to `'left_only'` rows, which is only about finding no match on the *right*, not about losing the row's own data. D wrongly assumes a derived column blocks outer merge from adding new rows at all.
3. **D** — Grouping by the new `team_cat` column produces identical groups to grouping by `team` itself, since both categories are present; `transform()` broadcasts each row's own group's boolean verdict back to all 6 rows (Red mean `85.0`: Alice/Carol above, Eve below; Blue mean `≈51.67`: only Dave above), giving `[True, False, True, True, False, False]`. The output dtype is whatever the lambda returns element-wise — plain booleans, so `bool` — regardless of the grouping key's own `category` dtype. A swaps the two teams' results. B wrongly imports `agg()`'s one-row-per-group collapsing behavior into `transform()`, which is specifically designed to avoid that mismatch. C wrongly assumes a derived column inherits its grouping key's dtype rather than being determined by what the callable itself returns.
4. **A** — the true team-relative percentages from Day 39 (`34.51, 29.03, 36.08, 38.71, 29.41, 32.26`) get truncated toward zero by `astype(int)` to `[34, 29, 36, 38, 29, 32]`. Because `subset=['pct_int']` only compares that one column, Bob's `29` (Blue) and Eve's `29` (Red) — unrelated rows on different teams that only coincide after the decimals are dropped — count as duplicates; `keep='first'` leaves Bob's earlier occurrence `False` and flags Eve's later one `True`. B wrongly smuggles `team` back into a comparison that `subset` deliberately restricts to `pct_int` alone. C reintroduces the rounding-vs-truncation mix-up Day 39 already called out — `astype(int)` truncates, it doesn't round. D gets the right rows flagged but swaps which occurrence `keep='first'` exempts.
5. **B** — Deduping on `(team, region)` only drops rows that repeat that exact pair (Carol duplicates Alice's `(Red, North)`; Frank duplicates Bob's `(Blue, South)`), leaving `clean2` with 4 rows where `team` is still duplicated — `Red` for Alice and Eve, `Blue` for Bob and Dave. `validate='one_to_one'` requires uniqueness on *both* keys, so it raises `MergeError` no matter what the earlier subset-based dedup achieved. The `dev` column was already fully computed before that failed merge attempt, from each row's deviation within `clean2`'s own two groups (Red mean `81.5`, Blue mean `52.5`), giving `[6.5, -7.5, 7.5, -6.5]` in `clean2`'s original row order. A wrongly assumes composite-key dedup also guarantees single-column uniqueness. C keeps the right exception but swaps the two teams' means. D misreports the exception type, same confusion as Q1's distractor B.
