## Q1. Returning to Day 53-55's two-team score grid, Grace pulls out the high scores with a boolean mask, tweaks the pulled-out copy, then tries writing through the mask directly. What does this print? (Roadmap #45, #42)

```python
import numpy as np

grid = np.array([[88, 92, 79], [45, 50, 60]])
mask = grid > 60

high = grid[mask]
high[0] = -1
print(grid.tolist())

grid[mask] = 0
print(grid.tolist())
```
A. `[[88, 92, 79], [45, 50, 60]]` then `[[0, 0, 0], [45, 50, 60]]` — Indexing with a boolean mask to *read* (`grid[mask]`) always returns an independent copy, same family of rule as Day 52's fancy-indexing lesson — so mutating `high[0]` never touches `grid`, which prints unchanged. Boolean-mask *assignment* (`grid[mask] = 0`) is a different operation: it writes `0` into every position the mask marks `True` directly inside `grid`'s own memory, zeroing out the three values that were originally over `60` (`88, 92, 79`) while leaving the untouched row (`45, 50, 60`) alone.
B. `[[-1, 92, 79], [45, 50, 60]]` then `[[0, 0, 0], [45, 50, 60]]` — wrongly assumes `grid[mask]` returns a view sharing memory with `grid`, so mutating `high[0]` propagates back; boolean indexing to read always copies, exactly like fancy indexing, never like a basic slice.
C. `[[88, 92, 79], [45, 50, 60]]` then `[[0, 0, 79], [45, 50, 0]]` — correctly keeps the first print unchanged but recomputes `mask` against the *mutated* `high` array for the second line, as if `grid[mask] = 0` only zeroed the first and last flagged positions; `mask` was already a fixed boolean array computed once from the original `grid`, and all three `True` positions get zeroed.
D. `[[88, 92, 79], [45, 50, 60]]` then `[[88, 92, 79], [45, 50, 60]]` — wrongly assumes boolean-mask *assignment* also leaves `grid` untouched, as if every operation involving a boolean mask were read-only; assigning through `grid[mask]` is explicitly a write that mutates `grid` in place, unlike reading `grid[mask]` into a new array.

## Q2. Building on Q1, Grace uses `np.where` instead of mask-assignment to flag the low scores, but mixes up which argument goes where. What does this print? (Roadmap #45)

```python
import numpy as np

grid = np.array([[88, 92, 79], [45, 50, 60]])

result = np.where(grid > 60, -1, grid)
print(result.tolist())
```
A. `[[-1, -1, -1], [45, 50, 60]]` — `np.where(condition, x, y)` fills each position with `x` where `condition` is `True` and `y` where it's `False`. Here the condition `grid > 60` is `True` for the first row (`88, 92, 79`), so those positions take the second argument, `-1`; the second row (`45, 50, 60`) is all `False`, so those positions keep their original values from the third argument, `grid` — the exact opposite of what Q1's `grid[mask] = 0` zeroed.
B. `[[45, 50, 60], [-1, -1, -1]]` — wrongly swaps which row ends up as `-1`, as if `grid > 60` evaluated `True` for the *second* row instead of the first; `88`, `92`, and `79` are each greater than `60`, and `45`, `50`, `60` are not (`60` is not strictly greater than `60`), so it's the first row that satisfies the condition.
C. `[[88, 92, 79], [-1, -1, -1]]` — wrongly assumes `np.where`'s argument order is `(condition, value_if_false, value_if_true)`, placing `-1` on the `False` row and the original values on the `True` row; the second positional argument is always the `True`-branch value and the third is always the `False`-branch value.
D. `[[-1, -1, -1], [-1, -1, -1]]` — wrongly assumes `grid` is ignored entirely once any `-1` is involved, as if `np.where` replaced the whole array rather than selecting elementwise between its two branches based on `condition`.

## Q3. Contrasting with Day 52's row-vs-column view/copy question, Grace masks the Q1 grid two different ways — once with an elementwise condition, once with a per-row flag — and checks what shape each result comes back in. What does this print? (Roadmap #45, #41)

```python
import numpy as np

grid = np.array([[88, 92, 79], [45, 50, 60]])

elementwise_mask = grid > 60
by_value = grid[elementwise_mask]
print(by_value.shape, by_value.tolist())

row_mask = np.array([True, False])
by_row = grid[row_mask]
print(by_row.shape, by_row.tolist())
```
A. `(3,) [88, 92, 79]` then `(1, 3) [[88, 92, 79]]` — a boolean mask with the *same shape as the array it indexes* (here `(2, 3)`, matching `grid` exactly) always collapses the result down to a flat 1-D array of just the `True` elements, in row-major order — there's no way to keep 2-D structure when every individual cell can independently be `True` or `False`. A boolean mask shaped like just *one axis* (here `(2,)`, one flag per row) instead selects whole rows and keeps the array 2-D — picking only row `0` here produces shape `(1, 3)`, a single-row 2-D array, not a flattened 1-D one.
B. `(2, 3) [[88, 92, 79], [0, 0, 0]]` — wrongly assumes an elementwise boolean mask preserves the original 2-D shape and zero-fills the `False` positions, the way `np.where` would; plain boolean-mask *indexing* (not assignment) always returns only the `True` elements packed into a new, shorter array — it never keeps the original shape or inserts filler values.
C. `(3,) [88, 92, 79]` then `(2,) [88, 45]` — gets the elementwise case right but wrongly assumes a per-row mask also flattens down to one value per row (as if picking a "representative" element), when selecting whole rows with a `(2,)` mask keeps every column of each selected row intact, giving shape `(1, 3)`, not `(2,)`.
D. `(2, 3) [[True, True, True], [False, False, False]]` then `(1, 3) [[88, 92, 79]]` — correctly handles the row-mask case but wrongly prints the boolean mask itself in place of `grid[elementwise_mask]`, as if indexing with a mask returned the mask unchanged instead of the array values it selects.

## Q4. Still building on Q1's grid, Grace tries to combine two conditions into one mask the way she's done before, but drops a pair of parentheses this time. What does this print? (Roadmap #45)

```python
import numpy as np

grid = np.array([[88, 92, 79], [45, 50, 60]])

try:
    sweet_spot = grid > 50 & grid < 90
    print(sweet_spot.tolist())
except ValueError as e:
    print("ValueError")

sweet_spot_fixed = (grid > 50) & (grid < 90)
print(sweet_spot_fixed.tolist())
print(grid[sweet_spot_fixed].tolist())
```
A. `ValueError` then `[[True, False, True], [False, False, True]]` then `[88, 79, 60]` — Python's bitwise `&` binds *tighter* than the comparison operators `>`/`<`, so `grid > 50 & grid < 90` is actually parsed as the chained comparison `grid > (50 & grid) < 90`, which Python evaluates as `(grid > (50 & grid)) and ((50 & grid) < 90)` — and that implicit `and` tries to coerce a multi-element array to a single `bool`, raising `ValueError` ("truth value of an array...is ambiguous"), long before it can express "between 50 and 90" at all. Wrapping each comparison in its own parentheses first — `(grid > 50) & (grid < 90)` — forces both comparisons to happen before the elementwise `&`, correctly flagging every score strictly between `50` and `90`: `88` and `79` in row 0, and `60` in row 1.
B. `[[True, False, True], [False, False, True]]` then `[[True, False, True], [False, False, True]]` then `[88, 79, 60]` — wrongly assumes the unparenthesized version already works and happens to match the parenthesized one; `&`'s higher precedence than `>`/`<` means the unparenthesized expression doesn't even perform the comparisons in the intended order, so it raises instead of silently matching.
C. `ValueError` then `[[True, False, True], [False, False, True]]` then `[88, 92, 79, 60]` — correctly predicts the error and the mask but miscomputes the masked selection, wrongly including `92`; `92` is not strictly less than `90`, so it fails the second condition and must be excluded from `grid[sweet_spot_fixed]`.
D. `ValueError` then `[[True, True, True], [False, False, True]]` — correctly predicts the error but miscomputes the fixed mask, wrongly flagging `92` as inside the `50`–`90` range; `92 > 90`, so `92 < 90` is `False` and that position must stay `False` in `sweet_spot_fixed`.

## Q5. To close out this topic, Grace runs the Day 53/54 `int8` running totals through `np.where` with two different fallback branches instead of adding a scalar directly. What does this print? (Roadmap #45, #41, #44)

```python
import numpy as np

totals = np.array([120, 45, 92], dtype=np.int8)

same_dtype = np.where(totals > 90, totals, totals + 10)
print(same_dtype.dtype, same_dtype.tolist())

mixed_dtype = np.where(totals > 90, totals, totals + 10.5)
print(mixed_dtype.dtype, mixed_dtype.tolist())
```
A. `int8 [120, 55, 92]` then `float64 [120.0, 55.5, 92.0]` — `totals > 90` is `[True, False, True]` (`120>90` and `92>90` are both `True`; `45>90` is `False`), so positions 0 and 2 keep `totals` (`120`, `92`) and position 1 takes the fallback. In `same_dtype`, the fallback `totals + 10` stays `int8` (`45+10=55`, well within range), so `np.where` combines two same-dtype branches into an `int8` result. In `mixed_dtype`, the fallback `totals + 10.5` is a `float64` array — mixing an `int8` branch with a `float64` branch forces NumPy to promote the *entire* output to `float64`, so even the untouched `120` and `92` from the `totals` branch print with a trailing `.0`, not as plain integers.
B. `int8 [120, 55, 92]` then `int8 [120, 55, 92]` — wrongly assumes adding `10.5` (a float) to an `int8` array still produces an `int8` result, as if the fractional part were silently truncated and the dtype preserved; adding a float literal to an integer array always promotes that operand to a float dtype, and `np.where` then promotes its whole output to match the wider of its two branches.
C. `int8 [120, 55, 92]` then `float64 [120.0, 55.0, 92.0]` — gets the dtype promotion right but wrongly truncates `55.5` down to `55.0`, as if the float fallback got cast back through `int8` before the final promotion; `np.where` selects the already-computed float value `45 + 10.5 = 55.5` directly into the float64 result, with no intermediate truncation.
D. `float64 [120.0, 55.0, 102.0]` then `float64 [120.0, 55.5, 92.0]` — wrongly computes the first line's dtype as `float64` even though both of its branches (`totals` and `totals + 10`) are plain `int8`, and additionally miscalculates position 2 as the fallback value `92 + 10 = 102` instead of keeping the `True`-branch value `92`, since `92 > 90` is `True` there.

## Answer key

1. **A** — `grid[mask]` (read) always copies, so mutating `high` doesn't affect `grid`. `grid[mask] = 0` (write) mutates `grid` directly at every `True` position, zeroing the three values originally over `60`. B wrongly assumes the read returns a view. C wrongly recomputes the mask against the mutated copy. D wrongly assumes the write is also read-only.
2. **A** — `np.where(condition, x, y)` takes `x` where `True`, `y` where `False`. `grid > 60` is `True` for row 0, so row 0 becomes `-1` and row 1 keeps its original values. B swaps which row satisfies the condition. C swaps the argument order (`True`/`False` branches reversed). D wrongly assumes the whole array gets replaced.
3. **A** — A mask shaped like the whole array flattens to 1-D or just the `True` elements; a mask shaped like one axis selects whole rows and stays 2-D. B wrongly assumes elementwise masking preserves shape and fills gaps. C wrongly assumes row masking also flattens per-row. D wrongly prints the mask instead of the selected values.
4. **A** — `&` binds tighter than `>`/`<`, so the unparenthesized expression becomes an invalid chained comparison that raises `ValueError` via an implicit `and` on arrays. Parenthesizing each comparison fixes it, correctly flagging `88`, `79`, `60`. B wrongly assumes the unparenthesized version works anyway. C gets the mask right but wrongly includes `92` in the final selection. D wrongly flags `92` as inside the range.
5. **A** — The condition `totals > 90` is `[True, False, True]`. A same-dtype (`int8`) fallback keeps the result `int8`; a float fallback forces the whole output to `float64`, even the elements taken from the `int8` branch. B wrongly assumes adding a float keeps the array `int8`. C wrongly truncates the float fallback value. D wrongly computes the first line's dtype and miscalculates which branch position 2 takes.
