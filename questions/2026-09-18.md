## Q1. Building on Day 6's `np.where` and Day 7's Series, what does this print?

```python
import pandas as pd
import numpy as np
ages = pd.Series([25, 30, 35, 40], index=['a', 'b', 'c', 'd'])
result = np.where(ages > 30, ages, 0)
print(type(result), result)
```
A. `<class 'numpy.ndarray'> [ 0  0 35 40]`
B.
```
<class 'pandas.core.series.Series'>
a     0
b     0
c    35
d    40
dtype: int64
```
C. `<class 'numpy.ndarray'> [25 30 35 40]`
D. Raises a TypeError because `np.where` doesn't accept a pandas Series as an argument

## Q4. Building on Day 6's single-argument `np.where` form and Day 9's `.iloc`, what does this print?

```python
import pandas as pd
import numpy as np
data = {'name': ['Alice', 'Bob', 'Carol', 'Dave'], 'score': [88, 45, 92, 60]}
df = pd.DataFrame(data, index=[100, 101, 102, 103])
positions = np.where(df['score'] > 60)
print(positions, df.iloc[positions[0]]['name'].tolist())
```
A. `(array([0, 2]),) ['Alice', 'Carol']`
B. `(array([100, 102]),) ['Alice', 'Carol']`
C. `(array([0, 2]),) ['Bob', 'Dave']`
D. Raises a TypeError because `np.where`'s single-argument form doesn't work on a pandas Series

## Q5. Building on Day 8's custom-index DataFrame construction, spot the bug: this code is meant to print Bob's age, but raises an error. Which line is wrong, and what's the fix?

```python
import pandas as pd
data = {'name': ['Alice', 'Bob', 'Carol'], 'age': [25, 30, 35]}
df = pd.DataFrame(data, index=['r1', 'r2', 'r3'])

bob_age = df.iloc['r2', 'age']
print(bob_age)
```
A. `df.iloc['r2', 'age']` is the bug — `.iloc` requires integer positions, not labels, and raises a `ValueError`; fix it with `df.loc['r2', 'age']` (or `df.iloc[1, 1]`)
B. `df.iloc['r2', 'age']` is the bug — `.iloc` takes column first and row second; fix it with `df.iloc['age', 'r2']`
C. `data = {...}` is the bug — a dict passed to `pd.DataFrame` can't be combined with a custom `index=`
D. There is no bug; `df.iloc['r2', 'age']` runs fine and returns 30

## Answer key

1. **A** — `np.where(cond, x, y)`'s three-argument form always returns a plain **NumPy ndarray**, even when `x`/`y` are pandas Series — it operates on the underlying array data and drops the Series' index entirely. `ages > 30` is `[F, F, T, T]`, so positions `'a'`/`'b'` become `0` and `'c'`/`'d'` keep their original values, giving `[0, 0, 35, 40]`. B is the tempting-but-wrong answer: it's what you'd get from **boolean-mask indexing** (`ages[ages > 30]`, the Day 7 Q2 pattern), which *does* preserve the Series type and index — but that's a different operation from three-argument `np.where`. C forgets to apply the substitution and just prints the original values. D is wrong — `np.where` works on any array-like, pandas Series included, via NumPy's array protocol.
2. **A** — These are the exact same `.loc`/`.iloc` rules from Day 9, and they apply identically to a Series, not just a DataFrame: `.loc[5:15]` is label-based and **inclusive of the stop label**, covering labels 5, 10, 15 → `[100, 200, 300]`; `.iloc[0:2]` is purely positional with an **exclusive** stop, covering positions 0 and 1 → `[100, 200]`. B wrongly applies `.iloc`'s exclusive-stop rule to the `.loc` slice. C wrongly applies `.loc`'s inclusive-stop rule to the `.iloc` slice. D is wrong — `.loc` slicing works fine on any sorted, unique index (integer or otherwise); it has no requirement that consecutive labels be gap-free.
3. **A** — Constructing a DataFrame from a dict of Series aligns on the **union** of their indices (the Day 8 Q2 rule): the union of `a`'s `['p','q','r']` and `b`'s `['q','r']` is `['p','q','r']`, so `df` has a real row labeled `'p'` — it's just that column `'b'` has no value there, so it's `NaN`. `.loc['p', 'b']` is therefore a perfectly valid lookup that returns that `NaN`. B wrongly assumes missing alignment gets filled with `0` — pandas never does this automatically. C wrongly reasons about `b`'s *original* index instead of `df`'s actual (post-alignment) index, where `'p'` is a completely valid row label. D is wrong — Series of different lengths combine into a DataFrame without any error; that's exactly what union alignment is for.
4. **A** — `np.where(cond)` with a **single argument** doesn't return values at all — it returns a tuple of arrays giving the **positional** indices where `cond` is `True`, always 0-based regardless of the Series' actual index labels. `df['score'] > 60` is `[T, F, T, F]`, so the true positions are `0` and `2`, giving `(array([0, 2]),)`. Feeding that straight into `.iloc[...]` (positional) correctly grabs Alice and Carol. B is the tempting wrong answer — it assumes `np.where` returns the DataFrame's *index labels* (`100`, `102`) rather than raw positions; mixing that up with `.iloc`, which expects positions, would actually raise an `IndexError` for the out-of-range positions `100`/`102`. C comes from reading the condition backwards (picking the `False` positions instead). D is wrong — like Q1, `np.where` happily accepts a pandas Series via NumPy's array protocol.
5. **A** — `.iloc` requires integer **positions** on both axes; passing the label `'r2'` (and `'age'`) to it is invalid and raises a `ValueError` ("Location based indexing can only have [integer, ...] types"), since string labels only work with `.loc`. Swapping in `.loc['r2', 'age']` (label-based) or `.iloc[1, 1]` (fully positional) both correctly return `30`. B invents a row/column order swap that isn't how `.iloc` works — both `.loc` and `.iloc` take `[row_selector, column_selector]`, same order. C is wrong — passing `index=` alongside a dict to `pd.DataFrame` is a completely standard, valid pattern (used throughout Day 8/9). D is wrong — this line does raise; `.iloc` never falls back to label lookup just because a position lookup fails.
