## Q1. Building on Day 29's `.to_numpy()` extraction and Day 3's broadcasting basics, Grace reshapes the recurring `df6`'s scores into a 2×3 grid and subtracts each column's mean to see how far every score sits from its own column's average. What does this print? (Roadmap #33, #24, #3)

```python
import pandas as pd
import numpy as np

data6 = {'name': ['Alice', 'Bob', 'Carol', 'Dave', 'Eve', 'Frank'],
         'team': ['Red', 'Blue', 'Red', 'Blue', 'Red', 'Blue'],
         'region': ['North', 'South', 'North', 'North', 'South', 'South'],
         'score': [88, 45, 92, 60, 75, 50]}
df6 = pd.DataFrame(data6, index=[100, 101, 102, 103, 104, 105])

scores = df6['score'].to_numpy()
grid = scores.reshape(2, 3)
col_means = grid.mean(axis=0)
print((grid - col_means).tolist())
```
A. `[[14.0, -15.0, 21.0], [-14.0, 15.0, -21.0]]` — `reshape(2, 3)` fills row-major (the default "C" order), so `grid` is `[[88, 45, 92], [60, 75, 50]]`; `axis=0` collapses the 2 *rows*, leaving one mean per column (`74.0`, `60.0`, `71.0`), and that length-3 vector broadcasts against the grid's trailing axis — subtracting the matching column mean from every row
B. `[[13.0, -30.0, 17.0], [-1.67, 13.33, -11.67]]` — confuses `axis=0` (collapse down the columns) with `axis=1` (collapse across each row), computing per-row means instead and broadcasting those row-wise — the same `axis=0`/`axis=1` mix-up Day 4's aggregation lesson warned about
C. Raises a `ValueError`, wrongly assuming a length-3 vector can't broadcast against a `(2, 3)` array unless it's first reshaped to `(1, 3)` — missing that a plain 1-D array already aligns against the *last* axis automatically
D. `[[21.5, 16.0, 12.5], [-21.5, -16.0, -12.5]]` — wrongly assumes `.reshape()` fills column-by-column ("F" / Fortran order) by default, so believes `grid` is actually `[[88, 92, 75], [45, 60, 50]]` before any mean is even taken

## Q2. Grace tries the row-wise version of the same idea — subtracting each row's own mean — without thinking about shape first. What does this print? (Roadmap #33, #4)

```python
row_means = grid.mean(axis=1)
print(row_means.shape)
try:
    print(grid - row_means)
except ValueError as e:
    print(type(e).__name__)
print(np.round(grid - row_means.reshape(-1, 1), 2).tolist())
```
A. `(2,)` then `ValueError` then `[[13.0, -30.0, 17.0], [-1.67, 13.33, -11.67]]` — broadcasting compares shapes from the *trailing* axis inward: `grid`'s shape is `(2, 3)` and `row_means`'s is `(2,)`, so the last axes (`3` vs `2`) are compared first and neither is `1`, so they don't match and it raises; `.reshape(-1, 1)` turns `row_means` into shape `(2, 1)`, whose trailing `1` *does* stretch to match `3`, so the fixed version broadcasts cleanly per row
B. `(2,)` then `[[13.0, -30.0, 17.0], [-1.67, 13.33, -11.67]]` then `[[13.0, -30.0, 17.0], [-1.67, 13.33, -11.67]]` — wrongly assumes broadcasting checks shapes from the *leading* axis outward (so a 2-element vector "obviously" matches the grid's 2 rows), missing that NumPy always aligns from the last axis first, which is exactly why the plain subtraction fails
C. `(2, 1)` then `[[13.0, -30.0, 17.0], [-1.67, 13.33, -11.67]]` then `[[13.0, -30.0, 17.0], [-1.67, 13.33, -11.67]]` — wrongly assumes `keepdims=True` is `.mean()`'s default, so `axis=1` would already return shape `(2, 1)` without ever needing the explicit reshape
D. `(2,)` then `ValueError` then `ValueError` — correctly predicts the first failure but wrongly assumes `.reshape(-1, 1)` produces a *row* vector shape `(1, 2)` instead of a column vector `(2, 1)`, so expects the "fixed" line to fail the exact same way

## Q3. Contrasting with Day 3's row-vector broadcasting, Grace combines a per-row base score with a per-column bonus pattern purely through broadcasting, with no loop. What does this print? (Roadmap #33, #3)

```python
row_base = np.array([[100], [200]])
col_bonus = np.array([1, 2, 3])
adjusted = row_base + col_bonus
print(adjusted.shape)
print(adjusted.tolist())
```
A. `(2, 3)` then `[[101, 102, 103], [201, 202, 203]]` — `row_base` is explicitly 2-D with shape `(2, 1)`, and `col_bonus` is 1-D with shape `(3,)` (implicitly `(1, 3)` for broadcasting); each array's size-1 dimension stretches to match the other's — `row_base`'s lone column stretches across all 3 columns, `col_bonus`'s implicit single row stretches down both rows — combining into a full `(2, 3)` grid
B. Raises a `ValueError` — wrongly treats `row_base` as if it were a plain length-2 1-D array and `col_bonus` as length-3, concluding mismatched lengths can never broadcast; misses that `row_base`'s deliberate `(2, 1)` shape already satisfies the "size 1 stretches to fit" rule on its last axis
C. `(2, 3)` then `[[101, 2, 3], [201, 2, 3]]` — correctly predicts the shape but wrongly treats broadcasting as "fill the one matching slot, leave the rest as-is," so only column 0 gets `row_base` added while columns 1 and 2 keep `col_bonus`'s raw, un-added values
D. `(2, 1)` then `[[102], [202]]` — wrongly assumes a shorter array added to a longer one gets reduced down to a single combined value (as if NumPy averaged `col_bonus` to `2` first) rather than broadcast element-by-element across every column

## Q4. Grace redoes Q2's row-centering the cleaner way, flagging how far each score sits from its own row's maximum using `keepdims=True` instead of a manual reshape. What does this print? (Roadmap #33, #4)

```python
row_max = grid.max(axis=1, keepdims=True)
print(row_max.shape)
print((grid - row_max).tolist())
```
A. `(2, 1)` then `[[-4, -47, 0], [-15, 0, -25]]` — `keepdims=True` keeps the reduced axis as a size-1 dimension instead of dropping it, so `.max(axis=1, keepdims=True)` returns shape `(2, 1)` directly — already broadcast-ready against the `(2, 3)` grid with no `.reshape()` needed — and each row's own max (`92` for row 0, `75` for row 1) is subtracted from every entry in that row
B. `(2,)` then `ValueError` — wrongly treats `keepdims=True` as a no-op, reverting to the same dropped-axis shape (and the same broadcasting failure) Q2 hit without it
C. `(1, 3)` then `[[0, -30, 0], [-28, 0, -42]]` — confuses `axis=1` (collapse each row) with `axis=0` (collapse each column), computing the per-*column* max with `keepdims=True` instead — the same axis mix-up as Q1's distractor B, just applied to `.max()` instead of `.mean()`
D. `(2, 1)` then `[[-4, -47, 0], [-32, -17, -42]]` — correctly gets the `(2, 1)` shape from `keepdims=True`, but wrongly computes "each row's max" as the single *global* max (`92`) applied to every row, instead of letting `axis=1` find each row's own max independently

## Q5. Spot the bug: Grace wants to give the grid's first row a `+5` bonus and its second row a `+10` bonus, and writes what she thinks is a quick one-liner for it. What does this print? (Roadmap #33)

```python
bonus = np.array([5, 10, 15])
print((grid + bonus).tolist())
```
A. `[[93, 55, 107], [65, 85, 65]]` — `bonus` has 3 elements, matching `grid`'s trailing axis (3 columns), so it broadcasts *column-wise*: every row gets `+5` to column 0, `+10` to column 1, and `+15` to column 2, regardless of which row it's in; this has nothing to do with Grace's "row 0 vs row 1" plan, and NumPy never raises here because the shapes genuinely are broadcast-compatible — just not in the way she assumed
B. Raises a `ValueError` — wrongly assumes a 3-element array can never combine with a 2-row array, missing that broadcasting matches against `grid`'s *last* axis (3 columns), not its first axis (2 rows), so the shapes are actually compatible
C. `[[93, 50, 97], [70, 85, 60]]` — assumes, as Grace intended, that `bonus[0] = 5` applies to every entry in row 0 and `bonus[1] = 10` applies to every entry in row 1, with the extra `bonus[2] = 15` simply going unused; that's the row-wise result she meant to get, not what the code actually does
D. `[[103, 55, 97], [75, 85, 55]]` — correctly spots that it broadcasts column-wise without error, but wrongly pairs `bonus` to `grid`'s columns in reverse (as if alignment matched values right-to-left rather than by axis position), adding `15` to column 0, `10` to column 1, and `5` to column 2 instead

## Answer key

1. **A** — `scores.reshape(2, 3)` fills in row-major ("C") order by default, so `grid` is `[[88, 45, 92], [60, 75, 50]]`. `grid.mean(axis=0)` collapses the size-2 row axis, leaving one mean per column: `74.0`, `60.0`, `71.0`. That length-3 vector broadcasts against `grid`'s matching trailing axis, subtracting the right column mean from every row: `[[14.0, -15.0, 21.0], [-14.0, 15.0, -21.0]]`. B swaps `axis=0` for `axis=1`, computing row means instead of column means. C invents a reshape requirement that doesn't exist — a plain 1-D array already aligns against an array's last axis without help. D wrongly assumes Fortran-order filling is NumPy's default, when row-major is.
2. **A** — Broadcasting compares two shapes starting from the *last* axis and working inward. `grid` is `(2, 3)` and `row_means` is `(2,)`; comparing the trailing axes gives `3` vs `2`, which don't match and neither is `1`, so NumPy raises `ValueError`. Reshaping `row_means` to `(2, 1)` puts a `1` in the trailing position, which *does* stretch to match `3`, letting the subtraction broadcast correctly per row. B wrongly assumes broadcasting checks the *leading* axis first, which would make the mismatch look fine when it isn't. C wrongly assumes `keepdims=True` is `.mean()`'s default. D correctly predicts the first error but wrongly assumes `.reshape(-1, 1)` yields a row vector `(1, 2)` instead of the column vector `(2, 1)` it actually produces.
3. **A** — `row_base` has an explicit 2-D shape `(2, 1)`, and `col_bonus`'s shape `(3,)` is treated as `(1, 3)` for broadcasting purposes. Each array's size-1 dimension stretches to match the other, combining into a genuine `(2, 3)` outer-sum grid: `[[101, 102, 103], [201, 202, 203]]`. B wrongly treats `row_base` as a plain length-2 1-D array, ignoring that its deliberate `(2, 1)` shape is exactly what makes the broadcast valid. C correctly gets the shape but wrongly imagines broadcasting as filling one matching slot and leaving everything else untouched, rather than stretching across every position. D wrongly assumes a shorter array gets reduced/averaged into the longer one instead of combined element-by-element.
4. **A** — `keepdims=True` keeps the axis that `.max(axis=1, ...)` reduces as a size-1 dimension rather than dropping it, so the result is already shape `(2, 1)` — broadcast-ready against `grid`'s `(2, 3)` without any manual reshape. Each row's own max (`92` then `75`) is subtracted from every entry in that row, giving `[[-4, -47, 0], [-15, 0, -25]]`. B wrongly treats `keepdims=True` as having no effect, reverting to Q2's dropped-shape failure. C swaps `axis=1` for `axis=0`, computing per-column maxes instead of per-row ones. D gets the shape right but wrongly uses one single global max (`92`) for both rows instead of letting each row find its own.
5. **A** — `bonus` has 3 elements, which matches `grid`'s trailing axis (3 columns) exactly, so it broadcasts column-wise across both rows: `+5` to column 0, `+10` to column 1, `+15` to column 2, for every row — giving `[[93, 55, 107], [65, 85, 65]]`. This has nothing to do with "row 0 vs row 1," which is exactly the trap: the shapes are broadcast-compatible, so nothing errors, even though the result doesn't do what Grace intended. B wrongly assumes a 3-element array can't combine with a 2-row array at all, missing that broadcasting checks the trailing axis (3 columns), not the leading one (2 rows). C is the row-wise result Grace actually wanted, which this code does not produce. D gets "broadcasts column-wise, no error" right but wrongly reverses which bonus value lines up with which column.
