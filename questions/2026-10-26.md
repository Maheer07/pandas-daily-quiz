## Q1. Building on the recurring `df6`, Grace merges it with a new, intentionally mismatched `team_info` frame using an outer join with `indicator=True`. What does this print? (Roadmap #29, #15)

```python
import pandas as pd

data6 = {'name': ['Alice', 'Bob', 'Carol', 'Dave', 'Eve', 'Frank'],
         'team': ['Red', 'Blue', 'Red', 'Blue', 'Red', 'Blue'],
         'region': ['North', 'South', 'North', 'North', 'South', 'South'],
         'score': [88, 45, 92, 60, 75, 50]}
df6 = pd.DataFrame(data6, index=[100, 101, 102, 103, 104, 105])

team_info = pd.DataFrame({'team': ['Red', 'Green'], 'manager': ['Pat', 'Sam']})

merged1 = df6.merge(team_info, on='team', how='outer', indicator=True)
print(len(merged1))
print(merged1.loc[merged1['team'] == 'Green', 'name'].tolist())
```
A. `7` then `[nan]` — an outer join keeps all 3 Red rows (matched, `'both'`), all 3 Blue rows (unmatched on the right, `'left_only'`), and adds one new row for `'Green'` (unmatched on the left, `'right_only'`); that new row has no corresponding `df6` data, so its `name` is `NaN`
B. `6` then `[]` — wrongly treats `how='outer'` as if it behaves like `how='left'`, so the unmatched `'Green'` key from `team_info` is never added as a new row at all
C. `3` then `[]` — wrongly treats `how='outer'` as if it behaves like the default `how='inner'`, keeping only the matched `'Red'` rows and dropping both the unmatched `'Blue'` and `'Green'` keys
D. Raises a `KeyError`, assuming the `'team'` column is consumed by `on='team'` and no longer exists in the merged result

## Q2. Spot the bug: Grace merges `df6` with `team_info` but forgets to pass `how=`. What does this print? (Roadmap #29, #15)

```python
merged2 = df6.merge(team_info, on='team')
print(merged2['name'].tolist())
```
A. `['Alice', 'Carol', 'Eve']` — `merge()`'s default `how` is `'inner'`, so only rows whose `team` value exists on *both* sides survive; `'Red'` is the only such team (`'Blue'` has no match in `team_info`, `'Green'` has no match in `df6`), keeping just the three Red rows in their original order
B. `['Alice', 'Bob', 'Carol', 'Dave', 'Eve', 'Frank']` — wrongly assumes `merge()` defaults to `how='outer'` (or `'left'`), so every `df6` row survives regardless of whether its `team` value has a match
C. Raises a `TypeError`, wrongly assuming `how` is a required argument with no default
D. Raises a `pandas.errors.MergeError`, wrongly assuming `on='team'` only works when both frames share an identical set of key values, rather than simply controlling which column to join on

## Q3. Grace adds `validate='one_to_one'` to catch merge-cardinality mistakes. What does this print? (Roadmap #29)

```python
try:
    df6.merge(team_info, on='team', validate='one_to_one')
except Exception as e:
    print(type(e).__name__)
```
A. `MergeError` — `'one_to_one'` requires the merge key to be unique on *both* sides; `df6['team']` has `'Red'` three times, which alone violates that requirement (even though `team_info['team']` is unique), so pandas raises `pandas.errors.MergeError` before the join itself matters
B. Nothing is printed (no exception) — wrongly assumes `validate='one_to_one'` only inspects the right-hand frame, and since `team_info['team']` has no duplicates, concludes the check passes
C. `ValueError` — correctly identifies that `MergeError` is *raised* here, but assumes `type(e).__name__` reports the generic `ValueError` base class name rather than pandas' specific `MergeError` subclass that was actually raised
D. `KeyError` — wrongly assumes merge-cardinality violations are reported as a key-lookup failure rather than through a dedicated validation exception

## Q4. Contrast with Q3: Grace switches to `validate='many_to_one'` instead. What does this print? (Roadmap #29)

```python
merged4 = df6.merge(team_info, on='team', validate='many_to_one')
print(len(merged4))
```
A. `3` — `'many_to_one'` only requires the merge key to be unique on the *right*-hand frame (`team_info`'s `'Red'`/`'Green'` are unique), and duplicate keys are explicitly allowed on the left (`df6`'s three `'Red'` rows), so no error is raised; the join itself still defaults to `how='inner'`, keeping just the three matched Red rows
B. Raises `MergeError`, same as Q3 — wrongly assumes `'many_to_one'` still demands left-side uniqueness, when its entire purpose is to permit duplicate keys on the "many" (left) side
C. `7` — wrongly assumes passing any `validate=` argument changes the join type itself (e.g. forces `how='outer'`), when `validate` only checks cardinality and never alters which rows the join produces
D. Raises `MergeError` — mixes up the validate direction, assuming `'many_to_one'` requires the *left* key to be unique (which `df6`'s repeated `'Red'` violates), when it's actually the *right* key's uniqueness that `'many_to_one'` requires

## Q5. Building on Day 34/35's `~`/`.loc` boolean-mask pattern, Grace uses `indicator=True` to pull out exactly the `df6` rows that found no match in `team_info`. What does this print? (Roadmap #29, #28)

```python
merged5 = df6.merge(team_info, on='team', how='left', indicator=True)
unmatched = merged5.loc[merged5['_merge'] == 'left_only', 'name'].tolist()
print(unmatched)
```
A. `['Bob', 'Dave', 'Frank']` — with `how='left'`, every `df6` row is kept; the three Blue-team rows have no match in `team_info` and get labeled `'left_only'` (with `manager` as `NaN`), while the three Red-team rows are labeled `'both'`
B. `[]` — wrongly assumes a `how='left'` merge can never produce any `'left_only'` rows, reasoning that since every left row is always preserved, none of them could ever be *labeled* as unmatched
C. `['Alice', 'Carol', 'Eve']` — mixes up which side the label describes, pulling the matched Red rows (labeled `'both'`) instead of the unmatched Blue rows (labeled `'left_only'`)
D. Raises `KeyError: '_merge'` — wrongly assumes `indicator=True` names its marker column `'indicator'` rather than pandas' actual default name, `'_merge'`

## Answer key

1. **A** — An outer join unions both sides: the three Red rows match on both sides (`'both'`), the three Blue rows have no counterpart in `team_info` (`'left_only'`), and `team_info`'s `'Green'` row has no counterpart in `df6`, so it's added as a brand-new row (`'right_only'`) with every original `df6` column — including `name` — set to `NaN`. Total rows: `3 + 3 + 1 = 7`. B wrongly collapses `how='outer'` into `how='left'` behavior, which would never add the `'Green'` row at all. C wrongly collapses `how='outer'` into the default `how='inner'` behavior, which would drop both unmatched sides instead of keeping them. D is wrong — `on='team'` tells merge which column to join on, but that column still exists (and is shared) in the output; it isn't consumed or removed.
2. **A** — `merge()`'s default `how` is `'inner'`, so only `'Red'` (present on both sides) survives; `'Blue'` (only in `df6`) and `'Green'` (only in `team_info`) are both dropped, leaving `['Alice', 'Carol', 'Eve']` in their original relative order. B wrongly assumes a more permissive default `how` (like `'outer'` or `'left'`) that would keep every `df6` row regardless of match. C invents a requirement that `how` must be supplied explicitly — it has a documented default. D invents a restriction on `on=` that doesn't exist — it simply names the join column and never requires both frames to share identical key sets.
3. **A** — `validate='one_to_one'` requires the merge key to be unique in *both* frames; `df6['team']` has `'Red'` three times, which alone breaks that guarantee regardless of `team_info`'s own uniqueness, so pandas raises `pandas.errors.MergeError`. B wrongly assumes the check only looks at the right-hand frame — `'one_to_one'` checks both sides, and the left side's duplicates are exactly what trips it. C correctly spots that an exception fires but misreports which one — `MergeError` is a subclass of `ValueError`, but `type(e).__name__` reports the exact runtime class that was raised (`'MergeError'`), not an ancestor class's name. D invents an unrelated exception type; merge-cardinality violations are reported through pandas' own `MergeError`, not `KeyError`.
4. **A** — `'many_to_one'` only requires uniqueness on the right-hand frame; since `team_info['team']` has no duplicates, the check passes even though `df6['team']` repeats `'Red'` three times (duplicates are exactly what "many" permits on the left). The join itself still defaults to `how='inner'`, so the result is unchanged from Q2: the three matched Red rows, `len == 3`. B wrongly imports Q3's `'one_to_one'` failure into `'many_to_one'`, missing the entire point of the distinction between the two validate modes. C invents a side effect where `validate=` changes the join type — it only ever checks cardinality after the join type (here, the `how='inner'` default) has already determined the result. D reverses which side `'many_to_one'` requires to be unique — it's the right side, not the left, so `df6`'s duplicate `'Red'` values are exactly what the mode is designed to tolerate.
5. **A** — `how='left'` keeps every `df6` row; the three Blue rows find no match in `team_info` and are marked `'left_only'` (with `manager` left as `NaN`), while the three Red rows match and are marked `'both'`, so filtering for `'left_only'` isolates `['Bob', 'Dave', 'Frank']`. B wrongly assumes `'left_only'` can never occur under a left merge — it's precisely the label pandas uses for left rows that *didn't* find a match, which is common under a left join with mismatched keys. C swaps the two labels' meanings, grabbing the matched (`'both'`) rows instead of the unmatched (`'left_only'`) ones. D is wrong about the default indicator column name — `indicator=True` names it `'_merge'`; `'indicator'` would only be the name if a *string* had been passed to `indicator=` instead of `True`.
