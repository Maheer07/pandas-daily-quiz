## Q1. Returning to Day 7 Q2's `hot_days` Series, Grace adds a bonus Series that happens to repeat one label twice. What does this print? (Roadmap #46, #6)

```python
import pandas as pd

temps = pd.Series([68, 72, 95, 61, 88], index=['mon', 'tue', 'wed', 'thu', 'fri'])
hot = temps[temps > 80]
bonus = pd.Series([2, 2, 5], index=['wed', 'wed', 'fri'])

print(hot + bonus)
```
A. `fri 93`, `wed 97`, `wed 97` (as a three-row Series) — `hot` is `{'wed': 95, 'fri': 88}`. Series arithmetic aligns by label (Day 7 Q3), and when one side has a label appearing more than once (`'wed'` twice in `bonus`), that label is paired against `hot`'s single `'wed'` value for *each* occurrence, producing `'wed'` twice in the result (`95+2=97` both times) alongside `'fri'` once (`88+5=93`). Because a duplicate label is involved, pandas falls back to a sorted alignment instead of preserving either input's original order, so `'fri'` prints before `'wed'`.
B. `fri 93`, `wed 97` (as a two-row Series, duplicates collapsed) — wrongly assumes pandas deduplicates repeated labels before adding, as if `bonus` only had one `'wed'` entry; alignment pairs the single `hot['wed']` value against *every* matching `bonus` row, so a repeated label in one side genuinely produces a repeated label in the result, not a collapsed one.
C. `wed 97`, `fri 93` (same two rows as A, but in `hot`'s original order) — wrongly assumes the result keeps `hot`'s original label order; once a duplicate label is involved in the alignment, pandas can no longer rely on either side's original ordering and the result index comes back sorted, so `'fri'` (alphabetically first) prints before either `'wed'` row.
D. Raises a `ValueError` because `bonus`'s index isn't unique — wrongly assumes a non-unique index makes a Series unusable in arithmetic; pandas explicitly supports duplicate labels, and alignment with a non-unique index is a valid (if easy-to-misjudge) operation rather than an error.

## Q2. Building on Day 56 Q2's `np.where` argument-order lesson, Grace now runs it on a pandas Series instead of a NumPy array and compares it against the pandas-native equivalent. What does this print? (Roadmap #46, #45)

```python
import pandas as pd
import numpy as np

temps = pd.Series([68, 72, 95, 61, 88], index=['mon', 'tue', 'wed', 'thu', 'fri'])

via_numpy = np.where(temps > 80, temps, 0)
via_pandas = temps.where(temps > 80, 0)

print(type(via_numpy).__name__, via_numpy.tolist())
print(type(via_pandas).__name__)
print(via_pandas.tolist())
```
A. `ndarray [0, 0, 95, 0, 88]` then `Series` then `[0, 0, 95, 0, 88]` — `np.where` is a NumPy function: it happily accepts a Series as input but always hands back a plain `ndarray`, discarding the index entirely — same elementwise selection logic as Day 56 (condition picks the second argument, here `temps`, where `True`; the third, `0`, where `False`), just now stripped of labels. `Series.where(cond, other)` is the pandas *method* with the same selection logic but the opposite keep/replace convention from its name: it keeps the original value where the condition is `True` and substitutes `other` where it's `False` — landing on the same five numbers here, but returned as a label-preserving `Series`.
B. `ndarray [0, 0, 95, 0, 88]` then `Series` then `[95, 61, 60, 72, 68]` (reordered) — wrongly assumes `.where()` reorders its output to rank values from high to low; `Series.where` preserves the original index order exactly as given, it never sorts.
C. `Series [0, 0, 95, 0, 88]` then `ndarray` then `[0, 0, 95, 0, 88]` — swaps which call returns which type, as if the plain NumPy function `np.where` preserved pandas metadata and the pandas method `.where()` discarded it; it's the opposite — a NumPy function run on a Series-like input returns a bare array, while a Series method always returns a Series.
D. `ndarray [0, 0, 95, 0, 88]` then `Series` then `[68, 72, 0, 61, 0]` — wrongly assumes `Series.where(cond, other)` keeps values where `cond` is `False` and substitutes `other` where it's `True`, the reverse of its actual, easy-to-misremember convention: it keeps on `True` and replaces on `False`, just like Day 56's `np.where(condition, x, y)` keeps `x` on `True`.

## Q3. Contrasting with Day 54 Q5's NumPy `nan`-propagation lesson, Grace runs the same missing-score scenario through a pandas Series instead of a raw array. What does this print? (Roadmap #46, #44)

```python
import pandas as pd
import numpy as np

round_scores = pd.Series([88.0, 92.0, np.nan, 50.0, 60.0])

print(round_scores.sum())
print(round_scores.mean())
print(round_scores.to_numpy().sum())
```
A. `290.0` then `72.5` then `nan` — A pandas Series's `.sum()` and `.mean()` default to `skipna=True`, silently excluding `nan` entries from the calculation — the opposite default from the raw NumPy `.sum()` Day 54 taught, which always propagates `nan`. So `round_scores.sum()` adds only the four real values (`88+92+50+60=290`) and `.mean()` divides by the count of those four (`72.5`), while converting the *same* data `.to_numpy()` and summing that plain array reverts to NumPy's propagating behavior, giving `nan` — the data didn't change, only which aggregation rules apply to it.
B. `nan` then `nan` then `nan` — wrongly assumes a Series aggregation behaves exactly like the underlying NumPy array and propagates `nan` by default, when `Series.sum()`/`.mean()` default to skipping missing values specifically because real-world tabular data is expected to have gaps.
C. `290.0` then `72.5` then `290.0` — wrongly assumes converting to a plain NumPy array with `.to_numpy()` carries the Series's skip-`nan` behavior along with it; once the data is a bare `ndarray`, it's governed by NumPy's own aggregation defaults (propagate `nan`), not pandas's, so the exact same five numbers now sum to `nan`.
D. `230.0` then `57.5` then `nan` — wrongly computes the Series sum by dropping both the `nan` *and* one additional real value (`60.0`) as if two rows were excluded, and divides by a count of 4 anyway; only the single genuine `nan` entry is skipped, leaving all four real values (`88, 92, 50, 60`) in the sum.

## Q4. Still on the `temps` Series from Q1, Grace slices it by label instead of position and checks whether editing the slice reaches back to `temps` — tying in Day 48's Copy-on-Write lesson. What does this print? (Roadmap #46, #42, #39)

```python
import pandas as pd

temps = pd.Series([68, 72, 95, 61, 88], index=['mon', 'tue', 'wed', 'thu', 'fri'])

label_slice = temps['tue':'fri']
pos_slice = temps[1:4]
print(label_slice.tolist())
print(pos_slice.tolist())

label_slice.iloc[0] = -1
print(temps.tolist())
```
A. `[72, 95, 61, 88]` then `[72, 95, 61]` then `[68, 72, 95, 61, 88]` — Label-based slicing (`'tue':'fri'`) is **inclusive of the end label**, so it keeps every entry from `'tue'` through `'fri'` — four values. Positional slicing (`1:4`) follows ordinary Python half-open semantics and stops *before* index 4, giving only three values (`'tue'` through `'thu'`). Under pandas 3.x's Copy-on-Write, a slice always behaves as an independent object once you write to it — mutating `label_slice.iloc[0]` never reaches back into `temps`, which still prints its five original values unchanged.
B. `[72, 95, 61]` then `[72, 95, 61]` then `[68, 72, 95, 61, 88]` — wrongly treats the label slice as if it stopped *before* `'fri'` the way a positional slice stops before its end index; label-based slicing is inclusive of its end label specifically because labels aren't numeric positions pandas can "stop just short of" — it includes the endpoint you named.
C. `[72, 95, 61, 88]` then `[72, 95, 61]` then `[-1, 72, 95, 61, 88]` — wrongly assumes the slice still shares memory with `temps` the way it would have in older pandas without Copy-on-Write; under CoW (the default since pandas 2.0, and the only behavior in 3.x), writing to a slice triggers its own private copy first, so `temps` is never touched.
D. `[72, 95, 61, 88]` then `[68, 72, 95]` — wrongly computes the positional slice as starting from index 0 instead of index 1, as if `temps[1:4]` meant "the first four values" rather than "values at positions 1, 2, and 3."

## Q5. Tying Q1's duplicate-label alignment together with Day 56 Q4's lesson that NumPy boolean masks must match their target's shape, Grace tries to filter `temps` with a boolean Series built from a different subset of labels. What does this print? (Roadmap #46, #45, #6)

```python
import pandas as pd

temps = pd.Series([68, 72, 95, 61, 88], index=['mon', 'tue', 'wed', 'thu', 'fri'])

partial_mask = pd.Series([True, False, True], index=['wed', 'mon', 'tue'])
try:
    print(temps[partial_mask])
except Exception as e:
    print(type(e).__name__)

full_mask = pd.Series([False, False, True, False, True], index=['fri', 'thu', 'wed', 'tue', 'mon'])
print(temps[full_mask].tolist())
```
A. `IndexingError` then `[68, 95]` — Unlike the plain-`ndarray` boolean masks from Day 56, which only ever check *shape*, a boolean **Series** indexer is checked by *label*: pandas requires its index to exactly match the target's index as a set (order doesn't matter) before it will align anything. `partial_mask` only covers 3 of `temps`'s 5 labels, so pandas refuses rather than guessing, raising `IndexingError`. `full_mask` covers the same 5 labels as `temps`, just reordered, so pandas aligns it correctly by label and returns `temps`'s values at the labels flagged `True` (`'mon'` and `'wed'`) in `temps`'s own original order — `68` and `95`.
B. `[95, 61]` then `[68, 95]` — wrongly assumes a boolean Series indexer, like a boolean `ndarray`, is matched purely by *position* rather than by label, as if `partial_mask`'s 3 `True`/`False` flags simply lined up with `temps`'s first three positions; pandas aligns a boolean Series indexer by label and refuses outright when the label sets don't match, rather than silently truncating or reinterpreting it positionally.
C. `IndexingError` then `[88, 95]` — correctly predicts the error but miscomputes `full_mask`'s result order, as if the output followed `full_mask`'s own (reversed) label order rather than `temps`'s original order; label-based selection always returns results in the *indexed object's* order, not the indexer's.
D. `IndexingError` then `IndexingError` — wrongly assumes any boolean Series whose index isn't in the *same order* as the target also raises, as if alignment required identical ordering rather than just an identical set of labels; `full_mask` has exactly `temps`'s five labels, merely shuffled, which pandas aligns without complaint.
