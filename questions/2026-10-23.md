## Q1. Grace filters the recurring `df6` with `.query()` before pivoting it. What does this print? (Roadmap #27, #28)

```python
import pandas as pd

data6 = {'name': ['Alice', 'Bob', 'Carol', 'Dave', 'Eve', 'Frank'],
         'team': ['Red', 'Blue', 'Red', 'Blue', 'Red', 'Blue'],
         'region': ['North', 'South', 'North', 'North', 'South', 'South'],
         'score': [88, 45, 92, 60, 75, 50]}
df6 = pd.DataFrame(data6, index=[100, 101, 102, 103, 104, 105])
df6['bonus_pct'] = [0.1, 0.2, 0.15, 0.05, 0.25, 0.1]

sub1 = df6.query('bonus_pct >= 0.1')
pt1 = pd.pivot_table(sub1, values='score', index='team', columns='region',
                      aggfunc='mean', fill_value=0)
print(pt1.loc['Blue'].tolist())
```
A. `[0.0, 47.5]` — the `>= 0.1` filter excludes only Dave (`bonus_pct=0.05`), so Blue has no surviving `North` row at all; `fill_value=0` replaces that missing `(Blue, North)` cell with `0.0`, leaving Blue's real `South` mean (Bob+Frank, `47.5`) untouched
B. `[60.0, 47.5]` — ignores the `bonus_pct >= 0.1` filter entirely, leaving Dave in Blue's `North` group, giving a mean of `60.0` there instead of the empty cell `fill_value` should fill
C. `[nan, 47.5]` — assumes `fill_value` only has an effect when `aggfunc` is a list of functions rather than a single string like `'mean'`
D. `[47.5]` — assumes the missing `(Blue, North)` combination simply never appears in the pivoted table at all (as if `fill_value` only changed how `NaN` displays rather than actually materializing the cell), so `pt1.loc['Blue']` has only one entry, for `South`

## Q2. Building on Day 34's `~`/`.isin()` pattern, Grace now chains it straight into a groupby-and-sort. What does this print? (Roadmap #26, #28)

```python
chain1 = (df6[~df6['team'].isin(['Blue'])]
          .groupby('region')['score']
          .mean()
          .sort_values(ascending=False))
print(chain1.tolist())
```
A. `[90.0, 75.0]` — `~df6['team'].isin(['Blue'])` keeps only the three Red rows (Alice, Carol, Eve); grouping those by region gives `North` (Alice+Carol) a mean of `90.0` and `South` (Eve alone) a mean of `75.0`, and `sort_values(ascending=False)` puts the larger mean first
B. `[75.0, 90.0]` — reaches the same two correct means but assumes `sort_values()` defaults to ascending order even though `ascending=False` is passed explicitly, so it prints the smaller mean first
C. `[60.0, 47.5]` — drops the `~`, so it keeps the Blue rows instead of excluding them, giving `North` (Dave alone) a mean of `60.0` and `South` (Bob+Frank) a mean of `47.5`
D. Raises the same `TypeError` as Day 34 Q1's precedence bug — assumes `~` binds before `.isin(...)` finishes evaluating, when in fact the method call binds tighter than the unary `~`, so `.isin()` fully returns its boolean Series first and no error occurs here

## Q3. Grace wants, for score-≥-60 rows only, each region's total bonus amount (`score * bonus_pct`), sorted highest-first, in one single vectorized chain. Which line is correct? (Roadmap #25, #26)

A. `df6.assign(bonus_amt=df6['score'] * df6['bonus_pct'])[df6['score'] >= 60].groupby('region')['bonus_amt'].sum().sort_values(ascending=False)` — correct: computes `bonus_amt` with one vectorized multiplication via `.assign()`, keeps only the rows with `score >= 60` (Alice, Carol, Dave, Eve), sums by region (`North` 8.8+13.8+3.0=`25.6`, `South` 18.75), and sorts descending — no per-row Python-level work anywhere
B. `df6[df6['score'] >= 60].apply(lambda r: r['score'] * r['bonus_pct'], axis=1).groupby(df6.loc[df6['score'] >= 60, 'region']).sum().sort_values(ascending=False)` — reaches the same two totals (`North` 25.6, `South` 18.75), but computes each qualifying row's bonus by invoking a Python-level lambda once per row via `apply(axis=1)`, not a single vectorized multiplication across the whole column
C. `df6.assign(bonus_amt=df6['score'] * df6['bonus_pct']).groupby('region')['bonus_amt'].sum()[df6['score'] >= 60].sort_values(ascending=False)` — raises an alignment error: the boolean mask `df6['score'] >= 60` is built against `df6`'s original 6-row index, but it's applied to the already-grouped 2-row region-indexed `Series`, and pandas can't align a boolean indexer against a `Series` of mismatched length/index
D. `df6.assign(bonus_amt=df6['score'] * df6['bonus_pct']).groupby('region')['bonus_amt'].sum().sort_values(ascending=False)` — omits the `score >= 60` filter entirely, so every row's bonus is summed into its region's total; `North`'s total happens to still come out as `25.6` (none of its three rows — 88, 92, 60 — fail the `>= 60` test anyway), but `South`'s total becomes `32.75` (Bob's 9.0 + Eve's 18.75 + Frank's 5.0) instead of the intended `18.75` (Eve alone), since Bob and Frank wrongly stay included

## Q4. Grace compares a built-in string `aggfunc` against an equivalent lambda in `pivot_table`. Which statement is true? (Roadmap #25, #27)

```python
pt_a = pd.pivot_table(df6, values='score', index='team', aggfunc='mean')
pt_b = pd.pivot_table(df6, values='score', index='team', aggfunc=lambda s: s.mean())
```
A. `pt_a` and `pt_b` produce identical values (`Red` 85.0, `Blue` ≈51.667), but `aggfunc='mean'` dispatches to pandas' optimized, vectorized reduction, while the lambda forces a separate Python-level function call for each group — so `pt_b` does the same job with more per-group overhead despite the matching result
B. `pt_a` and `pt_b` differ — the lambda version returns `NaN` for both teams, because a custom callable passed to `aggfunc` isn't allowed to call `.mean()` on the group internally
C. `pt_a` raises a `ValueError`, because `'mean'` as a bare string is only accepted by `.groupby().agg()`, not by `pivot_table`'s `aggfunc`, which requires an actual callable
D. `pt_b` is faster than `pt_a`, because passing a custom lambda skips the internal name-validation step that a string like `'mean'` has to go through first

## Q5. Grace wants each team's total score, counting only `North`-region rows, in a single chained statement. Which line is correct? (Roadmap #26, #27, #28)

A. `df6[df6['region'] != 'South'].pivot_table(values='score', index='team', aggfunc='sum')` — correct: filters to the `North`-only rows first (Alice, Carol, Dave), then sums `score` by team, giving `Blue` 60 and `Red` 180 (88+92)
B. `df6.pivot_table(values='score', index='team', aggfunc='sum')[df6['region'] != 'South']` — raises an alignment error, since the boolean mask (built against `df6`'s original 6-row index) is applied to the already-pivoted 2-row team-indexed result instead of filtering `df6` first
C. `df6[~df6['region'].isin(['South'])].pivot_table(values='score', index='team', aggfunc='mean')` — filters to the same `North`-only rows as A, but uses `'mean'` instead of `'sum'`, giving each team's per-row average (`Red` 90.0, `Blue` 60.0) rather than the requested totals
D. `df6.query('region == "South"').pivot_table(values='score', index='team', aggfunc='sum')` — filters to the wrong region (`South` instead of `North`), giving `Blue` 95 (Bob 45 + Frank 50) and `Red` 75 (Eve alone) instead of the intended `North`-only totals

## Answer key

1. **A** — `sub1 = df6.query('bonus_pct >= 0.1')` keeps every row except Dave (`bonus_pct=0.05`), so after the filter Blue only has South-region rows left (Bob and Frank, mean `47.5`); the `(Blue, North)` combination has no data at all, and `fill_value=0` fills exactly that missing cell with `0.0` rather than leaving it `NaN`, giving `[0.0, 47.5]`. B wrongly assumes the filter does nothing, letting Dave's `60` leak into Blue's `North` group. C invents a restriction `fill_value` doesn't have — it works with any `aggfunc`, string or list. D wrongly assumes a missing combination is dropped from the result shape entirely rather than materialized and filled; `fill_value` guarantees the cell exists.
2. **A** — `~df6['team'].isin(['Blue'])` keeps the three Red rows (Alice 88/North, Carol 92/North, Eve 75/South); grouping by region gives `North` a mean of `90.0` (Alice+Carol) and `South` a mean of `75.0` (Eve alone), and `sort_values(ascending=False)` orders the larger mean first, printing `[90.0, 75.0]`. B gets the right means but wrongly assumes the explicit `ascending=False` is ignored. C forgets the `~`, so it keeps Blue's rows (Dave in `North`, Bob+Frank in `South`) instead of Red's. D wrongly imports Day 34 Q1's unary-`~`-before-`==` precedence trap into this expression — here `.isin(['Blue'])` is a method call, which binds tighter than `~`, so `.isin()` fully resolves into a boolean `Series` before `~` ever touches it; no error occurs.
3. **A** — `.assign(bonus_amt=df6['score'] * df6['bonus_pct'])` computes every row's bonus with one vectorized multiplication; filtering to `score >= 60` keeps Alice, Carol, Dave, and Eve; grouping by region and summing gives `North` (8.8+13.8+3.0=25.6) and `South` (18.75), and sorting descending puts `North` first — all without any per-row Python-level work. B reaches the identical two totals but computes each row's bonus through a `lambda` invoked once per row via `apply(axis=1)`, exactly the per-row overhead the question's "single vectorized chain" rules out. C builds the boolean mask against `df6`'s original 6-row index but tries to apply it to the already-grouped 2-row region-indexed result, which pandas can't align, so it raises rather than filtering anything. D forgets the `score >= 60` filter, so `South`'s total wrongly includes Bob and Frank's bonuses (giving `32.75` instead of `18.75`); `North`'s total happens to match anyway since all three of its rows already satisfy `score >= 60`.
4. **A** — Both pivots compute the same means (`Red` 85.0, `Blue` ≈51.667) since a lambda calling `.mean()` is mathematically identical to the string `'mean'`; the difference is purely performance — `aggfunc='mean'` lets pandas dispatch to its optimized, vectorized reduction, while a custom callable must be invoked separately as a Python-level function call for each group, the same vectorization-vs-per-call overhead distinction Day 31 drew between whole-column operations and `.apply()`/`.iterrows()`. B invents a restriction that doesn't exist — custom `aggfunc` callables can freely call `.mean()` or any other method on the group they receive. C is wrong — `'mean'` (and other named reductions) is explicitly supported as a string `aggfunc` in `pivot_table`, as shown repeatedly on Day 33. D reverses the real performance relationship — the string path is the optimized one, not the lambda.
5. **A** — Filtering `df6` to `region != 'South'` first leaves only the three `North` rows (Alice 88/Red, Carol 92/Red, Dave 60/Blue); pivoting that filtered frame with `aggfunc='sum'` gives `Red` `88+92=180` and `Blue` `60`. B pivots the unfiltered `df6` first (team-level totals over all 6 rows), then tries to apply a boolean mask sized and indexed for the original 6-row `df6` onto that 2-row team-indexed result, which pandas can't align. C filters to the correct `North`-only rows but swaps in `'mean'` for `'sum'`, so it reports each team's per-row average (`Red` 90.0, `Blue` 60.0) instead of the requested totals. D filters to `region == "South"` — the opposite region from what was asked — picking up Bob, Eve, and Frank instead of Alice, Carol, and Dave, and so reporting `Blue` 95 and `Red` 75 for the wrong rows entirely.
