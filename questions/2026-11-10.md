## Q1. Building on Day 46's flattened team/score data, Grace rewrites a filter-then-sort as one parenthesized method chain instead of separate statements. What does this print? (Roadmap #38, #12)

```python
import pandas as pd

flat = pd.DataFrame({
    'name': ['Alice', 'Bob', 'Carol'],
    'team': ['Red', 'Blue', 'Red'],
    'stats.score': [88, 45, 92],
})

chained = (
    flat
    .query("team == 'Red'")
    .sort_values('stats.score', ascending=False)
    .reset_index(drop=True)
)
print(chained['name'].tolist())
```
A. `['Carol', 'Alice']` — the chain filters down to the two Red-team rows (Alice 88, Carol 92), then `sort_values('stats.score', ascending=False)` re-orders them by score descending, so Carol (92) comes before Alice (88); `.reset_index(drop=True)` just renumbers the index and doesn't affect which names get printed
B. `['Alice', 'Carol']` — wrongly assumes `ascending=False` leaves rows in their original ascending order rather than actually reversing the sort to descending
C. `AttributeError` — wrongly assumes `.query()` mutates `flat` in place and returns `None` (the way `sort_values(inplace=True)` would), so the next `.sort_values()` call in the chain would fail on a `None`
D. `['Alice', 'Bob', 'Carol']` — wrongly assumes `.query("team == 'Red'")` needs the column referenced without any quoting of the comparison value to actually filter, so the condition silently matches nothing and every row passes through unfiltered

## Q2. Spot the bug — Grace tries to build a running total across two chained `.assign()` calls, referencing the first new column from inside the second. What does this print? (Roadmap #38, #10)

```python
flat = pd.DataFrame({'name': ['Alice', 'Bob', 'Carol'], 'score': [88, 45, 92]})

try:
    chained = (
        flat
        .assign(bonus=flat['score'] * 0.1)
        .assign(total=flat['score'] + bonus)
    )
    print(chained['total'].tolist())
except Exception as e:
    print(type(e).__name__)
```
A. `NameError` — each `.assign()` keyword argument is evaluated immediately in the surrounding Python scope, not against the DataFrame the previous chain step produced; `bonus` was only ever created as a *column* inside that intermediate result, never as a plain variable, so referencing the bare name `bonus` raises `NameError`. The fix is `.assign(total=lambda d: d['score'] + d['bonus'])`, where the lambda receives the chain's current DataFrame as `d`
B. `[96.8, 49.5, 101.2]` — wrongly assumes `.assign()` automatically threads the previous step's output into later keyword-argument expressions by name, as if `bonus` referred to the column just created rather than requiring an explicit lambda to access it
C. `KeyError: 'bonus'` — wrongly assumes `bonus` is looked up as a column on `flat` (which was never given a `bonus` column), when the real failure is that `bonus` is being used as a plain Python name that was never assigned, which fails before any column lookup happens
D. `AttributeError` — wrongly assumes stacking two `.assign()` calls back-to-back in a chain isn't supported at all, when chaining multiple `.assign()` calls is normal; the actual problem is the undefined name `bonus`, not the chaining itself

## Q3. Contrasting with Q1, Grace checks whether writing a chain actually skips creating the same intermediate DataFrames that naming each step separately would. What does this print? (Roadmap #38)

```python
flat3 = pd.DataFrame({'score': [88, 45, 92]})

step1 = flat3.query('score > 50')
step2 = step1.sort_values('score')

chained3 = flat3.query('score > 50').sort_values('score')

print(step2.equals(chained3))
print(id(step1) == id(step2))
```
A. `True` then `False` — `.query()` and `.sort_values()` each always return a brand-new DataFrame, whether or not the intermediate result is bound to a name. `step2` and `chained3` hold equal data (`True`), but `step1` (the query's result) and `step2` (the sort's result) are two distinct objects in memory (`False`) regardless of chaining style — the one-line chain creates the exact same number of intermediate DataFrames, it just never names them
B. `True` then `True` — wrongly assumes `.sort_values()` sorts `step1` in place and hands back that very same object, as if chaining style (not binding intermediates to names) were what avoids creating a separate `step2` object, rather than each method call always producing a new one
C. `False` then `False` — wrongly assumes the one-line chain skips a step and reaches a different final result than doing the filter and sort in two separate statements, when both approaches run the identical sequence of operations and must agree
D. `False` then `True` — combines both mistakes: wrongly predicts the two results differ while also wrongly assuming `step1` and `step2` are the same object

## Q4. Building on Q1's chain, Grace wants to peek at an intermediate step without breaking the chain into separate statements, so she inserts a `.pipe()` call that prints the shape and passes the DataFrame through unchanged. What does this print? (Roadmap #38)

```python
flat4 = pd.DataFrame({'name': ['Alice', 'Bob', 'Carol'], 'team': ['Red', 'Blue', 'Red'], 'score': [88, 45, 92]})

def debug_shape(df):
    print(df.shape)
    return df

result = (
    flat4
    .query("team == 'Red'")
    .pipe(debug_shape)
    .sort_values('score', ascending=False)
)
print(result['name'].tolist())
```
A. `(2, 3)` then `['Carol', 'Alice']` — `.pipe(debug_shape)` calls `debug_shape` with whatever DataFrame the chain has produced so far (the already-filtered, 2-row, 3-column Red-team slice), prints its `.shape`, and returns that same DataFrame unchanged so the chain keeps going; `.sort_values('score', ascending=False)` then reorders those two rows, giving `['Carol', 'Alice']`
B. `['Carol', 'Alice']` only, with no shape printed — wrongly assumes `.pipe()` is purely a no-op placeholder in a chain that doesn't actually call the function it's given
C. `(3, 3)` then `['Carol', 'Alice']` — wrongly assumes `.pipe()` receives the *original* `flat4` DataFrame (all 3 rows) rather than the already-filtered result produced by `.query()` earlier in the same chain
D. `AttributeError` — wrongly assumes `.pipe()` requires its argument to be a method name string rather than accepting any plain callable that takes and returns a DataFrame

## Q5. Building on Day 43's named-aggregation syntax, Grace writes a full filter-free groupby summary as one chain: group, aggregate with named columns, then sort by one of those new names. What does this print? (Roadmap #38, #35, #13)

```python
df5 = pd.DataFrame({
    'team': ['Red', 'Red', 'Blue', 'Blue', 'Blue'],
    'score': [88, 92, 45, 50, 60],
})

chained5 = (
    df5
    .groupby('team')
    .agg(total_score=('score', 'sum'), avg_score=('score', 'mean'))
    .sort_values('total_score', ascending=False)
)
print(chained5.index.tolist())
print(chained5['total_score'].tolist())
```
A. `['Red', 'Blue']` then `[180, 155]` — `.groupby('team').agg(...)` sums each team's score (Red: 88+92=180, Blue: 45+50+60=155) into the new `total_score` column in the same step that creates `avg_score`; `.sort_values('total_score', ascending=False)` right after, still inside the chain, puts the larger total first, so Red comes before Blue
B. `['Blue', 'Red']` then `[155, 180]` — wrongly assumes `ascending=False` still sorts ascending (smallest total first) rather than reversing to descending (largest total first)
C. `['Red', 'Blue']` then values from the `avg_score` column instead — wrongly assumes `chained5['total_score']` can pick up values from whichever named-aggregation column happens to be computed first, rather than the one actually named `total_score`
D. Raises `KeyError` — wrongly assumes `sort_values` can't reference a column name that was just created by a named aggregation earlier in the very same chain, as if `total_score` weren't a "real" column yet for the next chained call to use

D wrongly assumes the quoted comparison value inside `.query()` fails to filter anything.
2. **A** — `.assign()`'s keyword arguments are evaluated in the surrounding Python scope immediately, not against the chain's intermediate DataFrame; `bonus` only ever exists as a column on that intermediate result, never as a plain variable, so the bare name `bonus` raises `NameError`. The fix is a lambda: `.assign(total=lambda d: d['score'] + d['bonus'])`. B wrongly assumes `.assign()` auto-threads prior columns into later arguments by name. C misattributes the failure to a column lookup on `flat` rather than an undefined Python name. D wrongly assumes chaining two `.assign()` calls isn't supported.
3. **A** — `.query()` and `.sort_values()` always return new DataFrame objects whether or not each result is bound to a name, so `step2` and `chained3` hold equal data (`True`) while `step1` and `step2` are still two distinct objects (`False`). Chaining doesn't skip creating intermediates — it just doesn't name them. B wrongly assumes `.sort_values()` reuses `step1`'s object. C wrongly assumes the chain reaches a different result than the two-statement version. D stacks both mistakes.
4. **A** — `.pipe(debug_shape)` passes the chain's current (already-filtered, 2-row) DataFrame into `debug_shape`, which prints `(2, 3)` and returns it unchanged so `.sort_values()` can still run on it, giving `['Carol', 'Alice']`.
