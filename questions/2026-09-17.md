Topics: Selection with `.loc` vs `.iloc` (Roadmap #8)

## Q1. Building on Day 8's name/age DataFrame, given

```python
import pandas as pd
data = {'name': ['Alice', 'Bob', 'Carol', 'Dave'], 'age': [25, 30, 35, 40]}
df = pd.DataFrame(data, index=[10, 20, 30, 40])
print(df.loc[20, 'name'])
```

What does this print?
A. 'Bob'
B. 'Carol'
C. Raises a KeyError, because `.loc` only works with the default RangeIndex labels (0, 1, 2, 3), not custom ones like 20
D. Raises an IndexError, because 20 is out of bounds for a 4-row DataFrame

## Q2. Using the same `df` from Q1, what does this print?

A. 'Bob'

## Q3. Still using the same `df`, what does this print?

A. 3
B. 2
C. 4

## Q4. Building directly on Q3, what does this print?

```python
print(len(df.iloc[0:2]))
```
A. 2
B. 3
C. 1

## Q5. Using the same `df`, which line raises an error?

A. `df.loc[30, 'age']`
B. `df.iloc[2, 'age']`
C. `df.loc[[10, 30], 'age']`
D. `df.iloc[[0, 2], 1]`

## Answer key

1. **A** — `.loc` looks up rows by **label**, and label `20` is Bob's row (the DataFrame's index is `[10, 20, 30, 40]`, not the default `0..3`), so `df.loc[20, 'name']` is `'Bob'`. B miscounts which row label `20` points to, as if labels were 1-indexed positions. C is wrong — `.loc` works with *any* index labels, custom or default; it isn't restricted to `RangeIndex`. D confuses `.loc` with `.iloc`: an out-of-bounds *position* raises `IndexError` on `.iloc`, but `20` is a perfectly valid *label* here, so `.loc` finds it without issue.
2. **A** — `.iloc` ignores labels entirely and uses pure 0-based **position**: position `1` is the second row (label `20`, Bob), and column position `0` is `'name'`, giving `'Bob'`. B is the row-0 value instead of row-1 — an off-by-one on the row position. C (`30`) comes from reading column position `0` as if it were `'age'` instead of `'name'` — a column-position mix-up. D is wrong because `.iloc` never raises `KeyError`; positional lookups only fail with `IndexError` when a position is out of range, and `1` is well within range here.
3. **A** — `.loc` slicing is **label-based and inclusive of the stop label**, so `df.loc[10:30]` includes every row from label `10` through label `30` (10, 20, 30) — 3 rows. B applies `.iloc`'s exclusive-of-stop slicing rule to `.loc` by mistake, the single most common `.loc`/`.iloc` mix-up. C wrongly includes row `40`, as if the slice went to the end of the DataFrame instead of stopping at `30`. D is wrong — `.loc` slices perfectly well on integer labels; it just uses label-inclusive semantics instead of `.iloc`'s position-exclusive ones.
4. **A** — `.iloc` slicing uses plain **positional**, Python-style semantics where the stop is **exclusive**, so `df.iloc[0:2]` takes positions 0 and 1 only — 2 rows. B is what you'd get by wrongly applying `.loc`'s inclusive-of-stop rule (from Q3) to `.iloc` — the mirror-image mistake of Q3's distractor B. C undercounts by assuming only the start position is included. D is wrong — `.iloc` slices are purely positional and never consult the index's labels, so there's nothing here for a `KeyError` to be about.
5. **B** — `.iloc` requires **integer positions for both axes**; passing the string `'age'` as a column selector is invalid for `.iloc` (label strings only work with `.loc`), so it raises a `ValueError`. A works fine — `.loc[30, 'age']` is a valid label/column lookup, returning `35`. C works fine — `.loc` accepts a *list* of labels (`[10, 30]`) to pick multiple rows by label, returning a Series. D works fine — `.iloc` accepts a *list* of integer positions (`[0, 2]`) just as happily as a single integer, returning the rows at positions 0 and 2.
