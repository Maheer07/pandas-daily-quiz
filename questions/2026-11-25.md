## Q1. Returning to Day 8 Q1's dict-of-equal-length-lists rule, Grace tries a mismatched dict first, then falls back to a list of lists instead. What does this print? (Roadmap #47, #7)

```python
import pandas as pd

try:
    wide = pd.DataFrame({'a': [1, 2, 3], 'b': [4, 5]})
except ValueError as e:
    print(type(e).__name__)

long = pd.DataFrame([[1, 4], [2, 5], [3]])
print(long)
print(long.dtypes.tolist())
```
A. `ValueError` then
```
   0    1
0  1  4.0
1  2  5.0
2  3  NaN
```
then `[dtype('int64'), dtype('float64')]` — A dict of lists requires every value to be the *same length*, since each key becomes a full column — `'a'` has 3 entries and `'b'` has 2, so pandas refuses immediately with `ValueError`, exactly the Day 8 Q1 rule. A list of lists is row-oriented instead: each inner list is one row, and pandas simply pads any row shorter than the widest one with `NaN` in the missing trailing column rather than raising — the third row only supplies column 0, so column 1 gets `NaN` there. That `NaN` upcasts column 1 to `float64`, while column 0 (no missing values) stays `int64`.
B. `ValueError` then `ValueError` — wrongly assumes a ragged list of lists is rejected the same way a mismatched dict is; row-oriented construction from a list of lists has no "all rows must match" rule the way dict-of-lists does — it pads instead.
C. (no error) then
```
   a  b
0  1  4.0
1  2  5.0
2  3  NaN
```
— wrongly assumes the mismatched dict silently pads like a list of lists would, as if dict and list inputs shared one lenient length rule; a dict of lists has always required exact length matches and raises immediately rather than guessing how to fill the gap.
D. `ValueError` then
```
   0  1
0  1  4
1  2  5
2  3  0
```
then `[dtype('int64'), dtype('int64')]` — gets the exception right but wrongly assumes the missing value in a short row is filled with `0` instead of `NaN`, which would also (wrongly) keep column 1 as `int64` instead of upcasting to `float64`.

## Q2. Building on Day 57 Q1's duplicate-labeled `bonus` Series, Grace tries folding that same kind of Series straight into a `DataFrame` instead of just adding it. What does this print? (Roadmap #47, #46, #6)

```python
import pandas as pd

rounds = pd.Series([88, 72, 95, 61], index=['r1', 'r2', 'r3', 'r4'])
bonus = pd.Series([2, 2, 5], index=['r3', 'r3', 'r4'])

try:
    combo = pd.DataFrame({'base': rounds, 'bonus': bonus})
except ValueError as e:
    print(type(e).__name__)

print(rounds + bonus)
```
A. `ValueError` then
```
r1     NaN
r2     NaN
r3    97.0
r3    97.0
r4    66.0
dtype: float64
```
— Day 57 Q1 showed that plain Series **arithmetic** (`+`) tolerates a duplicate-labeled operand just fine, pairing `rounds`'s single `'r3'` against each `'r3'` in `bonus` and producing a duplicate-labeled, sorted result. Building a **`DataFrame`** out of a dict of Series is a different operation: it must reindex every Series onto one shared row index, and pandas explicitly refuses to reindex onto (or from) an axis that has duplicate labels, raising `ValueError` before any alignment happens. The later `rounds + bonus` line is unaffected by that failed `DataFrame` attempt and reproduces Day 57 Q1's behavior exactly: `'r3'` appears twice (`95+2=97` both times), `'r4'` becomes `61+5=66`, and `'r1'`/`'r2'` (absent from `bonus`) become `NaN`.
B. (no error) then the same five-row result — wrongly assumes building a `DataFrame` from a dict of Series is just as tolerant of duplicate labels as plain Series arithmetic; `DataFrame` construction needs a single well-defined row index to align every column onto, so a duplicate-labeled input Series is rejected rather than silently handled.
C. `ValueError` then `ValueError` — wrongly assumes the later plain-Series addition also fails, as if duplicate labels were disallowed everywhere once they'd caused one `ValueError`; `Series + Series` alignment has never required unique labels, only `DataFrame` construction's reindex step does.
D. `ValueError` then
```
r1    NaN
r2    NaN
r3    97.0
r4    66.0
dtype: float64
```
— gets the exception right but wrongly collapses the duplicate `'r3'` down to one row in the addition result, as if duplicate labels got deduplicated before pairing; each `'r3'` in `bonus` pairs separately against `rounds`'s single `'r3'`, so the result keeps `'r3'` twice, not once.

## Q3. Grace builds a `DataFrame` from a NumPy grid two different ways, then mutates the *original* array afterward to see which one notices. What does this print? (Roadmap #47, #39)

```python
import numpy as np
import pandas as pd

grid = np.array([[10, 20], [30, 40]])
df_default = pd.DataFrame(grid)
grid[0, 0] = -1
print(df_default.iloc[0, 0])

grid2 = np.array([[10, 20], [30, 40]])
df_shared = pd.DataFrame(grid2, copy=False)
grid2[0, 0] = -1
print(df_shared.iloc[0, 0])
```
A. `10` then `-1` — `pd.DataFrame(grid)` with no `copy=` argument makes its own independent copy of the source array by default, in keeping with pandas 3.x's Copy-on-Write philosophy (the same spirit as Day 57 Q4's slice behavior) — so mutating `grid` afterward never reaches `df_default`, which still reads the original `10`. Passing `copy=False` explicitly opts out of that safety copy: `df_shared` keeps sharing memory with `grid2`, so the later mutation at `[0, 0]` writes straight through and `df_shared.iloc[0, 0]` reads back `-1`.
B. `-1` then `-1` — wrongly assumes the default constructor shares memory with its source array the way a basic NumPy slice/view would; `pd.DataFrame(ndarray)` copies by default specifically so later changes to the source don't silently leak into an already-built `DataFrame`.
C. `10` then `10` — wrongly assumes `copy=False` is only a hint pandas is free to ignore; it's an explicit request to skip the safety copy, and pandas honors it, leaving `df_shared` genuinely sharing memory with `grid2`.
D. `-1` then `10` — reverses which construction shares memory with its source: the default call is the one that copies (stays `10`), and `copy=False` is the one that shares (becomes `-1`), not the other way around.

## Q4. Returning to the `temps` Series from Days 56-57 and to Day 8 Q2's dict-of-Series alignment rule, Grace now folds two *partial* bonus Series into a `DataFrame` with it at once. What does this print? (Roadmap #47, #7, #6)

```python
import pandas as pd

temps = pd.Series([68, 72, 95, 61, 88], index=['mon', 'tue', 'wed', 'thu', 'fri'])
r2_bonus = pd.Series([1, 1], index=['wed', 'mon'])
r3_bonus = pd.Series([9], index=['thu'])

table = pd.DataFrame({'temp': temps, 'r2_bonus': r2_bonus, 'r3_bonus': r3_bonus})
print(table)
print(table.dtypes.tolist())
```

```
     temp  r2_bonus  r3_bonus

mon    68       1.0       NaN
thu    61       NaN       9.0
tue    72       NaN       NaN
wed    95       1.0       NaN
```
then `[dtype('int64'), dtype('float64'), dtype('float64')]` — Just like Day 8 Q2, building a `DataFrame` from a dict of Series aligns every Series onto the **sorted union** of all their labels, not any one Series's original order — so even though `temps` was given in `mon, tue, wed, thu, fri` order, the row index comes back alphabetically sorted (`fri, mon, thu, tue, wed`). Each bonus Series only covers 2 or 1 of the 5 labels, so every label it's missing becomes `NaN` in that column, which upcasts both bonus columns to `float64`; `temp` has no gaps and stays `int64`.
B.
```
     temp  r2_bonus  r3_bonus
mon    68       1.0       NaN
tue    72       NaN       NaN
wed    95       1.0       NaN
thu    61       NaN       9.0
fri    88       NaN       NaN
```
then `[dtype('int64'), dtype('float64'), dtype('float64')]` — correctly computes every value but wrongly keeps `temps`'s original `mon, tue, wed, thu, fri` row order; a dict of Series doesn't preserve any single input's order once it has to union multiple indices together — the result index comes back sorted, exactly as Day 8 Q2 showed.
C.
```
     temp  r2_bonus  r3_bonus
fri    88       NaN       NaN
mon    68       NaN       1.0
thu    61       9.0       NaN
tue    72       NaN       NaN
wed    95       1.0       NaN
```
then `[dtype('int64'), dtype('float64'), dtype('float64')]` — gets the sorted row order right but swaps which bonus column receives `'mon'`'s and `'thu'`'s values, as if `r2_bonus` and `r3_bonus` were aligned by position within each row instead of by their own label-to-value mapping (`r2_bonus['mon']=1`, `r3_bonus['thu']=9` — not the reverse).
D.
```
     temp  r2_bonus  r3_bonus
fri    88         0         0
mon    68         1         0
thu    61         0         9
tue    72         0         0
wed    95         1         0
```
then `[dtype('int64'), dtype('int64'), dtype('int64')]` — gets the sorted row order and the real values right but wrongly assumes labels missing from a bonus Series fill with `0` instead of `NaN`, which would also (wrongly) keep every column `int64` instead of upcasting the two bonus columns to `float64`.

## Q5. Tying Q1's length rule together with Day 8 Q1, Grace adds a flat per-row fee as a bare scalar instead of a list, then tries the same trick with a second list column. What does this print? (Roadmap #47, #7)

```python
import pandas as pd

flat = pd.DataFrame({'id': [1, 2, 3], 'flat_fee': 100})
print(flat)

try:
    mismatched = pd.DataFrame({'id': [1, 2, 3], 'fee': [100, 100]})
except ValueError as e:
    print(type(e).__name__)
```
A.
```
   id  flat_fee
0   1       100
1   2       100
2   3       100
```
then `ValueError` — A bare scalar value in a dict passed to `pd.DataFrame` isn't a sized sequence that has to match any other column's length — pandas just **broadcasts** it down every row, so `flat_fee` becomes `100` three times to match `id`'s 3 rows. That broadcasting exemption doesn't extend to a second *list*, though: once both `'id'` and `'fee'` supply list-like sequences, Q1's dict-of-lists rule applies again, and `[100, 100]` (length 2) doesn't match `id`'s length 3, raising the same `ValueError` as Q1's mismatched dict.
B.
```
   id  flat_fee
0   1       100
1   2       100
2   3       100
```
then (no error, `fee` built successfully) — wrongly assumes a second *list* gets the same broadcasting leniency as a scalar, as if pandas repeated or padded a short list the way it repeats a scalar; a list is a sized sequence and must match the other columns' length exactly, just like Day 8 Q1 and Q1 above.
C. `ValueError` on the first line, then nothing printed for the second — wrongly assumes a scalar value must also match the other columns' length, as if `100` needed to be wrapped in a 3-element list first; a bare scalar has no length of its own to conflict with anything, so pandas broadcasts it without complaint.
D.
```
   id  flat_fee
0   1       100
1   2       100
2   3       100
```
then `ValueError` is right, but the reasoning given is that `fee`'s list is too *long* relative to `id` — this gets the exception right for the wrong reason: `[100, 100]` has length 2, which is *shorter* than `id`'s length 3, not longer; either direction of mismatch raises the same error, but miscounting which side is short doesn't reflect tracing the actual lengths.

## Answer key

1. **A** — A dict of lists requires equal-length values and raises `ValueError` on a mismatch (Day 8 Q1's rule); a list of lists is row-oriented and pads short rows with `NaN` instead, upcasting only the affected column to `float64`. B wrongly assumes the ragged list of lists also raises. C wrongly assumes the mismatched dict pads instead of raising. D wrongly fills the gap with `0` and keeps the column `int64`.
2. **A** — Series arithmetic (`+`) tolerates a duplicate-labeled operand (Day 57 Q1), but building a `DataFrame` from a dict of Series requires reindexing onto one shared index and explicitly rejects a duplicate-labeled input with `ValueError`. The later `rounds + bonus` line is unaffected and reproduces Day 57 Q1's duplicate-row, sorted-alignment result. B wrongly assumes `DataFrame` construction is as tolerant as arithmetic. C wrongly assumes the later addition also raises. D wrongly collapses the duplicate `'r3'` row.
3. **A** — `pd.DataFrame(ndarray)` copies its source by default, so later mutating the original array doesn't reach the `DataFrame` (`10`); `copy=False` opts out, so the `DataFrame` keeps sharing memory and the later mutation reaches it (`-1`). B wrongly assumes the default shares memory. C wrongly assumes `copy=False` is ignored. D reverses which construction copies vs. shares.
4. **A** — A dict of Series aligns onto the sorted union of all labels (Day 8 Q2's rule), not any one Series's original order; labels missing from a bonus Series become `NaN`, upcasting those columns to `float64`. B wrongly keeps `temps`'s original row order. C swaps which bonus column receives which label's value. D wrongly fills missing entries with `0` and keeps every column `int64`.
5. **A** — A bare scalar broadcasts down every row regardless of length; a second list-like column is still bound by the dict-of-lists equal-length rule and raises `ValueError` on a mismatch, same as Q1. B wrongly extends scalar-style broadcasting to a list. C wrongly assumes a scalar must also match length. D gets the exception right but misidentifies which side of the length mismatch is shorter.
