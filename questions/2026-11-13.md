## Q1. Grace receives a fresh nested payload — one entry per match with a list of per-team results — and normalizes it two ways: without `record_path`, then with it. What does this print? (Roadmap #37)

```python
import pandas as pd

matches = [
    {'match_id': 1, 'date': '2026-11-01', 'teams': [{'name': 'Red', 'score': 88}, {'name': 'Blue', 'score': 45}]},
    {'match_id': 2, 'date': '2026-11-08', 'teams': [{'name': 'Red', 'score': 92}, {'name': 'Blue', 'score': 50}]},
]

no_path = pd.json_normalize(matches)
print(no_path.columns.tolist())
print(type(no_path.loc[0, 'teams']).__name__)

flat = pd.json_normalize(matches, record_path='teams', meta=['match_id', 'date'])
print(flat.shape)
print(flat['name'].tolist())
```
A. `['match_id', 'date', 'teams']` then `'list'` then `(4, 4)` then `['Red', 'Blue', 'Red', 'Blue']` — without `record_path`, `json_normalize` only flattens nested *dicts* into dotted columns; a nested *list* like `teams` is left completely untouched as a single Python object per row, so `no_path` keeps one row per match with a raw `list` sitting in the `'teams'` column. Passing `record_path='teams'` explicitly tells it to explode that list into its own rows (one per team per match = 4 rows total), while `meta=['match_id', 'date']` carries the outer fields along onto each exploded row, preserving each team's original order within its match.
B. `['match_id', 'date', 'name', 'score']` then `'dict'` then `(4, 4)` then `['Red', 'Blue', 'Red', 'Blue']` — wrongly assumes plain `json_normalize(matches)` auto-explodes the nested `teams` list and flattens its dict keys up to the top level on its own; without `record_path`, a nested list is never auto-exploded, so the column stays named `'teams'` holding a `list`, not separate `name`/`score` columns.
C. `['match_id', 'date', 'teams']` then `'list'` then `(2, 3)` then `['Red', 'Blue']` — wrongly assumes that forgetting `meta=` would make `record_path='teams'` produce *fewer* rows (one per match) instead of properly exploding to one row per team; `record_path` alone always explodes to one row per team (4 total) regardless of whether `meta` is supplied — `meta` only controls which extra columns get attached, not how many rows result.
D. `['match_id', 'date', 'teams']` then `'list'` then `(4, 4)` then `['Blue', 'Red', 'Blue', 'Red']` — gets the shapes and dtype right but wrongly assumes `json_normalize` reorders or alphabetizes the exploded records within each match; it preserves each team's original order exactly as listed, and Red was listed before Blue in both matches.

## Q2. Spot the bug — Grace tries to extend the method-chaining habit from Day 47 but forgets what `inplace=True` hands back. What does this print? (Roadmap #38)

```python
import pandas as pd

df = pd.DataFrame({'name': ['Red', 'Blue', 'Red', 'Blue'], 'score': [88, 92, 45, 50]})

try:
    chained = (
        df
        .query("score > 50")
        .sort_values('score', inplace=True)
        .reset_index(drop=True)
    )
    print(chained['name'].tolist())
except Exception as e:
    print(type(e).__name__)
```
A. `AttributeError` — `sort_values(..., inplace=True)` sorts the DataFrame produced by `.query()` in place and returns `None`, exactly like `inplace=True` does everywhere else in pandas, instead of handing back the sorted DataFrame. The chain then tries to call `.reset_index(drop=True)` on that `None`, which has no such attribute, raising `AttributeError`. Every step in a chain must return an actual DataFrame for the next step to call a method on — `inplace=True` breaks that contract.
B. `['Red', 'Blue']` — wrongly assumes `inplace=True` sorts the intermediate DataFrame and *still* returns it so the chain can continue, as if `inplace=True` were just a flag that mutates and also returns, rather than one that mutates and returns `None`.
C. `['Blue', 'Red']` — makes the same wrong assumption as B about `inplace=True` returning the chain's DataFrame, and additionally assumes the sort landed in descending order, when `sort_values` defaults to ascending.
D. `TypeError` — wrongly names the exception; calling `.reset_index` on `None` is an attribute-lookup failure (`AttributeError`), not a type mismatch.

## Q3. Contrasting with Day 48's lesson that Copy-on-Write makes every filter independent, Grace checks whether that holds for both "fancy" (list-based) and plain slice-based `.iloc` indexing. What does this print? (Roadmap #39)

```python
import pandas as pd
import warnings

df = pd.DataFrame({'name': ['Alice', 'Bob', 'Carol', 'Dave'], 'score': [88, 45, 92, 50]})

fancy = df.iloc[[0, 2]]
basic = df.iloc[0:2]

with warnings.catch_warnings(record=True) as caught1:
    warnings.simplefilter('always')
    fancy['score'] = 0

with warnings.catch_warnings(record=True) as caught2:
    warnings.simplefilter('always')
    basic['score'] = 0

print('fancy warn:', caught1[0].category.__name__ if caught1 else 'none')
print('basic warn:', caught2[0].category.__name__ if caught2 else 'none')
print(fancy['score'].tolist())
print(basic['score'].tolist())
print(df['score'].tolist())
```
A. `none` then `none` then `[0, 0]` then `[0, 0]` then `[88, 45, 92, 50]` — under Copy-on-Write, pandas doesn't distinguish "fancy" (list-based) from "basic" (slice-based) `.iloc` selections the way old pandas's views-vs-copies rules did; every selection, whichever indexing style produced it, is its own independent object from the moment it's created. Both `fancy['score'] = 0` and `basic['score'] = 0` are single, direct assignments onto an already-named variable (not a chained double-indexing expression), so no `ChainedAssignmentError` fires either way — each assignment just mutates that independent copy, leaving `df` completely untouched.
B. `ChainedAssignmentError` then `none` then the same values otherwise — wrongly carries over the old pre-CoW distinction where basic slices could share memory with the original while fancy (list) indexing couldn't, flagging fancy indexing as the "risky" pattern; under CoW neither one shares memory, and neither assignment is a chained expression to begin with, so neither warns.
C. `none` then `none` then `[0, 0]` then `[0, 0]` then `[0, 45, 92, 0]` — wrongly assumes `basic = df.iloc[0:2]` is still a memory-sharing view onto `df`, the way a basic slice could be before Copy-on-Write, so mutating `basic` would also silently mutate the first two entries of `df`.
D. `none` then `none` then `[0, 0]` then `[45, 92]` then `[88, 45, 92, 50]` — gets the warnings and `df` right but wrongly assumes `basic['score'] = 0` silently failed to change `basic`, leaving it at its original (pre-slice) values, rather than having actually become `[0, 0]`.

## Q4. Continuing from Q1's flattened match data, Grace merges it against a team roster to add each team's region — first with `validate='many_to_one'`, then mistakenly retries with `validate='one_to_one'`. What does this print? (Roadmap #40, #37, #15)

```python
roster = pd.DataFrame({'name': ['Red', 'Blue', 'Green'], 'region': ['North', 'South', 'East']})

merged = flat.merge(roster, on='name', how='left', validate='many_to_one', indicator=True)
print(merged['_merge'].tolist())
print(merged['region'].tolist())

try:
    flat.merge(roster, on='name', how='left', validate='one_to_one', indicator=True)
    print('one_to_one ok')
except Exception as e:
    print(type(e).__name__)
```
A. `['both', 'both', 'both', 'both']` then `['North', 'South', 'North', 'South']` then `MergeError` — `'name'` repeats in `flat` (Red and Blue each appear once per match, so twice overall) but is unique in `roster`, which is exactly what `validate='many_to_one'` checks for ("many" on the left, "one" on the right) — it passes, and region broadcasts correctly onto every row in `flat`'s original order. Retrying with `validate='one_to_one'` additionally requires the *left* key to be unique too; since `'name'` repeats in `flat`, that stricter check fails and raises `MergeError`.
B. `MergeError` then (nothing further) — wrongly assumes `validate='many_to_one'` requires uniqueness on the "many" (left) side rather than the "one" (right) side, predicting the first merge fails when it's actually the second, stricter `validate='one_to_one'` call that fails.
C. `['both', 'both', 'both', 'both']` then `['North', 'South', 'North', 'South']` then `one_to_one ok` — wrongly assumes `validate='one_to_one'` only checks that every key *has a match* between the two frames (which it does here), rather than also requiring the key to be non-duplicated within *each* frame — `'name'` repeating in `flat` is enough to fail it regardless of whether every row finds a match.
D. `['both', 'both', 'both', 'both']` then `['North', 'North', 'South', 'South']` then `MergeError` — gets the merge indicator and the exception right but wrongly assumes the merge groups or reorders rows by `name`, rather than preserving `flat`'s original row order (match 1's Red/Blue, then match 2's Red/Blue) when attaching `region`.

## Q5. To cap off the roadmap, Grace chains a `.pipe()` debug step onto Q1's flattened data, adds each match's score share as a percentage, then keeps only the team with the majority share — deliberately referencing the chain's *starting* variable (not a lambda) in one `.assign()` step, following Day 47's lesson about when that's actually safe. What does this print? (Roadmap #40, #38, #37)

```python
def show_cols(d):
    print(sorted(d.columns.tolist()))
    return d

result = (
    flat
    .pipe(show_cols)
    .assign(match_total=flat.groupby('match_id')['score'].transform('sum'))
    .assign(pct=lambda d: (d['score'] / d['match_total'] * 100).round(1))
    .query('pct > 50')
    .reset_index(drop=True)
)
print(result['name'].tolist())
print(result['pct'].tolist())
print(flat.columns.tolist())
```
A. `['date', 'match_id', 'name', 'score']` then `['Red', 'Red']` then `[66.2, 64.8]` then `['name', 'score', 'match_id', 'date']` — `.pipe(show_cols)` runs first, printing `flat`'s own columns sorted alphabetically and passing `flat` through completely unchanged. The eager reference `flat.groupby('match_id')['score'].transform('sum')` is safe here specifically *because* `.pipe()` never altered `flat`'s shape or columns — computing `match_total` straight from the outer variable `flat` gives the exact same per-match totals (133 and 142) as computing it from whatever the chain currently holds. That's different from Day 47's `.assign(total=flat['score'] + bonus)` bug, which referenced a column (`bonus`) that only existed on an *intermediate chain result*, never as a plain variable — here `flat` genuinely is a plain variable, unmodified by any prior step, so no such problem arises. Red takes the majority share in both matches (88/133≈66.2%, 92/142≈64.8%), and `.assign()` never mutates its input, so `flat.columns` still shows its original four columns in their original order.
B. `['date', 'match_id', 'name', 'score']` then `NameError` — wrongly assumes the eager `flat` reference breaks the same way Day 47's `bonus` reference did; those are different cases — `bonus` was never a plain Python variable at all (only a column on an intermediate result), while `flat` genuinely is a variable already in scope that `.pipe()` left untouched, so referencing it eagerly works fine.
C. `['name', 'score', 'match_id', 'date']` then `['Red', 'Red']` then `[66.2, 64.8]` then `['name', 'score', 'match_id', 'date']` — gets everything else right but wrongly assumes `show_cols` prints the columns in their original insertion order, forgetting that `show_cols` explicitly calls `sorted(...)` before printing.
D. `['date', 'match_id', 'name', 'score']` then `['Red', 'Red']` then `[66.2, 64.8]` then `['name', 'score', 'match_id', 'date', 'match_total', 'pct']` — gets the printed shares right but wrongly assumes the chain's `.assign()` calls permanently added `match_total`/`pct` back onto `flat` itself; `.assign()` always returns a brand-new DataFrame and never mutates the object it's called on, so `flat` keeps exactly its original four columns throughout.
