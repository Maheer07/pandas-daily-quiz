## Q1. Building on Day 47's flat team/score DataFrame, Grace tries to zero out every Red-team score using a single chained-indexing expression instead of `.loc`. What does this print? (Roadmap #39, #38)

```python
import pandas as pd
import warnings

flat = pd.DataFrame({
    'name': ['Alice', 'Bob', 'Carol'],
    'team': ['Red', 'Blue', 'Red'],
    'stats.score': [88, 45, 92],
})

with warnings.catch_warnings(record=True) as caught:
    warnings.simplefilter('always')
    flat[flat['team'] == 'Red']['stats.score'] = 0

print(caught[0].category.__name__ if caught else 'no warning')
print(flat['stats.score'].tolist())
```
A. `ChainedAssignmentError` then `[0, 45, 0]` — wrongly assumes that even though pandas warns about the risky pattern, the write still somehow lands on `flat` despite the warning explicitly existing to flag that it doesn't
B. `ChainedAssignmentError` then `[88, 45, 92]` — `flat[flat['team'] == 'Red']` builds a brand-new, independent DataFrame (every selection behaves as its own copy under Copy-on-Write), and `['stats.score'] = 0` then assigns onto *that* throwaway object, not `flat`. Pandas detects this one-expression chained pattern and raises `ChainedAssignmentError` as a warning to flag that the assignment is pointless — `flat` itself is never touched
C. `no warning` then `[0, 45, 0]` — wrongly assumes chained indexing like this is silently fine under Copy-on-Write, both skipping the warning and successfully mutating `flat`
D. `SettingWithCopyWarning` then `[88, 45, 92]` — gets the "nothing actually changes" part right but names the wrong warning class; `SettingWithCopyWarning` was pandas's pre-3.0 warning for this exact chained-assignment pattern before Copy-on-Write became mandatory — current pandas raises `ChainedAssignmentError` instead

## Q2. Continuing directly from Q1 — since the chained assignment never actually changed `flat` — Grace redoes the same zero-out as a single `.loc` call instead. What does this print? (Roadmap #39)

```python
flat.loc[flat['team'] == 'Red', 'stats.score'] = 0
print(flat['stats.score'].tolist())
```
A. `[0, 45, 0]` — `.loc[boolean_mask, column_label]` performs the row filter and the column assignment as one single indexing operation, so pandas can trace the write straight back to `flat` itself — no intermediate throwaway object, no warning, and both Red rows (Alice at index 0, Carol at index 2) get zeroed
B. `[88, 45, 92]` — wrongly assumes `.loc[mask, col] = val` is just as "chained" as `df[mask][col] = val` from Q1 and also fails silently
C. Raises `KeyError` — wrongly assumes `.loc` needs `'stats.score'` written as a tuple label because it contains a dot, rather than treating it as one ordinary (if oddly named) column label
D. `[0, 45, 92]` — wrongly zeroes only the first Red row (Alice) and misses Carol's, as if the boolean mask stopped matching after its first `True`

## Q3. Spot the bug — Grace assumes that spreading the same filter-then-assign across two separate statements (rather than one chained expression like Q1) makes it safe. She assigns the filtered rows to a named variable first, then uses `.loc` on that variable. What does this print? (Roadmap #39)

```python
import warnings

flat2 = pd.DataFrame({
    'name': ['Alice', 'Bob', 'Carol'],
    'team': ['Red', 'Blue', 'Red'],
    'stats.score': [88, 45, 92],
})

with warnings.catch_warnings(record=True) as caught:
    warnings.simplefilter('always')
    red_only = flat2[flat2['team'] == 'Red']
    red_only.loc[:, 'stats.score'] = 0

print(caught[0].category.__name__ if caught else 'no warning')
print(red_only['stats.score'].tolist())
print(flat2['stats.score'].tolist())
```
A. `no warning` then `[0, 0]` then `[88, 45, 92]` — because the filter and the assignment happen as two separate statements instead of one chained expression, pandas has no single call to flag, so `ChainedAssignmentError` never fires here. But Copy-on-Write still means `red_only = flat2[...]` produced its own independent object the instant it was created, so `.loc` on `red_only` only ever mutates that separate copy — `flat2` was never going to change either way, warned or not
B. `ChainedAssignmentError` then `[0, 0]` then `[88, 45, 92]` — wrongly assumes pandas still raises the same warning even when the risky pattern is spread across two statements instead of written as one chained expression
C. `no warning` then `[0, 0]` then `[0, 45, 0]` — wrongly treats "no warning fired" as proof the write reached `flat2`, when the absence of a warning here just means pandas had no single chained call to flag — `red_only` was already an independent object before `.loc` ever ran
D. `no warning` then `[88, 45, 92]` then `[88, 45, 92]` — wrongly assumes `.loc[:, 'stats.score'] = 0` silently fails to modify even `red_only` itself

## Q4. Contrasting with Q1-Q3's filtering, Grace checks whether plain `=` assignment of a whole DataFrame behaves like those independent copies, or like a shared reference — compared against calling `.copy()` explicitly. What does this print? (Roadmap #39)

```python
flat3 = pd.DataFrame({'name': ['Alice', 'Bob'], 'stats.score': [88, 45]})
same_ref = flat3
same_ref.loc[0, 'stats.score'] = 0

flat4 = pd.DataFrame({'name': ['Alice', 'Bob'], 'stats.score': [88, 45]})
explicit_copy = flat4.copy()
explicit_copy.loc[0, 'stats.score'] = 0

print(flat3['stats.score'].tolist())
print(flat4['stats.score'].tolist())
print(same_ref is flat3)
```
A. `[0, 45]` then `[88, 45]` then `True` — `same_ref = flat3` doesn't create a new object at all, it's just another name bound to the exact same DataFrame (`same_ref is flat3` is `True`), so mutating through `same_ref` mutates `flat3` itself. `flat4.copy()`, by contrast, really does build an independent object, so mutating `explicit_copy` leaves `flat4` untouched. Unlike Q1-Q3's boolean-mask filtering, plain `=` assignment of a whole object was never a copying operation, Copy-on-Write or not
B. `[88, 45]` then `[88, 45]` then `True` — wrongly assumes Copy-on-Write makes even a bare `same_ref = flat3` assignment create an independent copy, when plain variable assignment never copies anything to begin with
C. `[0, 45]` then `[0, 45]` then `True` — wrongly assumes `.copy()` is a shallow no-op that still shares the same underlying data as the original, so mutating `explicit_copy` would also show up on `flat4`
D. `[0, 45]` then `[88, 45]` then `False` — gets the data right but wrongly assumes `same_ref = flat3` still produces a distinct object with its own identity, when `is` confirms they're the literal same object

## Q5. Building on Q4's views-vs-copies theme, Grace pulls a Series' underlying array out with `.to_numpy()` and tries to tweak a value in place. What does this print? (Roadmap #39)

```python
scores = pd.Series([88, 45, 92])
arr = scores.to_numpy()

try:
    arr[0] = 999
    print('mutated:', scores.tolist())
except Exception as e:
    print(type(e).__name__)

writable_copy = scores.to_numpy().copy()
writable_copy[0] = 999
print(scores.tolist())
print(writable_copy.tolist())
```
A. `ValueError` then `[88, 45, 92]` then `[999, 45, 92]` — under Copy-on-Write, `.to_numpy()` (and `.values`) hands back a read-only array by default, specifically so an in-place mutation can't silently corrupt the Series' real data behind pandas' back; writing to `arr[0]` raises `ValueError: assignment destination is read-only`. Calling `.copy()` on that array produces a genuinely independent, writable buffer, so mutating `writable_copy` changes only `writable_copy`, leaving `scores` exactly as it started
B. `mutated: [999, 45, 92]` then `[999, 45, 92]` then `[999, 45, 92]` — wrongly assumes `.to_numpy()` still returns a plain writable view sharing memory with the Series, and that mutating it mutates `scores` too
C. `ValueError` then `[88, 45, 92]` then `[88, 45, 92]` — correctly gets the read-only array right but wrongly assumes calling `.copy()` on top of an already-read-only array stays read-only too, so the second mutation attempt also silently fails to change `writable_copy`
D. `TypeError` then `[88, 45, 92]` then `[999, 45, 92]` — gets everything else right but names the wrong exception type; NumPy raises `ValueError`, not `TypeError`, for writing into a read-only array
