## Q1. Grace revisits Day 17's groupby with multiple aggregations, comparing the plain multi-function `.agg()` style against the newer named-aggregation style for clearer column labels. What does this print? (Roadmap #35, #14)

```python
import pandas as pd

data6 = {'name': ['Alice', 'Bob', 'Carol', 'Dave', 'Eve', 'Frank'],
         'team': ['Red', 'Blue', 'Red', 'Blue', 'Red', 'Blue'],
         'region': ['North', 'South', 'North', 'North', 'South', 'South'],
         'score': [88, 45, 92, 60, 75, 50]}
df6 = pd.DataFrame(data6, index=[100, 101, 102, 103, 104, 105])

plain = df6.groupby('team')['score'].agg(['mean', 'max'])
named = df6.groupby('team').agg(avg_score=('score', 'mean'), top_score=('score', 'max'))
print(plain.columns.tolist())
print(named.columns.tolist())
```
A. `['mean', 'max']` then `['avg_score', 'top_score']` — `df6.groupby('team')['score']` selects a single column first, so `.agg(['mean', 'max'])` returns flat, single-level columns named directly after the functions. Named aggregation always produces flat columns too, but uses exactly the keyword names given (`avg_score`, `top_score`) instead of the function names
B. `['avg_score', 'top_score']` then `['mean', 'max']` — swaps which style produces which labels, as if the plain list-of-functions form already picked up custom names and the named-aggregation form fell back to the raw function names
C. `[('score', 'mean'), ('score', 'max')]` then `['avg_score', 'top_score']` — wrongly assumes selecting a single column before `.agg()` still produces `MultiIndex` columns the way aggregating *multiple* columns at once (e.g. `df6.groupby('team').agg(['mean', 'max'])` with no column selected) would
D. `['mean', 'max']` then `[('score', 'avg_score'), ('score', 'top_score')]` — gets the plain case right but wrongly assumes named aggregation still tags each output column with its source column as a tuple, rather than using exactly the keyword name given

## Q2. Building on Q1's named-aggregation syntax, Grace writes the same idea with the fully explicit `pd.NamedAgg` form and adds a second, non-numeric aggregation to grab each team's first-listed region. What does this print? (Roadmap #35)

```python
summary2 = df6.groupby('team').agg(
    total_score=pd.NamedAgg(column='score', aggfunc='sum'),
    home_region=pd.NamedAgg(column='region', aggfunc='first'),
)
print(summary2.loc['Red', 'total_score'], summary2.loc['Red', 'home_region'])
print(summary2.loc['Blue', 'total_score'], summary2.loc['Blue', 'home_region'])
```
A. `255 North` then `155 South` — `pd.NamedAgg(column=..., aggfunc=...)` is just the fully explicit form of Q1's `name=(column, aggfunc)` tuple shorthand. `aggfunc='sum'` totals each group's scores (Red: `88+92+75=255`, Blue: `45+60+50=155`). `aggfunc='first'` returns the value from the *first row encountered in that group's original order* — Red's first row is Alice (`North`), Blue's first row is Bob (`South`)
B. `255 North` then `155 North` — wrongly assumes `aggfunc='first'` returns the alphabetically smallest region in the group rather than the first row by original order; this happens to match for Red (`North` is both alphabetically first and row-order first) but is wrong for Blue, where row-order-first is `South`, not the alphabetically-first `North`
C. Raises `AttributeError` — wrongly assumes `pd.NamedAgg` isn't part of pandas' actual public API and that only the plain tuple shorthand from Q1 is valid
D. `255 South` then `155 South` — mixes up `aggfunc='first'` with `aggfunc='last'`; Red's *last* row is Eve (`South`) and Blue's *last* row is Frank (`South`), not what `'first'` actually returns

## Q3. Spot the bug — Grace wants both the mean and max score per team as clearly named columns, but accidentally reuses the same keyword twice. What does this print? (Roadmap #35)

```python
try:
    bad = df6.groupby('team').agg(
        score=('score', 'mean'),
        score=('score', 'max'),
    )
    print(bad)
except Exception as e:
    print(type(e).__name__)
```
A. Nothing from the `try`/`except` ever runs — repeating the keyword `score=` twice in one call is rejected by *Python itself* while parsing the code (`SyntaxError: keyword argument repeated: 'score'`), before execution ever reaches the `try` block, so wrapping it in `try/except Exception` can't catch it
B. `AttributeError` — wrongly assumes pandas raises a runtime error for the duplicate keyword, when the problem is caught by Python's own parser before pandas ever sees the call
C. A DataFrame showing each team's **max** score under a column named `score` — wrongly assumes Python allows duplicate keyword arguments and just keeps the last one, the way a duplicate dict key would silently overwrite the first
D. `TypeError` — wrongly assumes `.agg()` itself validates keyword uniqueness at call time and raises its own error, rather than this being rejected earlier, at parse time, by Python itself

## Q4. Grace lines up three named aggregations — a count, a sum, and a mean — in a specific keyword order, then checks both the resulting column order and what happens when she pulls one team's row out as a Series spanning all three columns. What does this print? (Roadmap #35, #13)

```python
summary3 = df6.groupby('team').agg(
    n=('name', 'count'),
    total=('score', 'sum'),
    avg=('score', 'mean'),
)
print(summary3.columns.tolist())
print(summary3.loc['Blue'].tolist())
```
A. `['n', 'total', 'avg']` then `[3.0, 155.0, 51.666666666666664]` — named-aggregation output columns follow the order the keyword arguments were given in, not alphabetical order. But `summary3.loc['Blue']` pulls out a *row* spanning columns of different original dtypes (`n` and `total` are ints, `avg` is a float); pandas has to give that single returned Series one common dtype, so it upcasts the whole row to `float64` — even the integer-valued `n` and `total` print as `3.0` and `155.0`, not as plain ints
B. `['avg', 'n', 'total']` then `[51.666666666666664, 3.0, 155.0]` — wrongly assumes named-aggregation columns get sorted alphabetically by name rather than kept in keyword-argument order
C. `['n', 'total', 'avg']` then `[3, 155, 51.666666666666664]` — gets the column order right but wrongly assumes `.loc` row-selection preserves each column's own original dtype, rather than upcasting the whole returned row to one common dtype
D. `['n', 'total', 'avg']` then `[3.0, 155.0, 51.67]` — gets the order and the int-to-float promotion right but wrongly assumes Python's default float printing rounds to 2 decimal places rather than showing full precision

## Q5. Spot the surprise — Grace wants a flat summary with `team` as a normal column instead of the index, and tries adding it as a named aggregation on the grouping column itself, rather than calling `.reset_index()`. What does this print? (Roadmap #35)

```python
summary4 = df6.groupby('team').agg(
    team=('team', 'first'),
    avg_score=('score', 'mean'),
)
print(summary4.columns.tolist())
print(summary4.index.name)
```
A. `['team', 'avg_score']` then `team` — no error; the groupby key `'team'` becomes the result's **index name**, which lives in a completely separate namespace from its **columns**. So creating an aggregated column also named `'team'` doesn't clash with anything, and referencing the `'team'` column inside `.agg()` is legal even though you grouped by it — groupby doesn't remove the key column from the underlying data, it just becomes the result's index by default. `aggfunc='first'` on `'team'` just returns each group's own (identical, repeated) label back
B. Raises `ValueError` about an ambiguous or duplicate label `'team'` — wrongly assumes the groupby key's index name and an output column can't share the same string
C. Raises `KeyError` — wrongly assumes that once you group by a column, that column is dropped from the DataFrame entirely and can no longer be referenced inside `.agg()`
D. `['team', 'avg_score']` then `None` — gets the columns right but wrongly assumes adding a column also named `'team'` has the side effect of clearing the index's own `.name`, when the two are unrelated

## Answer key

1. **A** — `df6.groupby('team')['score']` narrows to a single column first, so `.agg(['mean', 'max'])` returns flat columns named directly after the functions: `['mean', 'max']`. Named aggregation (`avg_score=(...)`, `top_score=(...)`) always produces flat columns too, but under exactly the keyword names given: `['avg_score', 'top_score']`. B swaps which style produces which labels. C wrongly imports the `MultiIndex`-column behavior of aggregating *multiple* columns at once into this single-column case. D correctly reads the plain case but wrongly assumes named aggregation still tags columns with their source column as a tuple.
2. **A** — `pd.NamedAgg(column=..., aggfunc=...)` is the explicit form of the tuple shorthand. `aggfunc='sum'` gives Red `255` and Blue `155`. `aggfunc='first'` returns the value from each group's first row *by original row order* — Red's first row is Alice (`North`), Blue's is Bob (`South`). B wrongly treats `'first'` as "alphabetically smallest," which coincidentally matches for Red but gives `North` instead of `South` for Blue. C wrongly claims `pd.NamedAgg` isn't real pandas API. D confuses `'first'` with `'last'`.
3. **A** — Python rejects a function call with the same keyword argument given twice at *parse time*, raising `SyntaxError: keyword argument repeated` before the module even finishes compiling — so the surrounding `try/except Exception` never gets a chance to run at all. B and D misattribute this to a runtime error from pandas instead of a compile-time error from Python itself. C wrongly assumes duplicate keywords are silently allowed, with the later one overwriting the earlier one.
4. **A** — Named-aggregation columns keep the order their keyword arguments were written in: `['n', 'total', 'avg']`. Selecting `summary3.loc['Blue']` returns a single Series spanning columns of mixed original dtypes (two ints, one float), forcing pandas to upcast the whole row to one common `float64` dtype — so even `n` and `total` print as `3.0` and `155.0`. B wrongly assumes alphabetical column sorting. C correctly orders the columns but wrongly assumes `.loc` row-selection preserves each column's own dtype rather than unifying the row's dtype. D gets the promotion right but wrongly assumes default float printing rounds to 2 decimals.
5. **A** — The groupby key's **index name** and a DataFrame's **column labels** are separate namespaces, so having both named `'team'` causes no conflict. Grouping by a column doesn't remove it from the underlying data either, so `('team', 'first')` is a perfectly legal aggregation that just echoes each group's own label back. B and C both invent restrictions pandas doesn't actually enforce here. D correctly gets the columns but wrongly assumes adding a same-named column resets the index's own `.name` attribute, which is unaffected.
