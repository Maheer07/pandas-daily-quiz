## Q1. Grace reuses Day 52's two-team score grid and tries to add a per-column bonus, then a differently-shaped one. What does this print? (Roadmap #43, #3)

```python
import numpy as np

grid = np.array([[88, 92, 79], [45, 50, 60]])  # shape (2, 3): 2 teams, 3 rounds
bonus = np.array([10, 0, -5])                  # shape (3,): one bonus per round

print((grid + bonus).tolist())

try:
    print((grid + np.array([10, 0])).tolist())  # shape (2,): one value per team?
except Exception as e:
    print(type(e).__name__)
```
A. `[[98, 92, 74], [55, 50, 55]]` then `ValueError` — broadcasting always aligns shapes from the **trailing** dimension inward: `grid` is `(2, 3)` and `bonus` is `(3,)`, so NumPy matches `bonus`'s single axis against `grid`'s *last* axis (3 columns) and applies it to every row, adding `10`/`0`/`-5` to each round's score across both teams. The second attempt uses a length-2 array, hoping it'll line up "one value per team" (per row) instead — but broadcasting doesn't know rows from columns, it only compares trailing dimensions: `3` (grid's last axis) vs `2` (the new array's only axis) don't match and neither is `1`, so it raises `ValueError`.
B. `[[98, 92, 74], [55, 50, 55]]` then `[[98, 92], [55, 50]]` — correctly computes the first result but wrongly assumes a shape-`(2,)` array automatically broadcasts against `grid`'s *rows* instead of raising; broadcasting only ever matches dimensions from the trailing (rightmost) end, so a `(2,)` array is compared against `grid`'s 3 columns, not its 2 rows, and that mismatch fails rather than silently reinterpreting the array as row-wise.
C. `[[98, 92, 69], [55, 50, 50]]` — wrongly applies `bonus` positionally by overall index instead of per-column, as if the arrays were first flattened and added element-by-element in reading order (`88+10, 92+0, 79+(-5)` is actually right, but this option miscalculates `79 + (-5)` as `69` and `60 + (-5)` as `50`, double-subtracting the round-3 penalty into round 2 as well — not how broadcasting or elementwise addition works at all).
D. `ValueError` then `[[98, 92], [55, 50]]` — gets the two outcomes backwards: it's the *first* line, `grid + bonus`, that succeeds (shapes `(2,3)` and `(3,)` broadcast cleanly along the trailing axis), and the *second* line, with the mismatched `(2,)` array, that fails.

## Q2. Building on Q1's season grid, Grace flattens one team's row into its own array and vectorizes a "how far from average" check instead of looping. What does this print? (Roadmap #43, #3)

```python
import numpy as np

scores = np.array([88, 92, 45, 50, 60])

avg = scores.mean()
print(avg)

diffs = scores - avg
print(diffs.tolist())

above_avg = scores > avg
print(above_avg.tolist())
```
A. `67.0` then `[21.0, 25.0, -22.0, -17.0, -7.0]` then `[True, True, False, False, False]` — `scores.mean()` sums `88+92+45+50+60=335` and divides by 5, giving `67.0`. `scores - avg` broadcasts that single scalar against every element (a scalar is shape `()`, which always matches), subtracting `67.0` from each score to get the per-element distance from average. `scores > avg` broadcasts the same way to a boolean array — note `60` is still *below* `67.0`, so it's `False`, not `True`.
B. `67.0` then `[21.0, 25.0, -22.0, -17.0, -7.0]` then `[True, True, False, False, True]` — gets the mean and the diffs right but wrongly marks `60` as above the average; `60 < 67.0`, so that position must be `False`, not `True` — only the first two scores (`88`, `92`) actually exceed the mean.
C. `335.0` then `[21.0, 25.0, -22.0, -17.0, -7.0]` then `[True, True, False, False, False]` — correctly computes the diffs and mask but wrongly prints the *sum* (`335.0`) where `.mean()` was called, as if `.mean()` forgot to divide by the element count.
D. `67.0` then `[88.0, 92.0, 45.0, 50.0, 60.0]` then `[True, True, False, False, False]` — gets the mean and mask right but wrongly assumes `scores - avg` leaves `scores` unchanged (as if the scalar subtraction silently did nothing), rather than broadcasting the subtraction across every element.

## Q3. Grace builds a full team-vs-round bonus table at once by broadcasting a column vector against a row vector, instead of writing nested loops. What does this print? (Roadmap #43, #3)

```python
import numpy as np

team_base = np.array([[1], [2], [3]])      # shape (3, 1): one base value per team
round_bonus = np.array([10, 20, 30])       # shape (3,): one bonus per round

table = team_base + round_bonus
print(table.tolist())
print(table.shape)
```
A. `[[11, 21, 31], [12, 22, 32], [13, 23, 33]]` then `(3, 3)` — broadcasting stretches each operand along whichever axis has size `1` so the shapes line up: `team_base` is `(3, 1)`, so its single column is repeated across 3 columns, and `round_bonus` is `(3,)`, which is treated as shape `(1, 3)` and repeated across 3 rows. The result is every `team_base[i] + round_bonus[j]` combination at once — a `(3, 3)` outer-sum table — not a simple elementwise pairing of same-length 1-D arrays.
B. `[11, 22, 33]` then `(3,)` — wrongly assumes a `(3, 1)` array and a `(3,)` array must be the "same length" and get paired off elementwise like two ordinary 1-D arrays, missing that `team_base`'s explicit column shape `(3, 1)` is what triggers full 2-D broadcasting instead of a simple pairwise sum.
C. `[[11, 21, 31], [12, 22, 32], [13, 23, 33]]` then `(3,)` — gets the broadcast table's values right but wrongly reports its shape as 1-D; broadcasting a `(3, 1)` array against a `(3,)` array always produces a genuinely 2-D `(3, 3)` result, not a flattened one.
D. `ValueError` — wrongly assumes a column vector `(3, 1)` and a row-shaped `(3,)` array are incompatible because their axis lengths don't literally match; broadcasting explicitly allows a size-`1` axis to stretch to match any size, which is exactly the mechanism that makes this combination valid rather than an error.

## Q4. Contrasting with Q3, Grace multiplies the Q1 grid by a weight per round, then tries the same weights against a grid shaped the other way around. What does this print? (Roadmap #43, #3)

```python
import numpy as np

grid = np.array([[88, 92, 79], [45, 50, 60]])   # shape (2, 3)
weights = np.array([1, 0, 2])                   # shape (3,)

print((grid * weights).tolist())

grid_t = np.array([[88, 92], [79, 45], [50, 60]])  # shape (3, 2) — rounds as rows now
try:
    print((grid_t * weights).tolist())
except Exception as e:
    print(type(e).__name__)
```
A. `[[88, 0, 158], [45, 0, 120]]` then `ValueError` — `weights`'s trailing (and only) axis has length 3, which matches `grid`'s trailing axis (3 columns), so it broadcasts cleanly across every row, zeroing out round 2 and doubling round 3 for both teams. `grid_t` reshapes the data so rounds are now *rows* (shape `(3, 2)`) — its trailing axis is length 2, which doesn't match `weights`'s length-3 axis and isn't `1` either, so the shapes are incompatible and it raises.
B. `[[88, 0, 158], [45, 0, 120]]` then `[[88, 0], [158, 45], [0, 120]]` — gets the first multiplication right but wrongly assumes NumPy will silently reshape or re-flatten `weights` to fit whatever shape `grid_t` happens to have; broadcasting compares the actual trailing axis lengths and refuses rather than reinterpreting data to make things fit.
C. `[[88, 92, 158], [45, 50, 120]]` then `ValueError` — correctly predicts the error on the second line but miscalculates the first: weight `0` at index 1 must zero out the *entire* second column (`92 → 0` and `50 → 0`), not leave those values unchanged.
D. `ValueError` then `ValueError` — wrongly assumes the *first* multiplication also fails; `weights`'s length-3 axis matches `grid`'s length-3 trailing axis exactly, so that one broadcasts without any error — only the second, shape-mismatched multiplication raises.

## Q5. Tying back to Day 51 Q4's `int8` wraparound, Grace adds the same running totals to a *differently*-typed bump this time instead of another `int8`. What does this print? (Roadmap #43, #3, #41)

```python
import numpy as np

totals = np.array([120, 45, 92], dtype=np.int8)

same_dtype_bump = totals + np.int8(100)
print(same_dtype_bump.dtype, same_dtype_bump.tolist())

wider_bump = totals + np.int16(100)
print(wider_bump.dtype, wider_bump.tolist())
```
A. `int8 [-36, -111, -64]` then `int16 [220, 145, 192]` — adding `np.int8(100)` keeps both operands at `int8`, so the result stays `int8` too and wraps around via two's-complement on overflow, exactly like Day 51 Q4 (`120+100=220 → -36`, etc.). Adding `np.int16(100)` instead forces NumPy's type-promotion rules to upcast the *whole operation* to the wider `int16` dtype *before* adding — `int16`'s range comfortably holds `220`, `145`, and `192`, so none of them wrap and the true sums come through unchanged.
B. `int8 [-36, -111, -64]` then `int8 [-36, -111, -64]` — wrongly assumes the dtype of `totals` always "wins" regardless of what it's added to, as if NumPy kept the left operand's dtype no matter how much wider the other operand is; type promotion instead picks the *wider* of the two dtypes involved, which here is `int16`.
C. `int16 [220, 145, 192]` then `int16 [220, 145, 192]` — wrongly assumes adding any scalar, even a same-width `np.int8(100)`, automatically promotes the result to a wider dtype to avoid overflow; promotion only widens to the dtype actually involved in the operation, and `int8 + int8` stays `int8`, overflow and all.
D. `int8 [-36, -111, -64]` then `int32 [220, 145, 192]` — correctly contrasts the two cases but wrongly reports the promoted dtype as `int32`; `int8` combined with `np.int16(100)` promotes to `int16` specifically (the width actually present in the operation), not to some larger default integer size.

## Answer key

1. **A** — Broadcasting always aligns from the trailing axis inward: `bonus` (shape `(3,)`) matches `grid`'s last axis (3 columns), applying per-round across both teams. A shape-`(2,)` array, hoping to align per-team (per-row) instead, is compared against `grid`'s trailing axis (3) and fails since neither side is `1`. B wrongly assumes the length-2 array broadcasts row-wise instead of raising. C miscalculates the elementwise sum. D swaps which line succeeds and which fails.
2. **A** — `scores.mean()` is `335/5=67.0`. Subtracting that scalar broadcasts across every element for `diffs`, and comparing broadcasts the same way for the mask. `60 < 67.0`, so it's `False`. B wrongly marks `60` as above average. C prints the raw sum instead of the mean. D wrongly assumes scalar subtraction leaves `scores` unchanged.
3. **A** — `team_base` (`(3,1)`) and `round_bonus` (`(3,)`, treated as `(1,3)`) each have a size-`1` axis that stretches to match the other, producing every pairwise sum as a `(3,3)` table. B wrongly treats them as same-length 1-D arrays to pair off elementwise. C gets the values right but misreports the shape as 1-D. D wrongly treats the size-`1` axis as a hard mismatch rather than the very thing that makes broadcasting valid here.
4. **A** — `weights`'s length-3 axis matches `grid`'s trailing (column) axis, broadcasting cleanly per row. `grid_t`'s trailing axis is length 2, which doesn't match `weights`'s length 3 and isn't `1`, so it raises. B wrongly assumes NumPy reshapes `weights` to fit. C gets the error right but miscalculates the zeroed column in the first multiplication. D wrongly predicts the first multiplication also fails.
5. **A** — `int8 + int8` stays `int8` and wraps on overflow (same as Day 51 Q4). `int8 + int16` promotes the whole operation to `int16`, whose range holds the true sums without wrapping. B wrongly assumes the left operand's dtype always wins regardless of width. C wrongly assumes any scalar addition auto-widens, even same-width `int8 + int8`. D gets the contrast right but names the wrong promoted dtype (`int32` instead of `int16`).
