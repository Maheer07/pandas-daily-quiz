## Q1. Building on Day 23 Q1's `team` × `region` pivot table, this reshapes it back to long format. What does it print? (Roadmap #20)

```python
import pandas as pd
data6 = {'name': ['Alice', 'Bob', 'Carol', 'Dave', 'Eve', 'Frank'],
         'team': ['Red', 'Blue', 'Red', 'Blue', 'Red', 'Blue'],
         'region': ['North', 'South', 'North', 'North', 'South', 'South'],
         'score': [88, 45, 92, 60, 75, 50]}
df6 = pd.DataFrame(data6, index=[100, 101, 102, 103, 104, 105])

piv = pd.pivot_table(df6, index='team', columns='region', values='score').reset_index()
melted = piv.melt(id_vars='team', var_name='region', value_name='score')
print(melted.sort_values(['team', 'region']).reset_index(drop=True))
```
A.
```
   team region  score
0  Blue  North   60.0
1  Blue  South   47.5
2   Red  North   90.0
3   Red  South   75.0
```
B.
```
   team region  score
0  Blue  North   47.5
1  Blue  South   60.0
2   Red  North   75.0
3   Red  South   90.0
```
C.
```
   team  North  South
0  Blue   60.0   47.5
1   Red   90.0   75.0
```
D. Raises a `TypeError`, because `id_vars` must be passed as a list (`['team']`), not a bare string

## Q3. Spot the bug: this is meant to reproduce Day 23 Q1's `team`-rows/`region`-columns table using `groupby` + `unstack` instead of `pivot_table`, but picks the wrong level. What does it actually produce? (Roadmap #20)

```python
s = df6.groupby(['team', 'region'])['score'].mean()
print(s.unstack(level=0))
```
A. The exact same `team`-rows/`region`-columns table as Day 23 Q1 — `unstack(level=0)` and the no-argument default `unstack()` are equivalent here
B. A `region`-rows/`team`-columns table — transposed relative to intended, because `level=0` refers to `team` (the first/outer level of the groupby `MultiIndex`), not `region`
C. Raises a `ValueError`, because `unstack()` needs an explicit level only when there are more than two groupby keys
D. The same table, but every cell is `NaN`, because `level=0` can't locate `team` as a valid level name

## Q4. Building on Q2's `.stack()` lesson, a seventh teammate on a brand-new team is added, creating a pivot table with missing `team`/`region` combinations. What does this print? (Roadmap #20)

```python
data7 = {'name': ['Alice', 'Bob', 'Carol', 'Dave', 'Eve', 'Frank', 'Grace'],
         'team': ['Red', 'Blue', 'Red', 'Blue', 'Red', 'Blue', 'Green'],
         'region': ['North', 'South', 'North', 'North', 'South', 'South', 'East'],
         'score': [88, 45, 92, 60, 75, 50, 99]}
df7 = pd.DataFrame(data7)

piv7 = pd.pivot_table(df7, index='team', columns='region', values='score')
print(piv7.stack().shape)
```
A. `(9,)` — current `.stack()` keeps every `team`/`region` combination from the 3×3 grid, `NaN` cells included, since it no longer drops missing combinations by default the way older pandas versions did
B. `(5,)` — `.stack()` drops the `NaN` combinations by default, leaving only the 5 team/region pairs that actually appear in `df7`
C. `(3,)` — one entry per team, as if `.stack()` collapsed each team's regions into a single average
D. Raises a `ValueError`, because `.stack()` can't be called on a DataFrame that contains `NaN` values

## Q5. Using Q1's `piv` (columns `team`, `North`, `South`), which line raises an error? (Roadmap #20)

```python
piv = pd.pivot_table(df6, index='team', columns='region', values='score').reset_index()
```
A. `piv.melt(id_vars='team')`
B. `piv.melt(id_vars='team', value_vars=['North', 'South'])`
C. `piv.melt(id_vars='region')`
D. `piv.melt(id_vars='team', var_name='region', value_name='score')`

## Answer key

1. **A** — `.reset_index()` turns the pivot table's `team` row-index into a real column, giving `piv` three columns: `team`, `North`, `South`. `.melt(id_vars='team', var_name='region', value_name='score')` then keeps `team` fixed and unpivots the two value columns (`North`, `South`) into a `region` label column plus a `score` value column, one row per original cell: `Blue`/`North`→60.0, `Blue`/`South`→47.5, `Red`/`North`→90.0, `Red`/`South`→75.0 — exactly Day 23 Q1's numbers, just reshaped long. B keeps the right shape but swaps every team's North/South values with each other. C is wrong — that's the *original* wide `piv`, before `.melt()` ever ran; melting did nothing in this option. D is wrong — `id_vars` happily accepts a single column name as a bare string (it's only `value_vars` ambiguity that sometimes needs a list); no error occurs.
2. **A** — `piv2`'s columns are a single-level index (just `region`'s values, `North`/`South`), so `.stack()` moves that level onto the row index, producing a `Series` with a 2-level `MultiIndex` (`team`, `region`) — `nlevels` is `2` and the type is `Series`. B wrongly assumes stacking doesn't add a level at all. C is wrong — stacking a single-level column index collapses the result to a `Series`, not a `DataFrame`; a `DataFrame` only survives `.stack()` when the columns started with *more than one* level left over. D is backwards — `.stack()` works on an ordinary single-level column index too; it's precisely what moves that level into a `MultiIndex`, it doesn't require one to already exist.
3. **B** — the groupby `Series` has a 2-level `MultiIndex` with `team` as level `0` (outer) and `region` as level `1` (inner, the default `unstack()` target). Passing `level=0` explicitly moves `team` to the columns instead, leaving `region` as the row index — the table comes out transposed (`region` rows × `team` columns) relative to Day 23's `team`-rows/`region`-columns layout. A is wrong — that's exactly the bug: the no-argument `unstack()` defaults to the *last* level (`region`), while `unstack(level=0)` targets the *first* level (`team`) — they are not equivalent here. C is wrong — `unstack()` accepts an explicit `level` with exactly two keys just fine; no error. D is wrong — `team` is a perfectly valid level (by position or by name), so no `NaN`-filled failure occurs; the values are all still real numbers, just rearranged.
4. **A** — Current pandas `.stack()` no longer drops missing combinations by default the way the older implementation did; it always keeps the full cross-product of the row and column levels, filling in `NaN` for any `team`/`region` pair that doesn't exist in the data. `piv7` is a 3×3 grid (`Blue`/`Green`/`Red` × `East`/`North`/`South`), so stacking produces all 9 combinations — 5 real scores and 4 `NaN`s (e.g. `Green`/`North`, `Blue`/`East`). B describes the legacy `dropna=True`-by-default behavior, which no longer applies — that option doesn't even exist anymore for the default `.stack()` call. C invents an averaging step `.stack()` never performs — it reshapes, it doesn't aggregate. D is wrong — `.stack()` handles `NaN` cells without complaint; it's `.pivot()` (not `.pivot_table()` or `.stack()`) that's intolerant of missing/duplicate data, and that's a different failure mode entirely (see Day 23 Q3).
5. **C** — `id_vars` must name column(s) that actually exist in the DataFrame being melted; `piv` only has `team`, `North`, `South` — there is no `region` column yet (that label only gets created *by* melting, as the `var_name`). Passing `id_vars='region'` raises `KeyError: "The following id_vars or value_vars are not present in the DataFrame: ['region']"`. A is valid — omitting `value_vars` makes `.melt()` default to "every other column", i.e. `North` and `South`. B is valid — it's the same call as A, just with `value_vars` spelled out explicitly. D is valid — `var_name`/`value_name` just rename the two output columns `.melt()` creates; they don't need to already exist beforehand.
