## Q5. Given `rows = [[1, 'Alice', 25], [2, 'Bob', 30]]`, which line correctly produces a DataFrame with columns named `id`, `name`, `age` (instead of the default integer column labels)?

A. `pd.DataFrame(rows, columns=['id', 'name', 'age'])`
B. `pd.DataFrame(rows, index=['id', 'name', 'age'])`
C. `pd.DataFrame(rows, index=['id', 'name'])`
D. `pd.DataFrame(rows, header=['id', 'name', 'age'])`

## Answer key

1. **A** — Passing a dict of equal-length lists to `pd.DataFrame` turns each key into a column (in insertion order: `name`, `age`) and each list's items into that column's rows, giving 3 rows and 2 columns; `.shape` reports `(rows, cols)`. B swaps the two shape numbers — a common mix-up with `.shape`'s `(rows, cols)` ordering. C wrongly assumes columns always default to integer positions; that only happens when there are no key/column labels to draw from (e.g. a raw list of lists or a NumPy array, as in Q4/Q5 below) — here the dict keys supply real names. D is wrong: each column of a DataFrame independently holds its own dtype (`object`/string for `name`, `int64` for `age`), so there's no requirement that the source lists share a dtype.
2. **A** — Constructing a DataFrame from a dict of Series aligns each Series by index **label**, on the union of all the indices involved — the same label-based alignment rule from Day 7 Q3, just applied per-column instead of to a single `+`. The union `{'w','x','y','z'}` is sorted, and any label missing from one Series becomes `NaN` in that column (`x` has no `b` value, `w` has no `a` value), which also upcasts both columns to `float64`. B wrongly keeps only the overlapping labels `y`/`z`, as if it were an inner join instead of a union-based outer alignment. C is wrong — mismatched indices never raise an error; missing combinations simply become `NaN`. D has the right values but the wrong row order: it lists rows in "first-seen" order (`x, y, z` from `a` then `w` newly from `b`) rather than the sorted union order pandas actually produces.
3. **A** — Building a DataFrame from a list of dicts takes the **union of all keys** across every dict as the columns; any dict missing a given key gets `NaN` there (Bob has no `age`, Alice has no `city`), and the presence of that `NaN` upcasts the whole `age` column to `float64` even though `25` was written as a plain int. B wrongly assumes mismatched keys across dicts raise an error, rather than simply being treated as "missing → `NaN`" per row. C wrongly assumes `city` is dropped because it's absent from the *first* dict — column discovery isn't limited to the first record, it scans every dict in the list. D wrongly assumes missing entries are filled with `0` instead of `NaN`, which would also (wrongly) keep `age` as `int64`.
4. **A** — With no `columns=`/`index=` given, a DataFrame built from a 2D NumPy array falls back to default integer **labels**: columns `[0, 1, 2]` and a `RangeIndex` `[0, 1]` for the rows, and it keeps the source array's dtype (`int64`) for every column since the whole array was homogeneous ints. B wrongly stringifies the default column labels — they're real integers (`0`, `1`, `2`), not the strings `'0'`, `'1'`, `'2'`. C wrongly assumes converting a NumPy array to a DataFrame forces `object` dtype; the numeric dtype carries straight through unchanged. D is wrong — `columns=`/`index=` are optional. Unlike Q1, where the dict's keys supplied real column names, a plain array has no labels to borrow, so pandas falls back to integer defaults instead of raising.
5. **A** — `columns=` is the parameter that names a DataFrame's **columns** when building from a list of lists, giving the intended `id`/`name`/`age` header. B passes the same three labels to `index=` instead, which sets **row** labels, not columns — and since `rows` only has 2 rows against 3 index labels, it raises a `ValueError` for a length mismatch, not just a "wrong but valid" result. C avoids that length error (2 labels for 2 rows) but still mislabels the *rows* as `id`/`name` while the columns stay the default `0, 1, 2` — it "runs fine" but doesn't come close to answering the question asked. D uses `header=`, which isn't a valid `pd.DataFrame` constructor argument at all (that's a `pd.read_csv` parameter), so it raises a `TypeError` for an unexpected keyword argument.
