## Q1. Returning to Day 9's name/age `df` with its custom index `[10, 20, 30, 40]`, Grace tries to add a new row through `.loc`, then tries the same trick through `.iloc`. What does this print? (Roadmap #48, #8)

```python
import pandas as pd

df = pd.DataFrame({'name': ['Alice', 'Bob', 'Carol', 'Dave'], 'age': [25, 30, 35, 40]}, index=[10, 20, 30, 40])

df.loc[50, 'name'] = 'Eve'
print(df)

try:
    df.iloc[50, 0] = 'Frank'
except IndexError as e:
    print(type(e).__name__)
```
A.
```
     name   age
10  Alice  25.0
20    Bob  30.0
30  Carol  35.0
40   Dave  40.0
50    Eve   NaN
```
then `IndexError` — `.loc` is allowed to **enlarge** its target: assigning to a label that doesn't exist yet (`50`) creates a brand-new row, filling every column Grace didn't mention (here, `'age'`) with `NaN` — which upcasts the whole `age` column from `int64` to `float64`, the same upcast-on-`NaN` rule Days 56-58 kept relying on. `.iloc` has no such allowance: position `50` is nowhere near the (now 5-row) DataFrame's valid positions `0`-`4`, and unlike `.loc`, `.iloc` can never create a new row no matter the position — it simply raises `IndexError`.
B. `KeyError` (nothing else printed) — wrongly assumes `.loc` is just as strict as `.iloc` about only touching labels that already exist, as if assigning to a missing label failed outright instead of enlarging the DataFrame with a new row.
C.
```
     name   age
10  Alice  25.0
20    Bob  30.0
30  Carol  35.0
40   Dave  40.0
50    Eve   NaN
```
then (no error, `'Frank'` written in) — wrongly assumes `.iloc` can also enlarge past the current row count the way `.loc` just did; `.iloc` is purely positional and has no concept of "create the row at this position if it doesn't exist" — it only ever addresses rows that are already there.
D.
```
     name  age
10  Alice   25
20    Bob   30
30  Carol   35
40   Dave   40
50    Eve    0
```
then `IndexError` — gets the exception right but wrongly fills the new row's missing `age` with `0` instead of `NaN`, which would also (wrongly) keep the column `int64` instead of upcasting to `float64` — the same "fills with 0, not `NaN`" mistake Day 58 Q1/Q4's distractors made.

## Q2. Using the same `df` from Q1 (before its `.loc` enlargement), Grace reaches for a negative index to grab the last row — once with `.iloc`, once with `.loc`. What does this print? (Roadmap #48, #8, #42)

```python
import pandas as pd

df = pd.DataFrame({'name': ['Alice', 'Bob', 'Carol', 'Dave'], 'age': [25, 30, 35, 40]}, index=[10, 20, 30, 40])

print(df.iloc[-1]['name'])

try:
    print(df.loc[-1, 'name'])
except KeyError as e:
    print(type(e).__name__)
```
A. `Dave` then `KeyError` — `.iloc` is pure positional indexing, so `-1` means "last position" exactly like ordinary Python negative indexing (same rule NumPy slicing has used all along) — landing on the last row, label `40`, `'Dave'`. `.loc` never reinterprets `-1` as "from the end"; it only ever searches for the *literal label* `-1` among `df`'s actual labels (`10, 20, 30, 40`), finds no such label, and raises `KeyError`.
B. `Dave` then `Dave` — wrongly assumes `.loc` also treats a negative integer as "count from the end" the way `.iloc` does; `.loc` only ever matches labels literally, and `-1` isn't one of `df`'s labels, so there's nothing for it to find.
C. `KeyError` then `Dave` — swaps which call fails, as if `.iloc[-1]` were out of range (no "position -1" exists) and `.loc[-1, ...]` somehow matched something; negative positions are standard, valid `.iloc` syntax, and `.loc` is the one with nothing at label `-1`.
D. `Dave` then `IndexError` — gets the first line right but raises the wrong exception type on the second; `.loc` always reports a missing *label* as `KeyError`, never `IndexError` — `IndexError` is reserved for `.iloc`'s out-of-range *positions*.

## Q3. Returning to Day 58 Q4's sorted `table` DataFrame, Grace slices both rows and columns at once, once with `.loc` and once with `.iloc`. What does this print? (Roadmap #48, #47, #8)

```python
import pandas as pd

temps = pd.Series([68, 72, 95, 61, 88], index=['mon', 'tue', 'wed', 'thu', 'fri'])
r2_bonus = pd.Series([1, 1], index=['wed', 'mon'])
r3_bonus = pd.Series([9], index=['thu'])
table = pd.DataFrame({'temp': temps, 'r2_bonus': r2_bonus, 'r3_bonus': r3_bonus})

print(table.loc['mon':'tue', 'r2_bonus':'r3_bonus'])
print(table.iloc[1:3, 1:3])
```
A.
```
     r2_bonus  r3_bonus
mon       1.0       NaN
thu       NaN       9.0
tue       NaN       NaN
```
then
```
     r2_bonus  r3_bonus
mon       1.0       NaN
thu       NaN       9.0
```
— Day 58 Q4 established that `table`'s row index comes back **sorted** (`fri, mon, thu, tue, wed`), regardless of the order the Series were given in. `.loc['mon':'tue', 'r2_bonus':'r3_bonus']` slices **both axes by label, inclusive of the stop**: along the rows that's every label from `'mon'` through `'tue'` in that sorted order — `mon, thu, tue`, three rows — and along the columns, both `'r2_bonus'` and `'r3_bonus'`. `.iloc[1:3, 1:3]` slices **both axes by position, exclusive of the stop**, the ordinary Python-slice rule: row positions `1` and `2` only (`mon, thu` — not `tue`, which sits at position `3`) and column positions `1` and `2` (the same two bonus columns, which happen to align here).
B.
```
     r2_bonus  r3_bonus
mon       1.0       NaN
thu       NaN       9.0
```
then the same two rows — wrongly applies `.iloc`'s exclusive-of-stop rule to the `.loc` call too, dropping `'tue'` from the first result; label-based slicing with `.loc` always includes its stop label, on either axis.
C.
```
     r2_bonus  r3_bonus
mon       1.0       NaN
thu       NaN       9.0
tue       NaN       NaN
```
then the same three rows — wrongly applies `.loc`'s inclusive-of-stop rule to the `.iloc` call too, as if positional slicing also kept going through position `3`; `.iloc` is always exclusive of its stop position, exactly like a plain Python list slice.
D.
```
     r2_bonus
mon       1.0
thu       NaN
tue       NaN
```
then the two-row, two-column result from A — gets the row counts right but wrongly treats the `.loc` *column* slice as exclusive of its stop, dropping `'r3_bonus'`; `.loc` slicing is inclusive of the stop label on every axis it's applied to, rows or columns alike, not just rows.

## Q4. Still on Day 9's `df`, Grace zeroes out everyone over 30 two different ways — tying Q1-Q2's `.loc`/`.iloc` contrast to Day 48's Copy-on-Write lesson. What does this print? (Roadmap #48, #39, #8)

```python
import pandas as pd

df = pd.DataFrame({'name': ['Alice', 'Bob', 'Carol', 'Dave'], 'age': [25, 30, 35, 40]}, index=[10, 20, 30, 40])

df[df['age'] > 30]['age'] = 0
print(df['age'].tolist())

df.loc[df['age'] > 30, 'age'] = 0
print(df['age'].tolist())
```
A. `[25, 30, 35, 40]` then `[25, 30, 0, 0]` — `df[df['age'] > 30]` already returns an independent copy, same Copy-on-Write rule Days 52/56-58 kept relying on for reads; chaining `['age'] = 0` onto *that* copy only emits a `ChainedAssignmentError` warning and never reaches `df` at all, so the first print is unchanged. `df.loc[mask, 'age'] = 0` is a single combined label-based operation — row selector and column selector handed to one `.loc` call — so it writes directly into `df`'s own memory, zeroing the two rows where `age > 30` (labels `30` and `40`, values `35` and `40`).
B. `[25, 30, 0, 0]` then `[25, 30, 0, 0]` — wrongly assumes the chained `df[mask]['age'] = 0` on line 1 also writes through to `df`; indexing with `[mask]` to *read* always hands back a copy under Copy-on-Write, so any assignment chained onto it is writing to a throwaway object, not `df`.
C. `[25, 30, 35, 40]` then `[25, 30, 35, 40]` — wrongly assumes `.loc[mask, 'age'] = 0` is just as "chained" and silent as line 1; combining both selectors into one `.loc[]` call is exactly the single-step pattern that *does* write through — it's the fix for line 1's problem, not a repeat of it.
D. `[25, 30, 35, 40]` then `[25, 0, 0, 40]` — gets the concept right but miscomputes which rows satisfy `age > 30`, wrongly zeroing the row where `age` is `30`; `30 > 30` is `False`, so Bob's row must stay `30`, not become `0`.

## Q5. Still on the same `df`, continuing Q4's chained-assignment lesson, Grace tries what looks like the safe `.loc` pattern but splits it across two steps instead of one. What does this print? (Roadmap #48, #39, #8)

```python
import pandas as pd

df = pd.DataFrame({'name': ['Alice', 'Bob', 'Carol', 'Dave'], 'age': [25, 30, 35, 40]}, index=[10, 20, 30, 40])

df.loc[20]['age'] = 99
print(df['age'].tolist())

df.loc[20, 'age'] = 99
print(df['age'].tolist())
```
A. `[25, 30, 35, 40]` then `[25, 99, 35, 40]` — `df.loc[20]` on its own (no column selector) is a single-label row lookup, same rule as Day 9 Q1, and it hands back the row as its own freshly-built `Series` — not a view into `df`. Chaining `['age'] = 99` onto that `Series` is chained assignment all over again, just spelled with `.loc` instead of Q4's `df[mask]`, so it silently fails to reach `df`. Only when the row selector (`20`) and column selector (`'age'`) are both passed into the *same* `.loc[...]` call does pandas perform one combined, writable operation — updating Bob's row (label `20`) to `99`.
B. `[25, 99, 35, 40]` then `[25, 99, 35, 40]` — wrongly assumes that because the first line "starts with `.loc`", it already writes through like Q4's fix did; what matters isn't starting with `.loc`, it's whether the row *and* column selectors are given to `.loc` together in one call — splitting them into `.loc[20]` followed by `['age']` recreates the exact chained-assignment trap from Q4.
C. `[25, 30, 35, 40]` then `[25, 30, 35, 40]` — wrongly assumes the second line fails too, as if any assignment touching label `20` were now permanently chained once the first attempt failed; `df.loc[20, 'age'] = 99` is a fresh, independent, single-step `.loc` call with no connection to the failed attempt on the line before it.
D. `[25, 30, 35, 40]` then `KeyError` — wrongly assumes `df.loc[20, 'age'] = 99` needs label `20` to have been "established" by a prior standalone `.loc[20]` lookup; label `20` has been part of `df`'s index since it was constructed, so this assignment needs no such precondition and just works.

## Answer key

1. **A** — `.loc` can enlarge a DataFrame by assigning to a new label, filling unmentioned columns with `NaN` (upcasting `age` to `float64`); `.iloc` can never enlarge and raises `IndexError` on an out-of-range position. B wrongly assumes `.loc` also refuses missing labels. C wrongly assumes `.iloc` can also enlarge. D fills the gap with `0` instead of `NaN` and keeps the dtype `int64`.
2. **A** — `.iloc[-1]` is positional, so `-1` means "last row" (`Dave`); `.loc[-1, ...]` only matches the literal label `-1`, which doesn't exist in `df`'s index, raising `KeyError`. B wrongly assumes `.loc` also supports from-the-end negative indexing. C swaps which call fails. D raises the wrong exception type for a missing `.loc` label.
3. **A** — `.loc` slices both axes by label, inclusive of the stop (3 rows, both bonus columns); `.iloc` slices both axes by position, exclusive of the stop (2 rows, same 2 columns here). B wrongly applies `.iloc`'s exclusive rule to the `.loc` call. C wrongly applies `.loc`'s inclusive rule to the `.iloc` call. D wrongly treats `.loc`'s column slice as exclusive.
4. **A** — `df[mask]` returns a copy under Copy-on-Write, so chaining `['age'] = 0` onto it never reaches `df`; `df.loc[mask, 'age'] = 0` combines both selectors into one write that does. B wrongly assumes the chained line 1 writes through. C wrongly assumes the combined `.loc` line is just as silent. D zeroes the `age == 30` row, which doesn't satisfy `age > 30`.
5. **A** — `df.loc[20]` alone returns a fresh `Series`, so chaining `['age'] = 99` onto it is chained assignment and never reaches `df`; `df.loc[20, 'age'] = 99` combines both selectors in one call and writes through. B wrongly assumes starting with `.loc` alone is enough to write through. C wrongly assumes the independent second line also fails. D wrongly assumes label `20` needs to be "established" by a prior `.loc` call before a direct `.loc[20, 'age']` assignment can use it.
