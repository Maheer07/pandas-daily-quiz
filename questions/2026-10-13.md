## Q1. Using a fresh daily score log (built with `pd.date_range`, the same way Day 22's `.dt` lesson set up dates), what does this print? (Roadmap #22)

```python
import pandas as pd
scores = pd.Series([70, 75, 90, 60, 80, 95],
                    index=pd.date_range('2023-01-01', periods=6, freq='D'),
                    name='score')
print(scores.rolling(window=3).mean().tolist())
```
A. `[nan, nan, 78.333..., 75.0, 76.666..., 78.333...]` — the default `min_periods` equals the window size, so the first two rows (which can't see a full 3-value window yet) come out `NaN`, and the mean only starts once 3 values are available
B. `[70.0, 72.5, 78.333..., 75.0, 76.666..., 78.333...]` — `.rolling()` implicitly uses `min_periods=1` by default, averaging over whatever partial window is available at the start
C. `[nan, 75.0, 82.5, 75.0, 76.666..., 78.333...]` — only the very first row is `NaN`, since a 3-window rolling mean only needs one prior value, not two, before it can start
D. Raises a `ValueError`, because `window=3` requires the Series to have at least 3 full non-overlapping groups, and 6 isn't evenly divisible into windows of 3 starting cleanly

## Q2. Spot the bug: this is meant to compute each day's change from the **previous** day (i.e. reproduce `.diff()`), but uses `.shift()` the wrong direction. What does it actually print? (Roadmap #22)

```python
delta_wrong = scores - scores.shift(-1)
print(delta_wrong.tolist())
print(delta_wrong.equals(scores.diff()))
```
A. `[-5.0, -15.0, 30.0, -20.0, -15.0, nan]` then `False` — `shift(-1)` pulls *tomorrow's* value back to today's row, so this actually computes "today minus tomorrow" (the negative of tomorrow's real change), and the `NaN` lands on the **last** row instead of the first, since there's no "tomorrow" after the final date
B. `[nan, 5.0, 15.0, -30.0, 20.0, 15.0]` then `True` — this is what `scores.diff()` itself produces, and `shift(-1)` vs `shift(1)` only affects where the `NaN` falls, not the actual values
C. `[5.0, 15.0, -30.0, 20.0, 15.0, nan]` then `False` — same values as `.diff()` but shifted one position earlier, since `shift(-1)` moves everything up by exactly one slot relative to `.diff()`'s own internal shift
D. Raises a `ValueError`, because subtracting a Series from itself after a negative shift creates duplicate-aligned index labels that pandas can't subtract

## Q3. Building on Q1's `scores`, what does this print? (Roadmap #22)

```python
a = scores.expanding().sum()
b = scores.rolling(window=len(scores), min_periods=1).sum()
print(a.equals(b))
```
A. `True` — `.expanding()` is exactly equivalent to `.rolling()` with a window as large as the whole Series and `min_periods=1`: both grow a cumulative aggregate from the start, using however many values have arrived so far at each row
B. `False` — `.expanding()` only looks at the single most recently arrived value plus the running total, while `.rolling(window=len(scores))` re-aggregates the full fixed window every time, so only the last row happens to match
C. `False` — `.expanding()` returns a plain cumulative-sum-shaped object that isn't directly comparable via `.equals()` to anything produced by `.rolling()`, regardless of the values
D. Raises a `TypeError`, because `.expanding()` takes no window argument at all, so it can't be meaningfully compared to a `.rolling()` call that specifies one

## Q4. Building on Q1's `NaN`s, Frank "fixes" them by adding `min_periods=1`. What does this print now? (Roadmap #22)

```python
print(scores.rolling(window=3, min_periods=1).mean().tolist())
```
A. `[70.0, 72.5, 78.333..., 75.0, 76.666..., 78.333...]` — `min_periods=1` lets the window compute a mean from however many values are actually available so far (1, then 2, then the full 3 from row 3 onward), instead of requiring a complete window before producing anything
B. `[70.0, 70.0, 78.333..., 75.0, 76.666..., 78.333...]` — the first two rows both repeat the Series' very first value, since a window with fewer than 3 real entries forward-fills from the start instead of averaging what's there
C. `[nan, nan, 78.333..., 75.0, 76.666..., 78.333...]` — identical to Q1's output, because `min_periods` only changes the behavior of `.sum()`, not `.mean()`
D. Raises a `ValueError`, because `min_periods` can never be set smaller than `window`

## Q5. Spot the bug: building on yesterday's `MultiIndex` lesson, Grace wants a 2-game rolling average per team and then look up Alice's value by her original row label. What actually happens? (Roadmap #21, #22)

```python
import pandas as pd
data6 = {'name': ['Alice', 'Bob', 'Carol', 'Dave', 'Eve', 'Frank'],
         'team': ['Red', 'Blue', 'Red', 'Blue', 'Red', 'Blue'],
         'region': ['North', 'South', 'North', 'North', 'South', 'South'],
         'score': [88, 45, 92, 60, 75, 50]}
df6 = pd.DataFrame(data6, index=[100, 101, 102, 103, 104, 105])

result = df6.groupby('team')['score'].rolling(2).mean()
print(result.loc[100])
```
A. Raises a `KeyError`, because `.groupby().rolling()` returns a `Series` with a 2-level `MultiIndex` of `(team, original_index)` — `100` alone only matches against the **outer** level (`team`), and `100` isn't one of the team names (`Blue`/`Red`)
B. Returns `NaN`, because Alice is the first row within the `Red` group and a 2-row rolling window has no prior value yet to average with — `.loc` resolves the bare integer `100` by searching the inner level directly when the outer-level lookup fails
C. Returns `90.0`, because `.loc` on a `MultiIndex` Series automatically searches every level, however deep, for a bare label match
D. Returns the entire unfiltered `Series`, because a single integer passed to `.loc` on a `MultiIndex` is silently ignored and the whole object comes back unchanged

## Answer key

1. **A** — `.rolling(window=3)`'s default `min_periods` equals the window size, so pandas refuses to produce a value until a full 3-row window exists: rows 0 and 1 (which only have 1 and 2 values behind them) are `NaN`, and row 2 onward gives real means `(70+75+90)/3=78.33`, `(75+90+60)/3=75.0`, etc. B wrongly assumes `min_periods=1` is the default — it isn't; that behavior only appears once you pass `min_periods=1` explicitly (see Q4). C is wrong about *how many* rows need `NaN` — a window of 3 needs 2 prior values, not 1, before it can start. D is wrong — `.rolling()` is a sliding window over every row, not a partition into non-overlapping chunks, so there's no divisibility requirement at all.
2. **A** — `shift(-1)` pulls each *future* row's value backward onto the current row, so `scores - scores.shift(-1)` computes "today minus tomorrow" at every row — the exact negative of what `.diff()` (today minus *yesterday*) computes — and because there's no row after the last one, the `NaN` ends up at the **end** of the result instead of the beginning. B incorrectly claims the values match `.diff()`; they're negated and offset, so `.equals()` correctly returns `False`. C guesses a different, equally wrong set of values with no real basis in how `shift(-1)` behaves. D is wrong — arithmetic between a Series and its own shifted copy is a completely ordinary, well-defined operation; no duplicate-label error occurs.
3. **A** — `.expanding()` and `.rolling(window=len(scores), min_periods=1)` are different syntaxes for the same idea: a window that starts small (just the first value) and grows to include every prior value as you move down the Series, using whatever count is available at each step rather than requiring a fixed-size window up front — so both produce the identical running-sum sequence `[70.0, 145.0, 235.0, 295.0, 375.0, 470.0]`, and `.equals()` returns `True`. B invents a "most recent value plus running total" behavior that isn't how `.expanding()` works — it re-aggregates over *all* prior values every time, same as the rolling-with-full-window version. C is wrong on the facts — both sides are ordinary same-length `Series` objects, perfectly comparable with `.equals()`. D is wrong — `.expanding()` takes optional arguments like `min_periods`, and not needing a window size doesn't prevent comparing its result to a `.rolling()` result; both just produce `Series` of numbers.
4. **A** — `min_periods=1` tells `.rolling(window=3)` to compute an aggregate as soon as *at least one* value is available, using only the values actually present in the window so far: row 0 uses just `[70]` (mean `70.0`), row 1 uses `[70, 75]` (mean `72.5`), and row 2 onward has a full window of 3 and matches Q1's values exactly. B invents a forward-fill behavior that `.rolling()` never performs — it averages whatever's in the window, it doesn't repeat the first value. C is wrong — `min_periods` applies uniformly to every rolling aggregation function, `.mean()` included, not just `.sum()`. D is wrong — `min_periods` is specifically designed to be set *lower* than `window` (that's the whole point of the parameter); it defaults to equal to `window`, but can be any value from 1 up to `window`.
5. **A** — `df.groupby('team')['score'].rolling(2)` returns a result indexed by a 2-level `MultiIndex`: the group key (`team`) as the outer level, and each row's original index (`100`...`105`) as the inner level. A bare `.loc[100]` is matched against the **outer** level first, exactly like Day 26's `.loc` partial-indexing lessons — and since `100` isn't a value of `team` (`Blue`/`Red`), it raises `KeyError: 100` before ever reaching Alice's row. The correct lookup is the full tuple `result.loc[('Red', 100)]`, which does return `NaN` (Alice has no prior Red-team row to average with) — but that's not what the bare `.loc[100]` call in the question does. B describes the right *value* you'd eventually get with the right key, but incorrectly claims `.loc[100]` resolves to it — it doesn't, because of the outer-level mismatch explained above. C invents a "search every level" fallback that `.loc` does not perform on a `MultiIndex`. D is wrong — passing an unmatched label to `.loc` never silently returns the whole object; it raises `KeyError`.
