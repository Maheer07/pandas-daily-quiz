## Q2. Bob and Dave's scores from yesterday's missing-data example have now both come in at `60`. Spot the bug: this is meant to sort by score descending, tie-breaking by age ascending, but doesn't do what's intended. What does it actually print?

```python
import pandas as pd
data = {'name': ['Alice', 'Bob', 'Carol', 'Dave'], 'age': [25, 30, 35, 40], 'score': [88, 60, 92, 60]}
df = pd.DataFrame(data, index=[100, 101, 102, 103])
print(df.sort_values(by=['score', 'age'], ascending=False)['name'].tolist())
```
A. `['Dave', 'Carol', 'Bob', 'Alice']`
B. `['Carol', 'Alice', 'Bob', 'Dave']`
C. Raises a `ValueError`, because `ascending` must be a list of the same length as `by` whenever `by` has more than one column
D. `['Carol', 'Alice', 'Dave', 'Bob']`

## Q3. Using Day 11's filtering, then sorting the result, what does this print?

```python
import pandas as pd
data = {'name': ['Alice', 'Bob', 'Carol', 'Dave'], 'age': [25, 30, 35, 40], 'score': [88, 45, 92, 60]}
df = pd.DataFrame(data, index=[100, 101, 102, 103])
filtered = df[df['age'] > 25]
print(filtered.sort_index(ascending=False).index.tolist())
```
A. `[101, 102, 103]`
B. `[100, 101, 102]`
C. `[103, 102, 101]`
D. Raises a `KeyError`, because `sort_index` needs a `by` column to sort on, just like `sort_values`

## Q4. Still using today's tied scores (`[88, 60, 92, 60]`), what does this print?

```python
import pandas as pd
data = {'name': ['Alice', 'Bob', 'Carol', 'Dave'], 'age': [25, 30, 35, 40], 'score': [88, 60, 92, 60]}
df = pd.DataFrame(data, index=[100, 101, 102, 103])
print(df['score'].rank().tolist())
```
A. `[3.0, 1.5, 4.0, 1.5]`
B. `[3.0, 1.0, 4.0, 2.0]`
C. `[2.0, 0.5, 3.0, 0.5]`
D. Raises a `ValueError`, because `rank()` can't handle duplicate values unless `method='dense'` is passed

## Q5. Given the same tied-score `df`, which line raises an error?

A. `df.sort_index(axis=1)`
B. `df['score'].rank(method='dense')`
C. `df.sort_values('score', axis=1)`
D. `df.sort_values(by='score', ascending=False, kind='quicksort')`

## Answer key

1. **B** — `sort_values('score')` sorts **rows** ascending by the `score` column by default, and — unlike `sort_index` on a fresh RangeIndex — it never touches the original row labels, so the sorted rows keep their original index (`101, 103, 100, 102`). A applies the sort in the wrong direction (descending instead of the default ascending). C wrongly assumes `sort_values` resets the index to `0, 1, 2, 3`; that only happens if you also chain `.reset_index(drop=True)`. D is wrong — `sort_values` works fine with its default `axis=0`; no explicit `axis` is required.
2. **D** — When `ascending` is passed as a single bool with a multi-column `by`, pandas broadcasts that **same direction to every sort column**, not just the first. So both `score` and `age` are sorted descending: `score` desc gives Carol (92), Alice (88), then the tie at 60 between Bob (age 30) and Dave (age 40) is *also* broken descending by age, putting Dave before Bob — `['Carol', 'Alice', 'Dave', 'Bob']`. A misreads the column priority, sorting by `age` before `score`. B is the tempting "intended" result you'd get *only* if the tie-break were ascending (e.g. `ascending=[False, True]`) — but that's not what a single scalar `False` does. C is wrong — a scalar `ascending` with a list `by` is completely valid and broadcasts silently; it doesn't raise.
3. **C** — Filtering keeps only Bob/Carol/Dave at their original labels `[101, 102, 103]`; `sort_index(ascending=False)` then reorders by index label descending, giving `[103, 102, 101]`. A is what plain ascending `sort_index()` (or no sorting at all, since the filtered index already happened to be ascending) would give — it ignores `ascending=False`. B confuses this with a *positional* reset (as `.reset_index()` or `.iloc` would produce), not label-based sorting. D is wrong — `sort_index` sorts by the index itself and takes no `by` argument at all; that's precisely what distinguishes it from `sort_values`.
4. **A** — `rank()`'s default `method='average'` gives tied values the **average of the ranks they'd occupy**: sorted ascending the values are `60, 60, 88, 92`, so both `60`s tie for ranks 1 and 2 and each gets `1.5`; `88` gets rank `3.0` and `92` gets rank `4.0`. In row order (Alice, Bob, Carol, Dave) that's `[3.0, 1.5, 4.0, 1.5]`. B is what `method='first'` would give instead — breaking the tie by order of appearance (Bob gets `1.0`, Dave gets `2.0`). C incorrectly shifts every rank down by `0.5` as if ranks were 0-indexed; pandas ranks always start at `1`. D is wrong — `rank()` handles duplicates perfectly well with its default method; `method='dense'` is an optional alternative tie-breaking scheme, not a requirement.
5. **C** — `sort_values(by, axis=1)` sorts **columns** using values from a **row label** named in `by` — so `by` must be a value from `df.index` (`100`-`103`), not a column name. `'score'` isn't an index label, so this raises `KeyError: 'score'`. A is valid — `sort_index(axis=1)` needs no `by` at all; it just alphabetizes the column labels (`age`, `name`, `score`). B is valid — `'dense'` is a real, documented `rank()` method. D is valid — `kind='quicksort'` is (and happens to be) the default sorting algorithm for `sort_values`, and combining it with `ascending=False` is unremarkable.
