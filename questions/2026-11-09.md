## Q1. Building on Day 43's team/score dataset, Grace now gets the same kind of data from an API as a list of nested JSON-style records instead of a flat dict, and flattens it with `pd.json_normalize`. What does this print? (Roadmap #37, #14)

```python
import pandas as pd

records = [
    {'name': 'Alice', 'team': 'Red', 'stats': {'score': 88, 'bonus': 1}},
    {'name': 'Bob', 'team': 'Blue', 'stats': {'score': 45, 'bonus': 2}},
    {'name': 'Carol', 'team': 'Red', 'stats': {'score': 92, 'bonus': 3}},
]
flat = pd.json_normalize(records)
print(flat.columns.tolist())
print(flat.loc[0, 'stats.score'], flat.loc[1, 'stats.bonus'])
```
A. `['name', 'team', 'stats']` then `88 2` — correct values but wrongly assumes `json_normalize` leaves the nested dict untouched as a single `stats` column of dict objects, which is what plain `pd.DataFrame(records)` would do — `json_normalize`'s entire job is to flatten nested keys into their own dotted columns instead
B. `['name', 'team', 'stats.score', 'stats.bonus']` then `88 2` — `pd.json_normalize` walks each record's nested dict and flattens it into separate top-level columns, joining the parent key and child key with `.` by default (`stats.score`, `stats.bonus`). Looking up `flat.loc[0, 'stats.score']` gives Alice's `88`, and `flat.loc[1, 'stats.bonus']` gives Bob's `2`
C. `['name', 'team', 'stats_score', 'stats_bonus']` then `88 2` — gets the flattening right but wrongly assumes the default join character between parent and child keys is an underscore (`_`) rather than a dot (`.`) — underscore only appears if you explicitly pass `sep='_'`
D. Raises `ValueError` — wrongly assumes `json_normalize` can't handle a dict value nested inside a list of records, when flattening exactly this shape is `json_normalize`'s core purpose

## Q2. Building on Q1, Grace's teammate prefers snake_case column names, so she redoes the same flatten with an explicit `sep`. What does this print? (Roadmap #37)

```python
flat_us = pd.json_normalize(records, sep='_')
print(flat_us.columns.tolist())
print(flat_us.loc[2, 'stats_score'])
```
A. `['name', 'team', 'stats.score', 'stats.bonus']` then `92` — wrongly assumes `sep='_'` has no effect and the dot separator from Q1 still applies regardless of what's passed
B. Raises `TypeError` — wrongly assumes `sep` isn't a real keyword argument that `json_normalize` accepts
C. `['name', 'team', 'stats_score', 'stats_bonus']` then `92` — `sep` controls exactly the character used to join a nested key's path to its parent when flattening; passing `sep='_'` swaps every `.` from Q1's default for `_`, giving `stats_score`/`stats_bonus`. The row values themselves are unaffected by the separator choice, so Carol's row (index 2) still shows a score of `92`
D. `['name', 'team', 'score', 'bonus']` then `92` — wrongly assumes `sep='_'` strips the parent key prefix entirely rather than just changing the joining character, as if `sep` meant "drop the prefix" instead of "use this separator"

## Q3. Building on Day 44's team Red/Blue roster scenario, Grace's JSON now has one entry per team holding a nested list of players, and she wants one output row per player with the team's info attached. What does this print? (Roadmap #37, #13)

```python
teams = [
    {'team': 'Red', 'region': 'North', 'roster': [
        {'name': 'Alice', 'score': 88},
        {'name': 'Carol', 'score': 92},
    ]},
    {'team': 'Blue', 'region': 'South', 'roster': [
        {'name': 'Bob', 'score': 45},
    ]},
]
expanded = pd.json_normalize(teams, record_path='roster', meta=['team', 'region'])
print(expanded.columns.tolist())
print(len(expanded))
print(expanded.loc[2, 'team'], expanded.loc[2, 'region'], expanded.loc[2, 'name'])
```
A. `['name', 'score', 'team', 'region']` then `3` then `Blue South Bob` — `record_path='roster'` tells `json_normalize` to explode each team's nested `roster` list into its own row, one row per player; `meta=['team', 'region']` copies those two top-level fields onto every row produced from that team. Two teams with 2 and 1 players give 3 total rows, and row index 2 is Blue's only player, Bob, with `team='Blue'`, `region='South'` attached
B. `['team', 'region', 'name', 'score']` then `3` then `Blue South Bob` — gets the row count and values right but wrongly assumes the resulting column order puts the `meta` fields first, when `json_normalize` actually places the `record_path` fields first and appends the `meta` fields after
C. `['name', 'score', 'team', 'region']` then `2` then `Red North Carol` — wrongly assumes `json_normalize` produces one row per *team* (2 rows) rather than one row per *player* across all teams, as if `record_path` only validated the list existed rather than actually exploding it
D. `['name', 'score', 'team', 'region']` then `3` then `Blue South Alice` — gets the shape right but wrongly assumes `meta` values get matched up positionally across the *whole* flattened result rather than being tied back to each row's own originating team, mixing Blue's row with Red's player name

## Q4. Spot the bug — Grace's JSON feed has one team record where whoever built it forgot to include the `team` field at all. What does this print? (Roadmap #37)

```python
teams = [
    {'team': 'Red', 'roster': [{'name': 'Alice', 'score': 88}]},
    {'roster': [{'name': 'Bob', 'score': 45}]},
]
try:
    expanded = pd.json_normalize(teams, record_path='roster', meta=['team'])
    print(expanded.to_dict('records'))
except Exception as e:
    print(type(e).__name__)

fixed = pd.json_normalize(teams, record_path='roster', meta=['team'], errors='ignore')
print(fixed.to_dict('records'))
```
A. `AttributeError` then `[{'name': 'Alice', 'score': 88, 'team': 'Red'}, {'name': 'Bob', 'score': 45, 'team': nan}]` — wrongly names the exception; by default a record missing a requested `meta` field isn't silently tolerated, but the specific error pandas raises here is `KeyError`, not `AttributeError`
B. `KeyError` then `[{'name': 'Alice', 'score': 88, 'team': 'Red'}, {'name': 'Bob', 'score': 45, 'team': nan}]` — by default, `json_normalize` requires every record to actually have each `meta` field; Bob's team entry is missing `'team'` entirely, so the first call raises `KeyError`. Passing `errors='ignore'` tells it to fill in `NaN` for any record missing a requested `meta` field instead of raising, which is exactly why the second call succeeds, with Bob's `team` coming through as `NaN` while Alice's still shows `'Red'`
C. Nothing is printed from the first call, then `[{'name': 'Alice', 'score': 88, 'team': 'Red'}, {'name': 'Bob', 'score': 45, 'team': 'Red'}]` — wrongly assumes a missing `meta` key quietly reuses the previous record's value rather than either raising or filling `NaN`
D. `KeyError` then raises the same `KeyError` again — wrongly assumes `errors='ignore'` has no actual effect and the second call fails identically to the first, rather than suppressing the error and filling `NaN`

## Q5. Contrasting with Q1, Grace checks what a plain `pd.DataFrame(records)` does with the exact same nested records, versus `json_normalize`, when one record is also missing a nested key. What does this print? (Roadmap #37, #35)

```python
records = [
    {'name': 'Alice', 'stats': {'score': 88, 'bonus': 1}},
    {'name': 'Bob', 'stats': {'score': 45}},
]
plain = pd.DataFrame(records)
flat = pd.json_normalize(records)
print(plain.columns.tolist())
print(type(plain.loc[0, 'stats']))
print(flat.columns.tolist())
print(flat['stats.bonus'].tolist())
print(flat['stats.bonus'].dtype)
```
A. `['name', 'stats']` then `<class 'dict'>` then `['name', 'stats.score', 'stats.bonus']` then `[1.0, nan]` then `float64` — plain `pd.DataFrame(records)` leaves each record's nested dict untouched as a single `stats` column holding actual Python `dict` objects. `json_normalize`, by contrast, flattens it and also fills Bob's missing `'bonus'` key with `NaN` — and since mixing a real int (`1`) with `NaN` in one column forces pandas to upcast the whole column to `float64`, Alice's bonus prints as `1.0`, not `1`
B. `['name', 'stats']` then `<class 'dict'>` then `['name', 'stats.score', 'stats.bonus']` then `[1, nan]` then `float64` — correctly contrasts the two constructors but wrongly assumes a column can mix an actual Python `int` with `NaN` and keep the int's own type — once any value in a `float64` column is `NaN`, the *entire* column, including Alice's originally-int bonus, is upcast and prints as `1.0`
C. `['name', 'stats.score', 'stats.bonus']` then `<class 'numpy.float64'>` then `['name', 'stats.score', 'stats.bonus']` then `[1.0, nan]` then `float64` — wrongly assumes plain `pd.DataFrame(records)` already flattens nested dicts the same way `json_normalize` does, when only `json_normalize` performs that flattening — a plain `DataFrame` constructor just stores whatever object sits in each dict value, dict included
D. `['name', 'stats']` then `<class 'dict'>` then `['name', 'stats.score', 'stats.bonus']` then `[1.0, 0.0]` — gets the constructor contrast right but wrongly assumes a missing nested key gets filled with `0.0` instead of `NaN`, as if `json_normalize` treated an absent key as a numeric default rather than genuinely missing data
