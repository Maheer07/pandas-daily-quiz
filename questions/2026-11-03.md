## Q1. Building on Day 41's recurring 2×3 `grid` of scores, Grace combines each row with a weights vector two different ways to see how `@` differs from plain elementwise `*`. What does this print? (Roadmap #34, #33)

```python
import numpy as np

grid = np.array([[88, 45, 92], [60, 75, 50]])
weights = np.array([1, 0, 1])
print((grid @ weights).tolist())
print((grid * weights).tolist())
```
A. `[180, 110]` then `[[88, 0, 92], [60, 0, 50]]` — `@` between a `(2, 3)` matrix and a `(3,)` vector performs a matrix-vector product: each output row sums `grid[i, j] * weights[j]` over `j`, giving `88*1+45*0+92*1=180` and `60*1+75*0+50*1=110`. Plain `*` instead broadcasts `weights` across every row elementwise, zeroing out column 1 but keeping the full `(2, 3)` shape rather than summing anything
B. `[[88, 0, 92], [60, 0, 50]]` then `[180, 110]` — swaps the two operators' behavior, wrongly assuming `@` broadcasts elementwise the way `*` does here, and that `*` is the one that sums across each row into a matrix-vector product
C. Raises a `ValueError`, wrongly assuming a `(2, 3)` array can't combine with a plain `(3,)` 1-D vector via `@` unless the vector is first reshaped to `(3, 1)` or `(1, 3)` — missing that `@` already treats a 1-D operand as the right shape for a matrix-vector product
D. `[180, 110]` then `[180, 110]` — correctly gets `@` right but wrongly assumes `*` also reduces by summing across each row, rather than keeping every multiplied entry in a full `(2, 3)` result

## Q2. Grace treats Q1's weighted totals as a small linear system and solves for two unknowns directly with `np.linalg.solve`, then checks the answer. What does this print? (Roadmap #34, #1)

```python
A = np.array([[2, 1], [1, 3]])
b = np.array([180, 110])
x = np.linalg.solve(A, b)
print(x)
print((A @ x).tolist())
```
A. `[86. 8.]` then `[180.0, 110.0]` — `np.linalg.solve(A, b)` finds the `x` satisfying `A @ x == b` exactly: `2x+y=180` and `x+3y=110` solve to `x=86, y=8`. Because linear-algebra routines always work in floating point, the result prints as `86.` and `8.` rather than plain ints, and multiplying back through `A @ x` exactly reconstructs `b`, now as floats
B. `[60. 20.]` then `[140.0, 120.0]` — a plausible-looking but arithmetically wrong solution to the same system; plugging it back through `A @ x` doesn't reconstruct the original `b` at all, which is exactly how you'd catch this mistake by checking the second line
C. Raises `LinAlgError`, wrongly assuming `np.linalg.solve` needs its right-hand side `b` reshaped into a square matrix too, rather than accepting a plain 1-D vector directly as the equation's right-hand side
D. `[86 8]` then `[180 110]` — correctly solves the system but wrongly assumes the result keeps `A` and `b`'s original integer dtype, when `np.linalg.solve` always promotes its output to floating point regardless of the inputs

## Q3. Contrasting with Day 41's row-vector broadcasting, Grace multiplies a column vector against a matrix two ways — transposing the vector first, then transposing the matrix instead — to see how matmul's output shape tracks which side is transposed. What does this print? (Roadmap #34, #33)

```python
row_base = np.array([[100], [200]])
mat = np.array([[1, 2, 3], [4, 5, 6]])
print((row_base.T @ mat).tolist())
print((mat.T @ row_base).tolist())
```
A. `[[900, 1200, 1500]]` then `[[900], [1200], [1500]]` — matmul's output shape is always (rows of the left operand, columns of the right operand). `row_base.T` is `(1, 2)`, so `row_base.T @ mat` ((1,2)@(2,3)) gives a `(1, 3)` row: `[100*1+200*4, 100*2+200*5, 100*3+200*6] = [900, 1200, 1500]`. `mat.T` is `(3, 2)`, so `mat.T @ row_base` ((3,2)@(2,1)) gives a `(3, 1)` column holding the *same three numbers*, just transposed into rows instead of one row
B. `[900, 1200, 1500]` then `[900, 1200, 1500]` — gets the right numbers but wrongly flattens both results into plain 1-D lists, missing that matmul on 2-D operands always returns a 2-D result, preserving the row-vector vs. column-vector shape distinction
C. Raises a `ValueError` on the first line, wrongly assuming `(1, 2)` and `(2, 3)` can't combine via `@` because the *outer* dimensions (`1` and `3`) differ, rather than checking that the *inner* dimensions (`2` and `2`) are what must match
D. `[[900, 1200, 1500]]` then `[[900, 1200, 1500]]` — correctly gets the first line but wrongly assumes `mat.T @ row_base` produces the same shape as the first result, instead of its transpose — forgetting that swapping which operand is transposed also swaps the output's row/column orientation

## Q4. Grace checks several ways of sizing a plain vector with `np.linalg.norm`, to know which one to reach for later. What does this print? (Roadmap #34)

```python
v = np.array([3, -4])
print(np.linalg.norm(v))
print(np.linalg.norm(v, ord=1))
print(np.linalg.norm(v, ord=np.inf))
```
A. `5.0` then `7.0` then `4.0` — with no `ord` given, `np.linalg.norm` computes the Euclidean (L2) norm: `sqrt(3**2 + (-4)**2) = sqrt(25) = 5.0`. `ord=1` sums the absolute values instead: `|3| + |-4| = 7.0`. `ord=np.inf` takes the single largest absolute value: `max(3, 4) = 4.0`
B. `7.0` then `5.0` then `4.0` — swaps the default behavior with `ord=1`, wrongly assuming the no-`ord` case sums absolute values rather than computing the Euclidean norm
C. `5.0` then `4.0` then `7.0` — gets the default right but swaps `ord=1` and `ord=np.inf`, wrongly assuming `ord=1` picks the maximum magnitude and `ord=np.inf` sums the absolute values
D. `5.0` then `7.0` then `7.0` — gets the first two right but wrongly assumes `ord=np.inf` behaves like `ord=1` (summing absolute values) instead of taking the largest single magnitude

## Q5. Spot the bug: Grace reuses Q1's `grid` with a column of weights to get one weighted score per row, then tries to get the same numbers a second way by transposing the weights first. What does this print? (Roadmap #34, #33)

```python
weights2 = np.array([[0.5], [0.3], [0.2]])
print((grid @ weights2).tolist())
print(grid.dot(weights2.T).tolist())
```
A. `[[75.9], [62.5]]` then raises `ValueError` — `grid` is `(2, 3)` and `weights2` is `(3, 1)`; their shared inner dimension (`3`) lines up, giving one weighted sum per row: `88*0.5+45*0.3+92*0.2=75.9` and `60*0.5+75*0.3+50*0.2=62.5`. Transposing `weights2` to `(1, 3)` breaks that alignment — `grid.dot(weights2.T)` now pairs `grid`'s inner dimension (`3`) against `weights2.T`'s inner dimension (`1`), which don't match, so `.dot()` raises `ValueError` rather than silently reusing the first result
B. `[[75.9], [62.5]]` then `[[75.9], [62.5]]` — wrongly assumes `.dot()` tolerates a shape mismatch here the way elementwise `*` would broadcast it, rather than strictly enforcing that matrix multiplication's inner dimensions must match
C. Raises `ValueError` on the first line too — wrongly assumes `grid`'s `(2, 3)` and `weights2`'s `(3, 1)` shapes don't share a valid inner dimension, missing that `3` matches cleanly on both sides
D. `[[75.9, 62.5]]` then raises `ValueError` — correctly spots that the second line fails but wrongly flips the first result's shape, assuming `grid @ weights2` returns a `(1, 2)` row instead of the actual `(2, 1)` column

## Answer key

1. **A** — `@` between `grid` (`2, 3`) and `weights` (`3,`) performs a real matrix-vector product, summing `grid[i,j]*weights[j]` across each row to give `[180, 110]`. Plain `*` instead broadcasts `weights` elementwise across every row without summing, keeping the full `(2, 3)` shape with column 1 zeroed out: `[[88, 0, 92], [60, 0, 50]]`. B swaps which operator sums and which broadcasts. C invents a reshape requirement `@` doesn't need for a 1-D operand. D wrongly assumes `*` also collapses to a sum rather than staying elementwise.
2. **A** — `np.linalg.solve` finds the exact `x` satisfying `A @ x == b`: solving `2x+y=180`, `x+3y=110` gives `x=86, y=8`, printed as floats (`[86. 8.]`) since linear-algebra routines always compute in floating point. `A @ x` then exactly reconstructs `b` as `[180.0, 110.0]`. B is simply the wrong solution to the system — a useful distractor precisely because checking it against `A @ x` (giving `[140.0, 120.0]`, not `b`) is how you'd catch the error. C invents a restriction that doesn't exist; `solve` accepts a 1-D right-hand side directly. D wrongly assumes the output keeps the inputs' integer dtype instead of being promoted to float.
3. **A** — matmul's result shape is always (left operand's rows, right operand's columns). `row_base.T` (`1, 2`) against `mat` (`2, 3`) gives a `(1, 3)` row `[900, 1200, 1500]`; `mat.T` (`3, 2`) against `row_base` (`2, 1`) gives a `(3, 1)` column holding the same three numbers. B wrongly flattens both into plain 1-D lists, losing the shape distinction matmul always preserves on 2-D inputs. C checks the wrong pair of dimensions — matmul cares about the *inner* dimensions matching (both `2` here), not the outer ones. D correctly gets the first result but wrongly assumes the second keeps the same row-vector shape instead of becoming a column vector.
4. **A** — no `ord` means the default Euclidean (L2) norm, `sqrt(3**2+(-4)**2)=5.0`; `ord=1` sums absolute values, `7.0`; `ord=np.inf` takes the largest absolute value, `4.0`. B swaps the default L2 norm with the `ord=1` sum. C swaps `ord=1` and `ord=np.inf`'s behaviors. D wrongly treats `ord=np.inf` as if it summed like `ord=1`, instead of taking the single largest magnitude.
5. **A** — `grid` (`2, 3`) and `weights2` (`3, 1`) share inner dimension `3`, so `grid @ weights2` gives one weighted row-sum each: `75.9` and `62.5`. Transposing `weights2` to `(1, 3)` breaks that alignment — `grid`'s inner dimension (`3`) no longer matches `weights2.T`'s inner dimension (`1`), so `.dot()` raises `ValueError` instead of reusing the first answer. B wrongly assumes `.dot()` tolerates the mismatch the way broadcasting `*` would. C wrongly claims the *first* line's shapes don't align, when `3` matches cleanly there. D gets the second line's failure right but wrongly transposes the first result's own shape.
