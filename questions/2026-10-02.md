## Q1. Combining Day 18's `merge` with Day 16's `groupby`, what does this print? (Roadmap #13, #15)

```python
import pandas as pd
data = {'name': ['Alice', 'Bob', 'Carol', 'Dave'],
        'team': ['Red', 'Blue', 'Red', 'Green'],
        'score': [88, 45, 92, 60]}
df = pd.DataFrame(data, index=[100, 101, 102, 103])

team_info = pd.DataFrame({'team': ['Red', 'Blue', 'Yellow'],
                           'manager': ['Grace', 'Heidi', 'Ivan']})

merged = df.merge(team_info, on='team', how='left')
print(merged.groupby('manager')['score'].mean())
```

```

```
C. Raises a `KeyError`, because `merged` has no `manager` column — `merge(..., how='left')` only keeps columns from the left frame (`df`)
D.
```

Grace    90.0
Name: score, dtype: float64
```

## Q3. Spot the bug: building on Day 17's team+region DataFrame, this is meant to attach each row's region manager via `merge`, but doesn't do what's intended. What actually happens? (Roadmap #15)

```python
import pandas as pd
data6 = {'name': ['Alice', 'Bob', 'Carol', 'Dave', 'Eve', 'Frank'],
         'team': ['Red', 'Blue', 'Red', 'Blue', 'Red', 'Blue'],
         'region': ['North', 'South', 'North', 'North', 'South', 'South'],
         'score': [88, 45, 92, 60, 75, 50]}
df6 = pd.DataFrame(data6, index=[100, 101, 102, 103, 104, 105])

region_info = pd.DataFrame({'region': ['North', 'South'],
                             'manager': ['Grace', 'Heidi']})

result = df6.merge(region_info, on='team')
print(result[['name', 'manager']])
```
A. Raises a `KeyError`, because `region_info` has no `team` column — `on=` must name a column present in **both** frames, and the shared key here is `region`, not `team`
B. Merges silently by row position instead, producing a `manager` column of `['Grace', 'Heidi', 'Grace', 'Heidi', 'Grace', 'Heidi']`
C. Raises a `MergeError`, because `df6` has 6 rows while `region_info` has only 2, and `merge` requires both frames to have the same number of rows
D. Succeeds silently, because `merge` falls back to matching on whichever column name *is* shared (`region`) whenever the requested `on=` key is invalid

## Q5. Chaining `merge` straight into `groupby`, using `df6` and `region_info` from Q3, what does this print? (Roadmap #13, #15)

```python
result = (df6.merge(region_info, on='region', how='left')
             .groupby('manager')['score']
             .mean())
print(result)
```
A.
```
manager
Grace    80.000000
Heidi    56.666667
Name: score, dtype: float64
```
B.
```
manager
Heidi    56.666667
Grace    80.000000
Name: score, dtype: float64
```
C. Raises a `KeyError`, because `manager` doesn't exist on `df6` until you explicitly reselect columns after `.merge()` — chaining `.groupby('manager')` straight onto the merge result isn't valid
D. Raises a `TypeError`, because `.mean()` can't be called directly on a `.groupby(...)['score']` object — `.agg('mean')` must be used instead

## Answer key

1. **A** — `merge(..., how='left')` keeps every row of `df` and looks up a matching `manager`; Alice/Carol (`Red`) get `Grace`, Bob (`Blue`) gets `Heidi`, and Dave (`Green`) has no match in `team_info` so his `manager` comes back `NaN`. Crucially, `groupby()` **drops rows whose key is `NaN` by default** (`dropna=True`), so Dave's row is silently excluded from the grouping entirely — the result only has the `Grace`/`Heidi` groups, sorted alphabetically: `Grace 90.0` (mean of 88, 92), `Heidi 45.0`. B wrongly assumes `groupby` keeps a `NaN` group for Dave's unmatched row — it doesn't unless you explicitly pass `dropna=False`. C is wrong — `merge()` always adds the *other* frame's non-key columns (here, `manager`) into the result; `how='left'` controls which **rows** survive, not which columns get pulled in. D has the right two numbers but swaps which group prints first — groups are sorted alphabetically by key (`Grace` before `Heidi`), not by order of first appearance in the data (Bob/Heidi actually appears before Carol/Grace's second row, but that has no bearing on `sort=True`, the default).
2. **A** — `Series.map()` can take another `Series` as its mapping: it looks up each value of `df['team']` in `team_avg`'s **index** and substitutes the corresponding value, giving `Alice→90.0 (Red)`, `Bob→45.0 (Blue)`, `Carol→90.0 (Red)`, `Dave→60.0 (Green)` — a clean vectorized lookup. B is wrong — `.apply()` expects a *callable*; `team_avg` is a `Series`, not a function, so calling `team_avg(x)` for each element raises `TypeError: 'Series' object is not callable`. C is wrong — `df.apply(...)` with no `axis` defaults to `axis=0`, so the lambda receives each **column** as `row`, and `row.name` is the *column's* label (e.g. `'name'`, `'team'`, `'score'`) rather than a team name — `team_avg['name']` isn't a key in `team_avg`'s index (`['Blue', 'Green', 'Red']`), so it raises `KeyError`. D is wrong — directly assigning `df.groupby('team')['score'].mean()` (indexed by team name: `Blue`, `Green`, `Red`) to a column on `df` (indexed `100-103`) makes pandas align by index; since none of those labels match, the entire new column comes back `NaN` for every row instead of the per-row lookup `.map()` performs.
3. **A** — `on=` must name a column that exists in **both** frames being merged. `region_info` only has `region` and `manager` — it has no `team` column at all — so `df6.merge(region_info, on='team')` raises `KeyError: 'team'` immediately; it never gets to attach anything. B is wrong — `merge()` never silently falls back to row-position (positional) matching; it strictly matches by the key column's values, and here it can't even find that key column to begin with. C is wrong — `merge()` places no constraint on the two frames having equal row counts; merges routinely combine frames of very different sizes. D is wrong — there's no "fallback to the shared column name" behavior in `merge()`; an invalid or missing `on=` key is always a hard error, not a silent substitution.
4. **D** — `df6` only has `name`, `team`, `region`, and `score` columns — there is no `age` column — so `.agg({'score': 'mean', 'age': 'max'})` raises `KeyError: 'Column(s) [\'age\'] do not exist'`. A is valid — selecting `['score']` before `.agg(['mean', 'max'])` cleanly narrows to the numeric column, avoiding the string-column trap from earlier days. B is valid — `region` is a genuine shared column between `df6` and `region_info`, so this merge runs fine (and is exactly the fix for Q3's bug). C is valid — a dict passed to `Series.map()` just returns `NaN` for any value without a matching key (here, `45`, `60`, `75`, `50`); it never raises.
5. **A** — The merge attaches each row's region manager (`North→Grace`, `South→Heidi`) to all 6 rows; grouping by `manager` and averaging gives `Grace`'s rows (Alice 88, Carol 92, Dave 60) a mean of `80.0`, and `Heidi`'s rows (Bob 45, Eve 75, Frank 50) a mean of `56.666667`. As in Q1, groups print in alphabetical order of the key (`Grace` before `Heidi`), regardless of row order in the data. B has the right two numbers but the wrong order — this is the "order of first appearance" trap again (`Heidi`'s group has the first-appearing row, Bob, but that doesn't control sort order). C is wrong — `merge()` returns a perfectly normal DataFrame with `manager` as a real column; chaining `.groupby('manager')` straight onto it is completely standard, no reselection needed. D is wrong — `.mean()` is a valid aggregation method that can be called directly on a grouped-and-selected Series (`.groupby(...)['score']`); `.agg()` is only *one* of several equivalent ways to do this, not a requirement.
