## Q3. Which statement correctly describes the result of `a + b` below?

```python
import pandas as pd
a = pd.Series([1, 2, 3], index=['x', 'y', 'z'])
b = pd.Series([10, 20, 30], index=['y', 'z', 'w'])
print(a + b)
```
A. Values are aligned by index label; `'x'` and `'w'` become `NaN` because each is missing from one of the two Series, while `'y'` (2+10=12) and `'z'` (3+20=23) sum correctly.
B. Pandas ignores the index during arithmetic and adds position-by-position like NumPy, giving `[11, 22, 33]`.
C. Raises a ValueError because the two Series don't share identical indices.
D. Only the overlapping labels `'y'` and `'z'` appear in the result; `'x'` and `'w'` are dropped entirely, like an inner join.

## Q5. Building on Day 1/5's dtype-upcasting rule for NumPy arrays, what does this print?

```python
import pandas as pd
s = pd.Series([1, 2, 3, 4.5])
print(s.dtype)
```
A. float64
B. int64
C. object
D. Raises a TypeError because the list mixes int and float

## Answer key

1. **A** — A `Series` created without an explicit `index` gets a default `RangeIndex`, which prints as `RangeIndex(start=0, stop=3, step=1)`, not a plain Python list. B confuses the `Index` object's repr with a bare list. C uses old pandas terminology (`Int64Index` was removed/merged into the generic `Index`/`RangeIndex` in modern pandas) and isn't what actually prints. D is wrong — an explicit index is optional; pandas always supplies a default one.
2. **A** — Boolean masking on a Series works just like on a NumPy array (Day 6), but the result **keeps the original index labels** attached to the surviving values: `temps > 80` is `[F,F,T,F,T]`, so only `'wed'` (95) and `'fri'` (88) survive, each still tagged with its label. B wrongly assumes the result is a bare array, dropping the index — that's what you'd get from `.to_numpy()[mask]`, not from indexing the Series itself. C wrongly includes `'thu'` (61), which fails the `> 80` condition. D is false: Series boolean indexing is exactly as valid as it is on the underlying ndarray.
3. **A** — Arithmetic between two Series aligns values by index label first, on the **union** of both indices: `'y'` and `'z'` appear in both, so they add normally (`12`, `23`); `'x'` only exists in `a` and `'w'` only in `b`, so each becomes `NaN` since there's no matching value to combine with. B describes NumPy's shape-based positional behavior, but Series arithmetic is label-based, not positional — this is precisely the gotcha that distinguishes a Series from a plain ndarray. C is wrong — mismatched indices don't raise an error, they produce `NaN` for the unmatched labels. D describes an inner-join-style result, but default Series addition is an outer alignment (keeps every label, fills gaps with `NaN`) rather than dropping unmatched ones.
4. **A** — When a dict is passed to `Series` alongside an explicit `index`, the data is reindexed to match that `index` exactly: keys present in both (`'a'`, `'b'`) keep their values, a key in `index` but missing from the dict (`'d'`) becomes `NaN`, and a dict key *not* listed in `index` (`'c'`) is dropped entirely — and the presence of `NaN` upcasts the dtype to `float64`. B wrongly assumes `index` is ignored and the Series just uses the dict's own keys/order/dtype. C wrongly assumes an index label with no matching dict key raises immediately, rather than simply yielding `NaN`. D wrongly keeps `'c'` even though it isn't part of the supplied `index` — passing `index` really does filter the dict down, it doesn't just append extra labels on top.
5. **A** — Just like a NumPy array (Day 1/5), a pandas Series built from a list containing any float silently upcasts the *entire* Series to `float64`, even though three of the four values are plain ints. B wrongly assumes the ints "win" and the float gets coerced down instead. C wrongly assumes mixed numeric types force the catch-all `object` dtype — `object` only kicks in for genuinely incompatible types (e.g. mixing numbers with strings), not int/float, which have a clean common numeric type. D wrongly assumes an error is raised — the upcast happens silently, exactly as it does in NumPy.
