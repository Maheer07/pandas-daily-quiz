## Q1. Building on Day 37's point about `groupby()` sorting group keys alphabetically, Grace converts the recurring `df6`'s `team` column to a memory-saving dtype. What does this print? (Roadmap #32, #13)

```python
import pandas as pd

data6 = {'name': ['Alice', 'Bob', 'Carol', 'Dave', 'Eve', 'Frank'],
         'team': ['Red', 'Blue', 'Red', 'Blue', 'Red', 'Blue'],
         'region': ['North', 'South', 'North', 'North', 'South', 'South'],
         'score': [88, 45, 92, 60, 75, 50]}
df6 = pd.DataFrame(data6, index=[100, 101, 102, 103, 104, 105])

df6['team'] = df6['team'].astype('category')
print(df6['team'].dtype)
print(df6['team'].cat.categories.tolist())
```
A. `category` then `['Blue', 'Red']` — `astype('category')` changes the column's dtype label to `category` and infers its category list from the distinct values present; pandas stores that list sorted (alphabetically for strings) by default, not in first-appearance order, so `'Blue'` comes before `'Red'` even though row 100's `'Red'` appears first in the data — the same alphabetical-by-default behavior Day 37 showed for `groupby()`'s group keys
B. `category` then `['Red', 'Blue']` — wrongly assumes categories preserve first-appearance order (the same mistaken assumption Day 37's Q2 called out for `groupby()`'s default key ordering), rather than pandas' actual alphabetical default
C. `object` then `['Blue', 'Red']` — wrongly assumes `astype('category')` only reorders the values in place without actually changing the column's underlying dtype label
D. Raises `AttributeError`, assuming only an explicitly constructed `pd.Categorical()` exposes a `.cat` accessor, and that a column produced via `.astype('category')` doesn't

## Q2. Grace checks how much `astype('category')` would actually matter here by inspecting the raw integer dtype of `score` first. What does this print? (Roadmap #32, #1)

```python
print(df6['score'].dtype)
print(pd.to_numeric(df6['score'], downcast='integer').dtype)
```
A. `int64` then `int8` — pandas creates integer columns from plain Python ints using the platform default, `int64`; `pd.to_numeric(..., downcast='integer')` inspects the column's actual value range (`45`–`92`) and picks the smallest *signed* integer subtype that can safely hold every value — `int8` (`-128` to `127`) easily covers that range, so it downcasts all the way there
B. `int64` then `int64` — wrongly assumes `downcast='integer'` is a no-op unless a specific target subtype like `'int8'` is named explicitly, rather than something that inspects the data's own range automatically
C. `int64` then `uint8` — gets the byte width right but wrongly assumes `downcast='integer'` defaults to an *unsigned* subtype; `'integer'` only ever considers signed types, and `'unsigned'` is the separate option that would actually produce `uint8` here
D. Raises `TypeError`, wrongly assuming `pd.to_numeric()` can only be called on a plain Python list or NumPy array, not directly on a pandas Series column

## Q3. Contrasting with Day 37's team-percentage column, Grace "downcasts" it to save space by calling `.astype(int)` directly, without rounding first. What does this print? (Roadmap #32, #30)

```python
pct = df6['score'] / df6.groupby('team')['score'].transform('sum') * 100
print(pct.astype(int).tolist())
```
A. `[34, 29, 36, 38, 29, 32]` — the true percentages are `[34.51, 29.03, 36.08, 38.71, 29.41, 32.26]`; `astype(int)` truncates toward zero rather than rounding, simply dropping each value's decimal portion, which gives this list
B. `[35, 29, 36, 39, 29, 32]` — wrongly assumes `astype(int)` rounds to the nearest whole number the way `round()` would; this only disagrees with the correct truncated result at Alice's (`34.51`→`35` vs. the correct `34`) and Dave's (`38.71`→`39` vs. the correct `38`) positions, exactly where rounding and truncation diverge
C. Raises `ValueError`, wrongly assuming a float Series with non-integer values must be passed through `.round()` before `astype(int)` can convert it
D. `[34.0, 29.0, 36.0, 38.0, 29.0, 32.0]` — wrongly assumes `astype(int)` keeps the float dtype and only changes how the values are *displayed*, rather than actually converting the column to a true integer dtype

## Q4. Grace confirms *why* she's bothering with `category` at all by comparing memory footprints on the original `team` column. What does this print? (Roadmap #32, #23)

```python
team_obj = pd.Series(data6['team'], index=df6.index)
print(team_obj.memory_usage(deep=True))
print(team_obj.memory_usage(deep=False))
print(team_obj.astype('category').memory_usage(deep=True))
```
A. `363` then `96` then `159` — `deep=True` on an `object` column walks every actual Python string to measure its real size, giving `363` bytes total; the default `deep=False` only estimates an `object` column by its pointer width, wildly undercounting the true string data at just `96` bytes; converting to `category` instead stores a small integer `codes` array plus one shared array of the 2 distinct strings, bringing the genuinely-measured cost down to `159` bytes even with `deep=True`
B. `96` then `363` then `159` — swaps the two object-column figures, wrongly assuming the *default* call (`deep=False`) is the one that scans actual string content, while the explicit `deep=True` gives the cheap pointer-only estimate
C. `363` then `96` then `363` — gets the object-column figures right but wrongly assumes converting to `category` can't reduce the true, deeply-measured memory cost any further than the original `object` dtype
D. `363` then `96` then `48` — gets the object-column figures right but wrongly assumes a `category` column costs nothing beyond the index's own overhead, forgetting it still must store a small `codes` array and the categories themselves

## Q5. Building on Day 34's boolean-filtering review, Grace ranks each person into a performance tier and tries to filter for "better than Low" with a plain comparison. What does this print? (Roadmap #32, #28)

```python
df6['tier'] = df6['score'].map(
    {88: 'High', 45: 'Low', 92: 'High', 60: 'Mid', 75: 'Mid', 50: 'Low'}
).astype(pd.CategoricalDtype(categories=['Low', 'Mid', 'High']))

try:
    print(df6[df6['tier'] > 'Low']['name'].tolist())
except Exception as e:
    print(type(e).__name__)

df6['tier'] = df6['tier'].astype(pd.CategoricalDtype(categories=['Low', 'Mid', 'High'], ordered=True))
print(df6[df6['tier'] > 'Low']['name'].tolist())
```
A. `TypeError` then `['Alice', 'Carol', 'Dave', 'Eve']` — `pd.CategoricalDtype(categories=[...])` defaults to `ordered=False`, and pandas refuses to rank unordered categories with `<`/`>` (only equality/inequality checks are allowed), so the first comparison raises `TypeError`; re-casting with `ordered=True` turns `'Low' < 'Mid' < 'High'` into a real ranking, keeping everyone whose tier beats `'Low'` — Alice/Carol (`High`) and Dave/Eve (`Mid`)
B. `[]` then `['Alice', 'Carol', 'Dave', 'Eve']` — wrongly assumes an unordered categorical silently returns an empty/false-y comparison result instead of raising an error outright
C. `TypeError` then `TypeError` — correctly spots the first error but wrongly assumes re-casting to a brand-new `CategoricalDtype` with `ordered=True` still somehow carries over the original dtype's `ordered=False` setting
D. `['Alice', 'Carol']` then `['Alice', 'Carol', 'Dave', 'Eve']` — wrongly assumes the unordered categorical silently falls back to treating `>` as "strictly the single top category" rather than refusing the comparison entirely

## Answer key

1. **A** — `astype('category')` relabels the column's dtype as `category` and derives its categories from the distinct values present, storing that list sorted alphabetically by default rather than in first-appearance order; `'Blue'` sorts before `'Red'` even though `'Red'` appears first in row 100 — the identical default-sorting behavior Day 37 demonstrated for `groupby()`'s group keys. B imports exactly the wrong assumption Day 37's Q2 warned against (first-appearance order instead of the real alphabetical default). C is wrong about what `astype` actually does — it does change the dtype label, not just reorder values. D is wrong — any Series with `category` dtype, however it was produced, exposes a `.cat` accessor.
2. **A** — Plain Python integers become `int64` by default; `pd.to_numeric(..., downcast='integer')` looks at the column's real range (`45`-`92`) and picks the smallest signed subtype that can represent it without overflow, which is `int8` (`-128` to `127`). B wrongly treats `downcast='integer'` as inert without an explicit target subtype, when inspecting the actual data range *is* the whole point of the parameter. C correctly sizes the result to 8 bits but wrongly assumes `'integer'` defaults to unsigned — `'unsigned'` is pandas' separate, explicit option for that. D invents a restriction that doesn't exist; `pd.to_numeric()` works directly on Series input.
3. **A** — the real percentages (`34.51, 29.03, 36.08, 38.71, 29.41, 32.26`) each get their decimal portion dropped by `astype(int)`'s truncation-toward-zero behavior, giving `[34, 29, 36, 38, 29, 32]`. B assumes rounding instead of truncation; the two approaches only disagree at Alice's and Dave's positions (`35` vs `34`, `39` vs `38`), which is exactly what makes this distractor plausible rather than obviously wrong. C invents a restriction — `astype(int)` converts non-integer floats just fine, it simply discards the fractional part rather than rounding it. D misunderstands `astype` as a display-only operation rather than an actual dtype conversion.
4. **A** — `deep=True` genuinely measures each Python string's size for an `object` column (`363` bytes here, including the Series' own index overhead), while `deep=False` is a cheap estimate based only on pointer width, undercounting to `96` bytes; converting to `category` replaces those repeated strings with a tiny `codes` array plus one small array of the 2 unique strings, so even a true `deep=True` measurement drops to `159` bytes. B swaps which call does the expensive scan versus the cheap estimate. C wrongly assumes `category` dtype can't actually shrink the deeply-measured footprint, missing the entire motivation for using it on low-cardinality columns. D underestimates what a `category` column still has to store — codes plus the categories array, not just index overhead.
5. **A** — a `CategoricalDtype` is unordered unless `ordered=True` is passed explicitly, and pandas deliberately raises `TypeError` rather than silently answering `<`/`>` comparisons on an unordered categorical (equality/inequality still work fine). Re-casting to an explicitly `ordered=True` dtype over the same `['Low', 'Mid', 'High']` categories makes `'Low' < 'Mid' < 'High'` a real ranking, so `> 'Low'` keeps Alice and Carol (`High`) plus Dave and Eve (`Mid`), leaving out Bob and Frank (`Low`). B wrongly assumes a silent, falsy fallback instead of pandas' actual hard error. C wrongly assumes `ordered` carries over from the original dtype instead of being fully replaced by the new `CategoricalDtype` passed to `astype`. D invents a nonexistent "top category only" interpretation of `>` rather than pandas simply refusing the comparison outright.
